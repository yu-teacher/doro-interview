**모범 답변 (30~60초)**
`KEYS`는 한 번에 패턴에 맞는 모든 키를 찾는 O(N) 명령이라, Redis가 명령을 차례로 처리하는 탓에 키가 많으면 그동안 다른 요청이 막힙니다. 그래서 문서는 애플리케이션 코드에서 쓰지 말라고 경고합니다. `SCAN`은 커서를 받아 한 번에 조금씩만 돌려주고 다음 커서를 알려 주므로 서버를 오래 붙잡지 않습니다. 커서 0으로 시작해 응답의 커서가 0이 될 때까지 반복하면 되고, 순회 내내 존재한 키는 반드시 나오지만 같은 키가 여러 번 나올 수 있어 애플리케이션이 중복을 견뎌야 합니다. `COUNT`는 작업량의 힌트일 뿐이라 반환 개수를 보장하지 않고, 빈 결과가 와도 커서가 0이 아니면 끝난 게 아닙니다.

```
SCAN 0 MATCH user:* COUNT 100
# 응답: 다음 커서와 키 배열 -> 커서가 0이 될 때까지 반복
```

(공식 문서) KEYS 문서는 O(N)이고 큰 데이터베이스에서 성능을 해칠 수 있어 디버깅과 특수 작업용이며 일반 애플리케이션 코드에서 쓰지 말고 SCAN이나 집합을 고려하라고 한다. SCAN 문서는 증분 순회라서 KEYS나 SMEMBERS처럼 수 초간 서버를 막는 문제 없이 운영에서 쓸 수 있고, 순회 중 컬렉션이 변하므로 보장은 제한적이라고 한다. 전체 순회 동안 계속 있던 원소는 반드시 반환되고 계속 없던 원소는 반환되지 않지만, 원소가 여러 번 반환될 수 있고, 중간에 추가·삭제된 원소는 반환 여부가 정의되지 않는다. 한 호출의 반환 수는 범위 보장이 없고 0개일 수도 있으며, `COUNT` 기본값은 10이다.
(실험 확인) Redis 7.4.11에서 `cchv:scan:` 키 25개를 만든 뒤 `SCAN 0 MATCH cchv:scan:* COUNT 3`을 커서가 0이 될 때까지 반복하자 7번 호출에 키 25개가 모두(중복 없이) 나왔고, `KEYS`와 `redis-cli --scan --pattern`도 25개를 찾았다. 한 번 호출에 몇 개가 오는지는 데이터 상태에 따라 달랐다(같은 `COUNT 10`에서 7개가 온 실행도, 10개가 온 실행도 있었다). 맞는 키가 없는 `SCAN 0 MATCH zzz:* COUNT 10`은 0이 아닌 커서와 빈 목록을 돌려줘, 빈 응답만으로 끝났다고 볼 수 없음을 확인했다. 중복 반환이 실제로 나타나는 상황은 시도했으나 재현하지 못했다.
