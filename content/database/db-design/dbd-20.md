**모범 답변 (30~60초)**
CACHE를 1보다 크게 하면 각 세션이 시퀀스에서 번호를 한 번에 여러 개 미리 받아 메모리에 두고 씁니다. 번호가 서로 겹치지는 않지만, 세션 A가 1~10을 받아 1을 쓴 뒤 세션 B가 11~20을 받아 11을 쓰면 A의 2가 11보다 나중에 나올 수 있어서 시간 순서는 보장되지 않습니다. 또 세션이 끝나면 못 쓴 미리 받은 번호는 버려져 구멍이 생기고, 다른 세션에서 한 setval은 그 세션의 캐시가 소진되기 전에는 보이지 않습니다. 기본값 1에서는 번호가 순차적으로 발급됩니다. 그래도 id 순서를 커밋 순서로 믿으면 안 되니 정렬이 중요하면 별도 시각 컬럼을 둡니다.

```sql
CREATE SEQUENCE c10 CACHE 10;
-- 세션 A: nextval -> 1   세션 B: nextval -> 11, 12   세션 A: nextval -> 2
```

(공식 문서) PostgreSQL 16 sql-createsequence 페이지는 CACHE가 미리 할당해 메모리에 두는 번호 개수이고 기본은 1(캐시 없음)이라고 한다. 캐시가 1보다 크면 여러 세션이 동시에 쓸 때 예상치 못한 결과가 나올 수 있어, 세션이 쓰지 못한 미리 받은 번호는 세션이 끝나면 버려져 구멍이 생기고, 번호는 겹치지 않지만 전체적으로 순서대로 발급된다고 가정하면 안 되며(세션 A가 1을 받고 B가 11을 받은 뒤 A가 2를 받는 예시), 다른 세션의 `setval`은 그쪽 캐시가 소진된 뒤에야 보인다고 한다.
(실험 확인) PostgreSQL 16.15에서 `CACHE 10` 시퀀스를 세션 A가 `nextval` 하면 1, 1초 뒤 세션 B가 부르면 11과 12, 그다음 A가 두 번째로 부르면 2가 나왔다. 발급된 시간 순서는 1, 11, 12, 2였다. 세션 A가 캐시(21~30)를 받은 뒤 다른 세션에서 `setval('c10', 1000)`을 실행해도 A의 다음 `nextval`은 22였다(캐시가 남아 있는 동안 보이지 않음).
(보충) 기본값 CACHE 1에서도 번호를 받은 순서와 트랜잭션이 커밋되는 순서는 다를 수 있다는 점과, 정렬이 중요하면 별도 시각 컬럼을 두라는 조언은 일반적인 동시성 설명이며 문서에 있는 것이 아니고 이번 실험으로 확인하지도 않았다.
