**모범 답변 (30~60초)**
내장 로더는 셋입니다. 부트스트랩 로더는 JVM에 내장되어 있고 ClassLoader API에서는 보통 null로 표현되며 부모가 없습니다. 플랫폼 로더는 플랫폼 클래스를, 시스템 로더(애플리케이션 로더)는 클래스패스와 모듈 경로의 애플리케이션 클래스를 맡고, 플랫폼 로더가 그 부모 또는 조상입니다. 클래스를 요청받은 로더는 기본적으로 이미 로드했는지 확인하고, 부모에게 먼저 위임하고, 그래도 없으면 자기 findClass로 찾습니다. 그래서 커스텀 로더는 loadClass보다 findClass를 오버라이드하라고 권합니다. 같은 이름도 로더가 다르면 다른 클래스입니다.

(공식 문서) ClassLoader API 문서는 부트스트랩 로더를 "보통 null로 표현되고 부모가 없다"고 하고, 플랫폼 로더가 시스템 로더의 부모 또는 조상이라고 한다. 같은 문서가 내장 로더 세 가지와 기본 `loadClass`의 순서(findLoadedClass, 부모의 loadClass, findClass)를 밝히고, 서브클래스는 `loadClass`보다 `findClass`를 오버라이드하라고 권한다. JVM 사양 5.3절은 로딩된 클래스가 이름만이 아니라 (바이너리 이름, 정의 로더) 쌍으로 결정된다고 한다.
(공식 문서) 버전 차이. JEP 261에 따르면 Java 8까지는 확장 클래스 로더(extension class loader)가 확장 메커니즘의 클래스를 읽는 중간 단계였고, 9부터는 이 로더가 플랫폼 클래스 로더로 역할이 바뀌었으며 확장 메커니즘은 제거됐다. 8에서는 시스템 로더가 `URLClassLoader` 인스턴스였지만 9부터는 내부 클래스이다.
(실험 확인) Java 25(Corretto 25.0.3)에서 로더 계층과 위임, 같은 이름의 다른 클래스를 확인했다.

```text
String.class.getClassLoader()            -> null            (부트스트랩)
java.sql.Driver.class.getClassLoader()   -> PlatformClassLoader
system loader "app", parent "platform", grandparent null   (이 환경에서는 플랫폼 로더가 직접 부모)
child.loadClass("java.lang.String") == String.class  -> true
같은 클래스 파일을 로더 두 개로 각각 로딩: c1 == c2 -> false, c2.isInstance(o) -> false, c2.cast(o) -> ClassCastException
```
(실험 확인) 같은 로더 조회 코드를 Corretto 8, 11.0.33, 17.0.21에서 돌렸다. 세 버전 모두 `String.class.getClassLoader()`는 null이었다. Corretto 8에서는 시스템 로더가 `sun.misc.Launcher$AppClassLoader`로 `URLClassLoader`의 인스턴스(true)였고 부모가 `sun.misc.Launcher$ExtClassLoader`(그 부모는 null)였으며, `jre/lib/ext`에 있는 `sun.security.ec.SunEC`는 확장 로더가, `java.sql.Driver`는 부트스트랩(null)이 로드했다. Corretto 11과 17에서는 시스템 로더가 `jdk.internal.loader.ClassLoaders$AppClassLoader`로 `URLClassLoader`가 아니었고(false), 부모가 `PlatformClassLoader`, `java.sql.Driver`와 `sun.security.ec.SunEC`는 플랫폼 로더가 로드했다. Corretto 11에서 `-Djava.ext.dirs=...`를 주면 `-Djava.ext.dirs=/tmp/ext is not supported.  Use -classpath instead.`로 JVM이 뜨지 않았다(확장 메커니즘 제거와 일치).
