**모범 답변 (30~60초)**
setAccessible(true)은 접근 제어 검사를 끄지만 항상 되는 것은 아니고, 호출자와 선언 클래스가 같은 모듈이거나 선언 클래스의 패키지가 호출자 모듈에 opens된 경우 같은 조건이 필요합니다. 내가 만든 클래스패스의 클래스는 이름 없는 모듈에 있어 모든 패키지가 열려 있으니 되지만, java.base 같은 JDK 모듈의 비공개 멤버는 열려 있지 않아서 InaccessibleObjectException이 납니다. JDK 내부 접근은 9~15에서는 JDK 8에 있던 패키지가 클래스패스 코드에 열려 있어(첫 접근에 경고 한 번) 허용이 기본이었고 16에서 기본이 거부로 바뀌었으며, 17부터는 --illegal-access 옵션이 무효가 되어 우회하려면 --add-opens를 써야 합니다.

(공식 문서) AccessibleObject API 문서가 `setAccessible`을 쓸 수 있는 조건을 나열한다. 같은 모듈이거나, public 멤버를 가진 public 클래스의 패키지가 호출자 모듈에 exports된 경우, 선언 클래스의 패키지가 호출자 모듈에 opens된 경우 등이다. 이름 없는 모듈과 open 모듈의 모든 패키지는 모든 모듈에 열려 있어 항상 성공한다. 접근할 수 없으면 `InaccessibleObjectException`이다. 또 static final 필드, 레코드의 필드, 히든 클래스의 final 필드는 `setAccessible`로도 쓰기가 되지 않고 읽기만 된다.
(공식 문서) 버전 차이. JEP 396은 `--illegal-access=permit`이 JDK 8에 있던 패키지를 이름 없는 모듈의 코드에 열어 주고 첫 리플렉션 접근에만 경고를 내는 모드이며 9부터 기본이었다고 한다. JEP 396(Java 16)은 JDK 내부 요소의 강한 캡슐화를 기본으로 하되 사용자가 완화된 모드를 고를 수 있게 했고, JEP 403(Java 17)은 한 옵션으로 완화하는 것을 불가능하게 했다. `java` 도구 문서는 `--illegal-access`가 16에서 deprecated, 17에서 obsolete이고 `--add-opens`가 대체 수단이라고 한다. `sun.misc.Unsafe`처럼 대체재가 아직 없는 핵심 내부 API는 예외로 남긴다(JEP 396, 403).
(공식 문서) JEP 416(Java 18)은 `Method`, `Constructor`, `Field`를 메서드 핸들 위에 다시 구현한 내부 변경이며 `java.lang.reflect` API는 바뀌지 않는다.
(실험 확인) Java 25(Corretto 25.0.3), 클래스패스의 단일 파일 프로그램으로 확인했다.

```text
사용자 클래스의 private 필드 + setAccessible(true)            -> 읽힘
String.class.getDeclaredField("value").setAccessible(true)    -> InaccessibleObjectException (module java.base ... 비공개)
같은 코드 + --add-opens java.base/java.lang=ALL-UNNAMED       -> 접근 가능
record 의 필드에 setAccessible(true) 후 set                    -> IllegalAccessException
java --illegal-access=permit -version                         -> "Ignoring option --illegal-access=permit; support was removed in 17.0" 경고
```
