**모범 답변 (30~60초)**
finalize는 GC가 객체를 회수하기 전에 호출해 주는 메서드인데, 언제 호출될지 보장이 없고 호출 자체도 보장되지 않습니다. 코드가 자유라 this를 저장해 객체를 되살릴 수 있고, 오버라이드하면 모든 인스턴스에 적용되며 실행 스레드와 순서도 통제할 수 없습니다. finalizer 스레드가 못 따라가면 힙이 차서 OutOfMemoryError도 납니다. 그래서 Object.finalize는 9부터 deprecated이고 18에서 제거 예정으로 표시됐습니다. 자원은 try-with-resources로 닫고, 안전망이 필요하면 Cleaner를 씁니다. Cleaner의 정리 동작은 대상 객체를 참조하면 안 됩니다.

(공식 문서) JEP 421(Java 18)이 finalization의 결함을 예측 불가능한 지연, 제약 없는 동작(객체 부활 가능), 항상 켜져 있음, 불특정한 스레드와 순서로 정리하고, 대안으로 try-with-resources와 cleaner를 권한다. 활성 상태는 현재 기본이고 미래 릴리스에서 기본 비활성, 이후 제거 순서로 간다고 한다. JLS 12.6절은 Java SE 25부터 구현이 finalization을 끌 수 있게 허용한다고 하고, `java` 도구 문서는 `--finalization=disabled`가 finalizer 호출을 모두 막으며 기본은 enabled라고 한다. `Cleaner` 문서는 정리 동작이 등록 대상 객체를 참조하면 객체가 팬텀 도달 가능해지지 않아 자동으로 실행되지 않으며, 중첩(inner) 클래스는 바깥 인스턴스를 암묵 참조하므로 static 클래스를 쓰라고 한다.
(실험 확인) `finalize()`를 오버라이드한 객체와 `Cleaner`에 등록한 객체를 버리고 `System.gc()`를 반복 호출했다(HotSpot G1, Corretto 25.0.3).

```text
--finalization=enabled  : finalizer ran=true,  cleaner ran=true
--finalization=disabled : finalizer ran=false, cleaner ran=true
```

(실험 확인) 정리 동작을 비정적 내부 클래스로 만들어 바깥 인스턴스를 쓰게 하자 정리 동작이 실행되지 않았고(`false`), static 중첩 클래스로 만든 정리 동작은 실행됐다(`true`). `Cleaner` 문서의 경고와 같은 결과다(Corretto 25.0.3).
(공식 문서) 문제 해결 가이드는 finalizer를 과하게 쓰는 애플리케이션에서 finalization 큐가 쌓여 `Java heap space` OOM이 날 수 있다고 한다.
(공식 문서) 버전. `Object.finalize`의 API 문서는 `@Deprecated(since="9", forRemoval=true)`를 보여 주고, JEP 421(Java 18)이 제거 예정 표시와 `--finalization` 옵션을 새로 도입했다. 따라서 17 이하에서는 이 옵션이 없고, 25에서도 기본은 enabled이며 `--finalization=disabled`로 끌 수 있다.
(공식 문서) `Object.finalize` 문서는 finalization이 꺼졌거나 제거된 JVM에서는 GC가 finalize를 호출하지 않으며, 켜진 JVM에서도 "무기한 지연 뒤에" 호출할 수 있다고 한다. JEP 421은 GC가 어떤 finalizer든 호출한다는 보장이 없다고 적는다(JLS 12.6은 객체 저장소를 회수하기 전에 호출한다고 적으나 25부터 구현이 끌 수 있게 허용한다).
