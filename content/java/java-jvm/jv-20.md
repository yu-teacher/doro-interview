**모범 답변 (30~60초)**
System.gc()는 JVM에 가비지 컬렉션을 해 달라고 제안하는 것이고, 문서는 최선의 노력을 한다고만 하며 어떤 양의 공간을 회수하거나 정해진 시간 안에 끝난다는 것을 보장하지 않습니다. 참조 객체가 지워지고 큐에 들어간다는 보장도 없습니다. HotSpot에서는 기본적으로 이 호출이 처리되어 G1에서 로그에 Pause Full (System.gc())로 나타나는 전체 수거가 일어납니다. -XX:+DisableExplicitGC를 켜면 호출이 무시되고, G1에서는 -XX:+ExplicitGCInvokesConcurrent로 동시 GC로 처리하게 할 수도 있습니다. 필요할 때 JVM이 알아서 GC하므로 일반 코드에서는 호출하지 않는 게 좋습니다.

(공식 문서) System API 문서는 `gc()`가 JVM이 재활용에 노력을 쏟도록 제안하는 것이고, 반환 시점에 최선의 노력을 했을 뿐 회수량이나 완료 시점, Reference 객체 정리를 보장하지 않는다고 한다. `java` 도구 문서는 `-XX:+DisableExplicitGC`가 `System.gc()` 호출 처리를 끄는 옵션이며 기본은 꺼져 있고 호출이 처리되고, 끄더라도 필요하면 JVM이 GC를 수행한다고 한다. 같은 문서가 `-XX:+ExplicitGCInvokesConcurrent`는 `System.gc()` 요청에 동시 GC를 쓰게 하며 기본은 꺼져 있고 `-XX:+UseG1GC`와 함께일 때만 켤 수 있다고 한다. GC 튜닝 가이드의 로그 예시에도 `Pause Full (System.gc())`가 나온다.
(실험 확인) `System.gc()` 한 번만 호출하는 프로그램을 `-Xlog:gc`로 실행했다(HotSpot G1, Corretto 25.0.3).

```text
(기본)                       : GC(0) Pause Full (System.gc()) 24M->2M(96M) 2.552ms
-XX:+DisableExplicitGC       : Pause Full 로그 없이 종료(Using G1 줄만 출력)
-XX:+ExplicitGCInvokesConcurrent : GC(0) Pause Young (Concurrent Start) (System.gc()) 24M->3M(388M), 이어서 GC(1) Concurrent Mark Cycle
-XX:+UseParallelGC (+ExplicitGCInvokesConcurrent 를 더해도) : Pause Full (System.gc()) (옵션 오류 없음)
-XX:+UseZGC                  : GC(0) Major Collection (System.gc())
```

(보충) 일반 코드에서 호출하지 말라는 권고는 호출이 전체 수거를 유발해 정지 시간을 키울 수 있다는 일반적인 설명이고, 위 문서가 금지하는 것은 아니다.
