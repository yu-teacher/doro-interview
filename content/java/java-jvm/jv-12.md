**모범 답변 (30~60초)**
자바에서는 직접 해제하지 않아도 되지만, 더는 쓰지 않는 객체를 애플리케이션이 의도치 않게 계속 참조하면 GC가 회수하지 못하고 이것이 자바식 메모리 누수입니다. 대표 유형은 계속 쌓이기만 하는 static 컬렉션이나 캐시, 해제하지 않은 리스너와 콜백 등록, 스레드 풀처럼 스레드가 오래 사는 환경에서 remove하지 않은 ThreadLocal 값, 클래스 로더를 붙잡아 클래스까지 못 내리는 경우입니다. 안정된 부하에서도 풀 GC 뒤 사용량인 라이브 셋이 계속 늘면 누수를 의심하고, 힙 덤프로 누가 붙잡고 있는지 참조 경로를 봅니다.

(공식 문서) 문제 해결 가이드의 메모리 누수 장에 근거한다. 누수를 애플리케이션이 Java 객체나 클래스를 의도치 않게 참조해 GC를 막는 것으로 정의하고, 라이브 셋(풀 GC 뒤 힙이나 Metaspace 사용량)이 안정 상태에서 계속 늘면 누수의 강한 신호라고 한다. 탐지 방법으로 JConsole, JDK Mission Control, GC 로그, 힙 덤프(`jcmd`, `jmap`, `-XX:+HeapDumpOnOutOfMemoryError`)를 든다. 호출하는 API가 의도치 않게 객체 참조를 쥐는 경우도 있다고 한다.
(공식 문서) ThreadLocal 문서는 스레드가 살아 있고 ThreadLocal 인스턴스에 접근할 수 있는 동안 스레드가 값 복사본을 암묵적으로 참조한다고 한다.
(실험 확인) 스레드 1개짜리 풀에서 작업이 `ThreadLocal`에 1MB 배열을 넣고 끝난 뒤 `System.gc()`를 호출해 WeakReference로 값의 생존을 봤다(HotSpot).

```text
remove() 호출 없이 작업 종료 -> 값 여전히 도달 가능: true
작업 안에서 remove() 호출     -> 값 여전히 도달 가능: false
```

(보충) static 컬렉션, 리스너 미해제, 클래스 로더 누수는 위 문서가 유형으로 나열한 것이 아니라 일반적으로 알려진 사례를 설명한 것이다. 클래스 로더 누수는 로더가 붙들리면 그 로더가 로딩한 클래스와 메타데이터가 해제되지 않아 Metaspace가 커진다는 형태로 나타난다.
