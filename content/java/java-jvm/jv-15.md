**모범 답변 (30~60초)**
Java 9에 들어온 모듈 시스템은 module-info.java의 module 선언으로 이 모듈이 무엇에 의존하고 무엇을 공개하는지 선언하게 합니다. requires는 다른 모듈에 대한 의존입니다. exports로 지정한 패키지의 public과 protected 타입만 다른 모듈이 컴파일과 런타임에 쓸 수 있고, 나머지 패키지는 막히는데 이것이 강한 캡슐화입니다. opens는 런타임 리플렉션으로 그 패키지의 비공개 멤버까지 접근하는 것을 허용합니다. open module은 모든 패키지를 런타임에 열어 둡니다. 모듈 선언이 없는 클래스패스의 클래스는 이름 없는 모듈에 속하고 이 모듈의 패키지는 모두 열려 있습니다.

(공식 문서) JLS 7.7절은 일반 모듈은 명시적으로 exports한 패키지의 public·protected 타입과 그 멤버만 컴파일·런타임에 접근을 허용하고, 리플렉션은 exports나 opens한 패키지에 허용하며 opens한 패키지는 모든 타입과 멤버에 접근할 수 있다고 한다. `open` 모듈은 모든 패키지를 opens한 것처럼 취급한다. Module API 문서는 클래스 로더마다 이름 없는 모듈이 있고 이름 있는 모듈에 속하지 않은 타입은 정의 로더의 이름 없는 모듈에 속한다고 한다.
(실험 확인) 모듈 `lib`가 `lib.api`만 exports하고 모듈 `app`이 `requires lib`인 구성으로 확인했다(Corretto 25.0.3).

```text
javac: error: package lib.impl is not visible  (lib 모듈이 lib.impl 을 export 하지 않음)
실행: Api.hello()를 통한 간접 호출은 성공("impl")
      Class.forName("lib.impl.Impl") 성공, 그 클래스의 public 메서드를 reflection 으로 호출 -> IllegalAccessException
```

(실험 확인) 같은 구성에서 `lib`의 module-info에 `opens lib.impl;`을 더하자, 이전에는 막히던 `Class.forName`으로 얻은 `lib.impl.Impl`의 private 필드를 `setAccessible(true)`로 읽을 수 있었다(값 "s").
(공식 문서) 버전 차이. 모듈 시스템은 Java 9(JEP 261)에서 도입됐고, JDK 내부 요소를 강하게 캡슐화하는 것이 기본이 된 것은 16(JEP 396)이며 17(JEP 403)부터 명령행 한 옵션으로 완화할 수 없다. 8에는 모듈이 없고 9~15에서는 완화된 캡슐화가 기본이었다. 자세한 접근 규칙은 jv-18을 본다.
