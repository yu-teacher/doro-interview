**모범 답변 (30~60초)**
G1은 힙을 같은 크기의 리전으로 나누고, 각 리전을 eden이나 survivor(young), 또는 old에 배정합니다. 리전 크기의 절반 이상인 큰 객체는 humongous 객체로 연속된 리전 하나 이상(둘 이상일 수도 있습니다)을 차지하며 old 쪽에 바로 할당됩니다. 수거는 주로 evacuation, 곧 선택한 리전의 살아 있는 객체를 새 리전으로 복사하면서 압축하는 방식입니다. 과거 정지 시간으로 비용 모델을 만들어 정지 시간 목표에 맞게 한 번에 처리할 양을 정하고, 쓰레기가 많은 리전부터 거둬서 Garbage-First라 부릅니다. young만 거두는 단계와 old 공간도 점차 회수하는 단계를 번갈아 하며, 전체 마킹 같은 작업은 애플리케이션과 동시에 합니다.

(공식 문서) 튜닝 가이드 7장(G1)에 근거한다. 가이드는 G1이 generational, incremental, parallel, mostly concurrent, stop-the-world, evacuating 컬렉터라고 소개하고, 실시간 컬렉터가 아니어서 정지 시간 목표를 높은 확률로 맞추려 할 뿐 매번 보장하지는 않는다고 밝힌다. 수거 사이클은 Young-Only 단계와 Space-Reclamation 단계가 반복되고, old 점유율이 임계값(Initiating Heap Occupancy)에 이르면 Concurrent Start 수거로 마킹을 시작한다. 가이드는 처리량 컬렉터에 비해 G1이 정지는 짧지만 동시 작업 때문에 처리량은 약간 낮은 경향이 있다고 한다.
(공식 문서) 가이드는 humongous 객체를 리전 크기의 절반 이상인 객체로 정의하고, 연속된 리전 열로 old 세대에 할당되며 마지막 리전의 남는 공간은 객체가 회수될 때까지 쓸 수 없다고 한다.
(실험 확인) 8,000,000바이트 배열을 5번 할당하고 `System.gc()`를 호출해 `-Xmx256m -Xlog:gc*`로 봤더니 리전 크기가 1M였고 `Humongous regions: 40->8`로 나왔다. 8,000,000바이트 배열이 리전 8개를 차지하는 humongous 객체로 다뤄졌다(HotSpot G1, 한 번 실행한 결과). 경계를 보려고 같은 방식으로 5개를 잡아 크기만 바꾸자(`-Xmx256m`, 리전 1M) 400,000바이트에서는 `Humongous regions: 0->0`, 600,000바이트에서는 `5->5`였다.
(공식 문서) 버전. JEP 248에 따라 G1은 Java 9부터 서버 구성의 기본이다. 이 질문의 세부 동작은 25 가이드 기준이고, 리전 크기·임계값 같은 수치는 환경과 힙 크기에 따라 달라진다.
