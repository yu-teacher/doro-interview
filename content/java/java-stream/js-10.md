**모범 답변 (30~60초)**
reduce는 원소들을 하나의 값으로 접는 연산으로, 초기값과 두 값을 합치는 함수를 받습니다. 병렬에서 안전하려면 identity가 결합 함수에 대한 항등원이어야 하고, 결합 함수는 결합 법칙이 성립하며 상태가 없어야 합니다. 병렬 실행은 데이터를 쪼개 부분 결과를 만든 뒤 combiner로 합치기 때문에, 예를 들어 identity로 10을 주면 쪼개진 조각마다 10이 더해져 순차와 결과가 달라집니다. 뺄셈도 결합 법칙이 없어 같은 문제가 생깁니다. identity가 없는 형태는 빈 스트림일 때를 위해 Optional을 돌려줍니다.

```java
Stream.of(1,2,3,4).reduce(10, Integer::sum);             // 순차 20
Stream.of(1,2,3,4).parallel().reduce(10, Integer::sum);  // 이 PC에서 50
IntStream.rangeClosed(1,8).boxed().reduce(0, (x, y) -> x - y);            // 순차 -36
IntStream.rangeClosed(1,8).boxed().parallel().reduce(0, (x, y) -> x - y); // 이 PC에서 0
Stream.<Integer>empty().reduce(Integer::sum);            // Optional.empty
```

(공식 문서) Stream.reduce(identity, accumulator) 문서는 identity가 accumulator에 대한 항등이어야 하고(모든 t에 대해 accumulator.apply(identity, t)가 t와 같다), accumulator가 associative이며 non-interfering·stateless여야 한다고 한다. 패키지 문서의 "Reduction operations"는 병렬 reduction이 입력을 분할해 부분 결과를 만든 뒤 combiner로 합치며, 세 인자 reduce에서 identity는 combiner에 대한 항등이고 combiner는 associative여야 하며 accumulator와 호환되어야 한다고 설명한다. identity 없는 reduce(BinaryOperator)는 결과가 없을 수 있어 Optional을 돌려준다(Stream 메서드 요약).
(실험 확인) 위 코드를 다시 실행한 결과 순차 20/병렬 50, 순차 -36/병렬 0이었다(15코어 PC). 병렬 결과는 분할 방식에 의존하므로 코어 수가 다른 환경에서는 다른 값이 나올 수 있다. 반례로 올바른 조건인 `reduce(0, Integer::sum)`은 1~1000 병렬에서 500500, 결합 법칙은 있으나 교환 법칙이 없는 문자열 concat도 병렬에서 `abcdefgh` 순서를 유지했다.
(보충) 뺄셈이 결합 법칙을 만족하지 않는다는 것은 산술 일반론이며, 문서의 결합 법칙 요구와 위 실험 결과를 합친 설명이다.
