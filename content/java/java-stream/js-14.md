**모범 답변 (30~60초)**
스트림은 요청하지 않으면 순차로 실행되고, parallelStream()이나 parallel()을 호출했을 때만 병렬로 실행됩니다. 문서가 정한 전제는 동작 매개변수가 상태가 없고 원본을 건드리지 않아야 하며, 실행 방식이 결과를 바꾸면 안 된다는 것입니다. limit처럼 순서에 묶인 연산은 버퍼링으로 이득을 깎고, sorted나 distinct 같은 상태 있는 연산은 여러 번 훑거나 많이 버퍼링할 수 있으며, forEach는 순서를 보장하지 않습니다. 순서가 필요하면 forEachOrdered나 collect를 씁니다. HotSpot에서는 공통 ForkJoinPool 스레드가 일을 나눠 맡습니다. 병렬이 항상 빠른 것은 아니니 측정해서 판단해야 합니다.

```java
IntStream.range(0, 10).parallel().forEach(i -> sb.append(i));        // 예: 6589721034 (순서 비결정)
IntStream.range(0, 10).parallel().forEachOrdered(i -> sb2.append(i)); // 0123456789
IntStream.range(0, 10).parallel().boxed().toList();                  // [0..9] 순서 유지
```

(공식 문서) 패키지 문서의 Parallelism, Non-interference, Stateless behaviors, Ordering 절에 근거한다. JDK 스트림은 병렬을 명시적으로 요청하지 않으면 순차이고, 실행 방식(순차/병렬)이 결과를 바꾸면 안 되며(findAny 같은 명시적 비결정 연산 제외), 동작 매개변수는 non-interfering이고 대부분 stateless여야 한다. forEach는 병렬에서 encounter order를 보장하지 않으며(Stream 문서), limit처럼 encounter order에 묶인 연산은 버퍼링이 필요해 병렬 이득을 해칠 수 있고, 상태 있는 연산은 여러 번의 순회나 많은 버퍼링이 필요할 수 있다고 한다. 패키지 문서는 groupingBy 같은 맵 병합 reduction이 병렬에서 오히려 역효과일 수 있다고도 한다. ForkJoinPool 문서는 특정 풀에 명시적으로 제출하지 않은 ForkJoinTask가 공통 풀을 쓰며, 블로킹 I/O 같은 비관리 동기화에서는 스레드 수 조정이 보장되지 않는다고 한다. 병렬 스트림이 공통 풀을 쓴다는 문장은 읽은 Java 25 문서에 직접 나오지 않는다.
(실험 확인) HotSpot(Corretto 25)에서 병렬 스트림 작업은 `ForkJoinPool.commonPool-worker` 스레드와 main에서 실행됐고(15코어 PC에서 공통 풀 병렬도 14), forEach는 순서가 뒤섞이고 forEachOrdered와 toList는 순서를 지켰다. 사용자 지정 ForkJoinPool 안에서 parallel 파이프라인을 실행하면 그 풀의 스레드(`ForkJoinPool-1-worker`)가 쓰였으나 이 방법은 문서에 보장되어 있지 않다. 공통 풀 스레드 전부를 병렬 스트림의 `Thread.sleep` 작업으로 막아 두자, 같은 시점에 `CompletableFuture.supplyAsync`(문서상 기본 실행기는 공통 풀)가 끝나기까지 1.7초가 걸렸고 풀이 한가할 때는 0ms였다.
(보충) 병렬 스트림이 순차보다 빠르다는 보장이 없어 측정해서 판단해야 한다는 조언, 그리고 블로킹 작업을 공통 풀에서 돌리면 다른 병렬 작업이 지연된다는 일반적 주의는 위 실험과 일반론이며 Stream·패키지 문서의 명시 문장은 아니다.
