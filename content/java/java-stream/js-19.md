**모범 답변 (30~60초)**
원본 수정은 두 경우로 나뉩니다. 스트림을 만든 뒤라도 종결 연산이 시작되기 전에 수정하면, 잘 만들어진 소스인 JDK 컬렉션에서는 그 변경이 결과에 반영됩니다. 반면 종결 연산이 실행되는 동안 동작 매개변수가 소스를 수정하면 문서가 말하는 간섭이라 예외나 잘못된 결과가 나올 수 있고, ArrayList에서는 ConcurrentModificationException으로 나타나는 경우가 많지만 예외 종류도 보장되지 않습니다. 이 규칙은 병렬뿐 아니라 모든 파이프라인에 적용됩니다. 동시성 컬렉션처럼 수정을 견디도록 설계된 소스만 예외입니다. 변경이 필요하면 새 컬렉션으로 수집한 뒤 반영합니다.

```java
var al = new ArrayList<>(List.of(1, 2, 3));
Stream<Integer> s = al.stream();
al.add(4);
s.toList();                                         // [1, 2, 3, 4]  (종결 연산 전 수정은 반영)
al.stream().forEach(x -> { if (x == 2) al.add(99); }); // ConcurrentModificationException
```

(공식 문서) 패키지 문서의 "Non-interference"에 근거한다. 대부분의 소스에서는 파이프라인 실행 중 소스를 전혀 수정하지 않아야 하며, 비동시성 소스를 수정하면 예외, 잘못된 결과, 비표준 동작이 생길 수 있고, 이 요구는 병렬뿐 아니라 모든 파이프라인에 적용된다. 잘 만든 소스는 종결 연산 전 수정이 반영되며(문서의 "one two three" 예, JDK 컬렉션 대부분이 해당), 동시성 컬렉션(spliterator가 CONCURRENT 특성을 보고)은 예외다. Stream 문서도 동시 수정을 위해 설계된 소스가 아니면 예측 불가하거나 오류인 동작이 생길 수 있다고 한다.
(실험 확인) Java 25의 ArrayList에서 위 예의 결과를 확인했고, forEach·map 안에서 같은 리스트에 add하면 ConcurrentModificationException이 났다. 같은 forEach에서 `remove(0)`을 하면 이 JDK에서는 CME가 아니라 NullPointerException이 났고, CopyOnWriteArrayList에서는 예외 없이 끝났다(HashMap의 keySet 스트림에서 put하면 CME). 예외 발생과 종류는 문서가 보장하는 것이 아니라 각 컬렉션 구현의 동작이다.
