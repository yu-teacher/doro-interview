**모범 답변 (30~60초)**
중간 연산(filter, map 등)은 새 스트림을 돌려줄 뿐 아무것도 실행하지 않고, 종결 연산(forEach, collect, count 등)이 호출될 때 비로소 소스를 순회하며 파이프라인이 실행됩니다. 이것이 지연 평가입니다. filter나 map처럼 상태 없는 연산만 이어진 파이프라인은 단계마다 전체를 훑지 않고 원소 하나가 파이프라인을 통과하는 식으로 한 번에 처리되고, findFirst 같은 short-circuit 종결 연산이 있으면 필요한 만큼만 소스를 읽고 멈춥니다. sorted처럼 전체 입력이 필요한 상태 있는 연산은 이 흐름을 끊습니다.

```java
Stream.of("a","bb","ccc")
      .filter(x -> { System.out.println("f " + x); return x.length() > 1; })
      .map(x -> { System.out.println("m " + x); return x; })
      .findFirst();
// f a / f bb / m bb   (ccc는 아예 검사하지 않음)
```

(공식 문서) java.util.stream 패키지 문서의 "Stream operations and pipelines"에 근거한다. 중간 연산은 항상 lazy이고 소스 순회는 종결 연산이 실행될 때 시작되며, 종결 연산이 끝나면 파이프라인은 소비된 것으로 본다. 상태 없는 연산(filter, map)만 있는 파이프라인은 한 번의 순회로 융합될 수 있고, 상태 있는 연산(distinct, sorted)은 전체 입력을 처리해야 결과를 낼 수 있다고 한다. short-circuit 연산이 있다고 해서 무한 스트림이 반드시 끝나는 것은 아니라는 설명도 같은 절에 있다. Stream 문서는 소스 원소가 필요한 만큼만 소비된다고 한다.
(실험 확인) 종결 연산 없이 `filter`와 `map`만 붙인 스트림은 람다가 한 번도 호출되지 않았다. 위 코드는 주석처럼 원소 단위로 번갈아 실행되며 `ccc`는 처리되지 않았다. 사이에 `sorted()`를 넣으면 앞쪽 peek가 모든 원소(c, a, b)에 먼저 실행된 뒤 뒤쪽 peek가 정렬된 순서(a, b, c)로 실행됐다.
