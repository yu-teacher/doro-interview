**모범 답변 (30~60초)**
정답이 정해져 있지는 않고 용도에 따라 고릅니다. 필터링, 변환, 집계처럼 입력에서 결과를 계산하는 흐름은 스트림이 선언적이고 부작용이 없어 읽기 쉽고, 문서도 가변 누적보다 reduction을 권합니다. 반대로 람다 안에서는 함수형 인터페이스가 허용하지 않는 체크 예외를 던질 수 없고, 바깥 지역 변수를 바꿀 수 없으며, break나 continue를 쓸 수 없고 return은 람다만 빠져나오기 때문에 이런 제어가 많은 로직은 for 루프가 자연스럽습니다. 디버깅할 때 스택이 깊어지는 것도 감안합니다. 성능은 일률적으로 말할 수 없어 측정이 필요합니다.

```java
// 체크 예외: 컴파일 오류 (unreported exception IOException; must be caught or declared to be thrown)
List.of("a").stream().map(s -> readFile(s)).toList();   // readFile이 IOException을 던지는 경우
// 조기 종료는 short-circuit 연산으로 표현
l.stream().filter(x -> x == 3).findFirst();   // Optional[3]
```

(공식 문서) 패키지 문서가 스트림의 특성(저장 없음, 함수형, 지연, 무한 가능)과 가변 누적 대신 reduction을 선호할 이유(병렬화 용이, 동기화 불필요)를 설명한다. JLS 11.2.3은 람다 본문이 던질 수 있는 체크 예외가 대상 함수형 인터페이스의 throws 절에 없으면 컴파일 오류라고 하고(JLS 15.27.3도 이를 가리킨다), 람다의 지역 변수 제약은 JLS 15.27.2다. Java 24부터 Gatherer로 사용자 정의 중간 연산을 만들 수 있다(Gatherer 문서 Since 24, JEP 485가 24에서 최종 도입, 22와 23에서는 프리뷰). Java 21 이하에는 Gatherer가 없다.
(실험 확인) 람다 안에서 IOException을 던지는 메서드를 호출하면 javac가 `unreported exception IOException`으로 거부했고, 람다 안의 `break`는 `break outside switch or loop` 오류였다. 람다 안의 `return`은 해당 람다만 끝내 `continue`처럼 동작했다. 같은 예외를 던질 때 스택 프레임 수는 for 루프 7개, 스트림 16개였다(HotSpot Corretto 25, 소스 파일 런처로 실행한 이 간단한 예 기준이며 구현 의존).
(보충) 성능 우열과 가독성 판단은 상황에 따른 일반론이며 이번에 벤치마크하지 않았다.
