**모범 답변 (30~60초)**
람다 본문에서 바깥 지역 변수, 매개변수, 예외 매개변수를 쓰려면 final이거나 effectively final이어야 합니다. final을 안 붙였어도 값이 정해진 뒤 다시 대입되거나 증감되지 않으면 effectively final입니다. 명세는 이유를 동적으로 바뀌는 지역 변수를 캡처하면 동시성 문제가 생기기 쉽기 때문이라고 설명합니다. 람다는 다른 스레드에서 나중에 실행될 수 있으니 지역 변수는 값이 복사되어 넘어간다고 이해하면 쉽습니다. 이 제한은 지역 변수에만 해당하고 인스턴스 필드와 static 필드는 읽고 쓸 수 있습니다. 전통적인 for 루프 변수는 안 되지만 향상된 for 변수는 반복마다 별개라 캡처할 수 있습니다.

```java
int n = 0;
Runnable r = () -> System.out.println(n);
n++;   // 컴파일 오류: local variables referenced from a lambda expression must be final or effectively final

for (String s : List.of("x", "y")) tasks.add(() -> System.out.print(s)); // 허용
```

(공식 문서) JLS 15.27.2가 람다 본문이 쓰는, 본문 밖에서 선언된 지역 변수·매개변수·예외 매개변수는 final이거나 effectively final이어야 한다고 하고, 이유로 effectively final 제한이 동적으로 바뀌는 지역 변수의 접근을 막아 동시성 문제를 피한다고 설명한다. 전통적 for 루프 변수는 이 제한에 걸리고 향상된 for 변수는 반복마다 별개 변수로 취급되어 제외된다는 것, 같은 취지의 규칙이 내부 클래스(8.1.3)에도 있다는 것도 같은 절이다. effectively final의 정의는 JLS 4.12.4이며, 초기화자가 있으면 다시 대입·증감되지 않을 때, 초기화자가 없으면 대입이 definitely unassigned 상태에서만 일어나고 증감되지 않을 때 해당한다.
(실험 확인) Java 25 javac가 위 첫 예시에서 메시지의 컴파일 오류를 냈고, 전통적 for 루프 변수 `i`를 캡처한 람다와 이후 값을 바꾼 지역 변수를 캡처한 익명 클래스도 `must be final or effectively final` 오류였다(익명 클래스는 `from an inner class`). 향상된 for 변수를 캡처한 람다는 `xy`를 출력했고, 람다 안에서 인스턴스 필드와 static 필드를 증가시키는 코드는 컴파일되어 둘 다 2가 됐다.
(보충) 지역 변수가 값으로 복사되어 넘어간다는 모델은 JLS의 이유 설명을 풀어 쓴 일반론이며 JLS 15.27.2가 복사를 명시하지는 않는다. 배열 한 칸이나 AtomicInteger로 우회할 수 있다는 점도 일반 설명이며(배열 우회는 실행해 `box=2` 확인), 스트림 안에서는 부작용이 되어 권장되지 않는다.
