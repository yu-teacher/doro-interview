**모범 답변 (30~60초)**
count()는 구현이 소스에서 크기를 바로 알 수 있으면 파이프라인을 아예 실행하지 않아도 된다고 문서에 적혀 있기 때문입니다. 리스트에서 만든 스트림에 peek만 붙여 count하면 원소를 순회하지 않고 크기를 돌려주므로 peek 안의 출력이 실행되지 않습니다. 반대로 filter가 끼어 크기가 정해지지 않으면 파이프라인이 실제로 돌아 peek가 출력됩니다. 문서는 부작용이 있는 동작 매개변수가 이런 최적화의 영향을 받을 수 있다고 하므로, peek는 디버깅용으로만 쓰고 필요한 동작을 거기에 넣으면 안 됩니다. 이 설명은 Java 9 문서부터 있습니다.

```java
var l = Arrays.asList("A", "B", "C", "D");
l.stream().peek(System.out::println).count();                           // 4 (출력 없음)
l.stream().filter(x -> true).peek(System.out::println).count();         // A B C D 출력 후 4
l.stream().map(x -> { System.out.println("map " + x); return x; }).count(); // 4 (map도 실행 안 됨)
```

(공식 문서) Stream.count의 API Note가 구현이 소스에서 개수를 직접 계산할 수 있으면 파이프라인을 실행하지 않을 수 있고 이때 소스 원소를 순회하지 않으며 중간 연산이 평가되지 않고, 부작용 있는 동작 매개변수가 영향받을 수 있다고 하며, 정확히 이 peek 예시를 든다(peek가 원소를 주입하거나 제거하지 않아 크기가 소스와 같다는 설명도 있다. flatMap이나 filter는 그럴 수 있다). peek 문서는 디버깅용이고 short-circuit 등으로 원소 생산이 최적화되면 action이 호출되지 않는다고 한다. 패키지 문서의 Side-effects 절도 같은 취지다. 버전: Java 8 API 문서의 count()에는 이 API Note가 없고 Java 9 API 문서에 있다(두 페이지를 읽어 확인한 것이며, Java 8 동작은 직접 실행하지 못했다).
(실험 확인) Java 25(Corretto)에서 위 세 호출의 결과가 주석과 같았다(`Stream.of("A","B").peek(...).count()`도 출력 없음). `flatMap`, `distinct`, 크기를 모르는 `iterate(...).limit(3)`이 앞에 있으면 peek가 실행됐고, `sorted`, `limit`, `skip`을 리스트 소스 뒤에 붙인 경우는 이 JDK에서 출력 없이 크기를 돌려줬다. 이 동작은 JDK 구현과 버전에 의존한다. `findFirst()` 앞의 peek는 첫 원소(A)에만 실행됐다.
