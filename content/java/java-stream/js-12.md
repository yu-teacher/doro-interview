**모범 답변 (30~60초)**
groupingBy는 분류 함수가 돌려준 키로 원소를 묶어 Map을 만들고, 값은 기본적으로 그 키에 속한 원소의 List입니다. 두 번째 인자로 다운스트림 컬렉터를 주면 그룹별로 counting, summingInt, mapping, joining 같은 리듀스를 적용할 수 있고, 세 번째 형태로 mapFactory를 주면 TreeMap처럼 원하는 맵 구현으로 받을 수 있습니다. 기본 형태는 맵과 리스트의 타입·가변성·스레드 안전성을 보장하지 않습니다. 분류 함수가 null 키를 만들면 이 JDK에서는 NullPointerException이 나지만 문서에는 규정이 없고, 참/거짓 두 그룹만 필요하면 partitioningBy가 맞습니다.

```java
Map<String,List<P>> g = ps.stream().collect(Collectors.groupingBy(P::dept));
TreeMap<String,Integer> tm = ps.stream()
    .collect(Collectors.groupingBy(P::dept, TreeMap::new, Collectors.summingInt(P::sal)));  // {dev=30, ops=5}
ps.stream().collect(Collectors.groupingBy(P::dept, Collectors.mapping(P::name, Collectors.joining("/"))));
ps.stream().collect(Collectors.partitioningBy(p -> p.sal() > 8, Collectors.counting())); // {false=1, true=2}
```

(공식 문서) Collectors.groupingBy 문서가 분류 함수가 원소를 키로 매핑하고 기본 형태는 Map<K, List<T>>를 만들며 groupingBy(classifier, toList())와 비슷한 결과이고, 맵·리스트의 타입·가변성·직렬화 가능 여부·스레드 안전성에 보장이 없다고 한다. 다운스트림 컬렉터를 받는 오버로드와 mapFactory로 맵을 만드는 오버로드(TreeMap 예시 포함)가 있고, 반환 컬렉터는 concurrent가 아니라 병렬에서 맵 병합 비용이 클 수 있어 groupingByConcurrent가 나을 수 있다고 한다. partitioningBy는 Map<Boolean, ...>를 만들고 결과 맵이 항상 false와 true 키를 모두 가진다고 한다. Collectors.filtering·flatMapping은 Since 9, teeing은 Since 12다.
(실험 확인) 위 호출 결과가 주석대로였다(`{dev=30, ops=5}`, `{false=1, true=2}`). 분류 함수가 null을 돌려주면 `NullPointerException: element cannot be mapped to a null key`가 발생했는데 Collectors 문서에는 null 키 규정이 없다(이 JDK에서의 관찰). 기본 형태의 맵 구현은 이 JDK에서 HashMap, 그룹 리스트는 ArrayList였으나 보장은 아니다. 조건이 모두 거짓이어도 partitioningBy는 `true=[]`를 포함했다.
