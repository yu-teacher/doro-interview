**모범 답변 (30~60초)**
sealed는 클래스나 인터페이스를 직접 상속하거나 구현할 수 있는 하위 타입을 permits 절로 명시해 제한하는 기능이고, Java 17에서 정식이 됐습니다. 직접 하위 타입은 final, sealed, non-sealed 중 하나를 반드시 명시해야 해서, 계층을 더 열어 둘지를 작성자가 의식적으로 정하게 됩니다. permits를 생략하면 같은 컴파일 단위에서 직접 상속하는 클래스가 허용 대상이 되고, 명시하면 이름 있는 모듈에서는 같은 모듈, 이름 없는 모듈에서는 같은 패키지에 있어야 합니다. 가장 큰 쓸모는 도메인의 종류를 닫힌 집합으로 모델링하는 것이고, 그 덕분에 패턴 switch에서 모든 하위 타입을 다루면 default 없이도 완전하다고 컴파일러가 판단합니다. record와 enum은 암묵적으로 final이거나 sealed라 sealed 인터페이스를 구현할 수 있습니다.

(공식 문서) JLS 8.1.1.2는 sealed 클래스의 하위 클래스가 final, sealed, non-sealed 중 하나여야 하고 record·enum도 sealed 인터페이스를 구현할 수 있다고 하며, 8.1.6은 permits 절의 대상과 생략 시 추론 규칙, 모듈·패키지 제약을 밝힌다. JEP 409는 sealed가 Java 15, 16의 프리뷰를 거쳐 17에서 정식이 됐고 패턴의 완전성 분석을 위한 기반을 마련하는 것도 목표라고 하며, JEP 441은 sealed 계층이면 permits 절을 고려해 switch의 완전성을 판단한다고 설명한다.
(실험 확인) `sealed interface Shape permits Circle, Square, Rect`에 대해 `isSealed()`가 `true`, `getPermittedSubclasses()`가 세 타입을 돌려줬다. `permits` 없이 선언한 sealed 추상 클래스는 같은 파일의 하위 클래스 둘이 허용 목록이 됐다. permits에 없는 클래스가 구현하면 `class is not allowed to extend sealed class: S (as it is not listed in its 'permits' clause)`, 하위 클래스에 final·sealed·non-sealed가 없으면 `sealed, non-sealed or final modifiers expected`, switch가 하위 타입 하나를 빼먹으면 `the switch expression does not cover all possible input values`로 컴파일되지 않았다. `non-sealed` 하위 클래스는 자유롭게 상속할 수 있었다. 다른 패키지의 클래스를 permits에 적으면 이름 없는 모듈에서 `class S in unnamed module cannot extend a sealed class in a different package`로, sealed 상위 타입이 없는 클래스에 `non-sealed`를 쓰면 `non-sealed modifier not allowed here`로 컴파일되지 않았다.
(실험 확인) `sealed interface S permits A, B {}`와 두 record 구현은 Corretto 11.0.33에서 `<identifier> expected` 등으로 컴파일되지 않았고, Corretto 17.0.21에서는 컴파일·실행됐다(`A[]`). Corretto 17의 `javac --release 16`은 `sealed classes are not supported in -source 16`이었다(17에서 정식이라는 설명과 일치).
