**모범 답변 (30~60초)**
컴파일러는 이름이 같은 후보 중 호출에 적용 가능한 것을 세 단계로 찾습니다. 1단계는 박싱·언박싱과 가변 인자 없이, 2단계는 박싱·언박싱을 허용하되 가변 인자는 빼고, 3단계에서 가변 인자까지 허용하며, 앞 단계에서 하나라도 찾으면 거기서 멈추고 그 안에서 가장 구체적인 메서드를 고릅니다. 그래서 b(long)과 b(Integer)가 있을 때 b(5)는 박싱 없이 확대 변환만 쓰는 b(long)이 선택됩니다. 인자가 null이면 String과 Object 후보 중에서는 더 구체적인 String이 고르고, String과 StringBuilder처럼 서로 하위 관계가 없으면 모호하다는 컴파일 오류가 납니다. m(Object)와 m(Object...)가 함께 있으면 m(null)은 Object 배열을 받는 가변 인자 쪽이 선택되는 점도 알아 둘 만합니다.

```java
static void b(long x)    { /* b(long) */ }
static void b(Integer x) { /* b(Integer) */ }
static void b(int... x)  { /* b(int...) */ }
static void c(Integer x) {}  static void c(Object x) {}  static void c(int... x) {}
static void d(Object o)  {}  static void d(Object... o) {}
b(5);     // b(long)      1단계: 박싱 없이 int -> long 확대
c(5);     // c(Integer)   2단계: 박싱 후 Integer 가 Object 보다 구체적
d(null);  // d(Object...) 1단계에서 둘 다 적용되지만 Object[] 가 더 구체적
d("x");   // d(Object)
```

(공식 문서) JLS 15.12.2는 적용 가능한 메서드를 찾는 세 단계(엄격한 호출, 느슨한 호출, 가변 인자 호출)를 밝히고, 앞 단계에서 찾으면 뒤 단계로 가지 않으며 여러 개면 가장 구체적인 것을 고른다고 한다. 같은 절에 `m(Object)`가 있는 클래스에 `m(Object...)`를 선언하면 `m(null)`에 `m(Object[])`가 더 구체적이라 `m(Object)`가 선택되지 않는 예가 있다.
(실험 확인) `a(null)`은 `a(String)`, `a((Object) "s")`는 `a(Object)`였고 위 코드의 주석 결과가 그대로 나왔다(`d(null)`은 컴파일러가 varargs 호출인지 모호하다는 경고를 냈다). `m(String)`과 `m(StringBuilder)`에 `m(null)`은 `reference to m is ambiguous`로 컴파일되지 않았다. `m(int,double)`과 `m(double,int)`에 `m(1,1)`은 `reference to m is ambiguous`였다. `p(int...)`와 `p(Integer,Integer)`가 있을 때 `p(1,2)`는 박싱 단계(2단계)에서 `p(Integer,Integer)`가 선택됐고, `byte` 인자는 `q(char)`가 아니라 `q(int)`를 골랐다(JLS 5.1.2의 확대 변환 목록에 `byte`에서 `char`는 없다). `n(Object)`, `n(Integer)`, `n(long)`이 있을 때 `n(5)`는 `n(long)`이었다.
