**모범 답변 (30~60초)**
Object.equals의 기본 구현은 두 참조가 같은 객체일 때만 true를 돌려주는 동일성 비교이고, == 도 참조를 비교합니다. 값이 같으면 같은 객체로 보고 싶을 때 equals를 오버라이드하는데, 반사성, 대칭성, 추이성, 일관성을 지켜야 하고 null에는 false를 돌려줘야 합니다. 이때 hashCode도 함께 오버라이드해야 하는 이유는 equals가 같은 두 객체는 반드시 같은 해시코드를 내야 한다는 계약이 있기 때문입니다. 이를 어기면 HashMap이나 HashSet이 해시코드로 버킷을 찾기 때문에, 값이 같은 객체를 넣어 놓고도 contains나 get에서 찾지 못하는 일이 생깁니다. 반대로 해시코드가 같다고 equals까지 같을 필요는 없습니다.

(공식 문서) Object API 문서의 `equals`는 반사성·대칭성·추이성·일관성과 `x.equals(null)`이 false여야 한다는 규약, 기본 구현이 `x == y`일 때만 true인 가장 세분화된 동치 관계라는 점을 밝힌다. `hashCode`의 일반 규약(같은 객체는 일관된 값, equals가 같으면 해시코드도 같음, 다르다고 해서 해시코드가 달라야 하는 것은 아님)과, equals를 오버라이드하면 보통 hashCode도 오버라이드해야 한다는 API Note도 같은 문서에 있다. HashMap 문서는 해시 테이블 기반 구현이라고 하고 해시 함수가 요소를 버킷에 고르게 흩뜨린다는 전제에서 get·put이 상수 시간이라고 하며, HashSet 문서는 내부에서 HashMap 인스턴스를 쓴다고 한다.
(실험 확인) equals만 오버라이드한 클래스는 `new P1(1).equals(new P1(1))`이 `true`인데도 `HashSet`에 넣은 뒤 `contains(new P1(1))`이 `false`였다. 같은 값의 객체 1000쌍으로 반복하니 `contains`가 `true`인 경우가 0건이었고(이 실행에서. 기본 hashCode가 객체마다 달라 찾는 위치가 달라지는 것이며, 두 객체의 기본 해시코드가 우연히 같으면 결과가 달라질 수 있다), `HashMap.get`도 `null`이었다. hashCode까지 오버라이드하면 1000건 모두 `true`였다. `"ab"` 리터럴과 `new String("ab")`는 `==` 이 `false`, `equals`는 `true`였다.
(보충) HashMap·HashSet이 해시코드로 버킷을 먼저 찾은 뒤 그 안에서 equals로 비교한다는 조회 절차 자체는 위 문서들이 서술하지 않는 일반적인 설명이다.
