**모범 답변 (30~60초)**
클래스를 final로 막아 하위 클래스가 변경 가능성을 끼워 넣지 못하게 하고, 모든 필드를 private final로 두고, setter 없이 변경이 필요하면 새 객체를 돌려주게 만듭니다. 가장 놓치기 쉬운 것은 가변 필드로, 생성자에서 받은 리스트나 Date를 그대로 저장하면 호출자가 나중에 바꿀 수 있으니 생성자에서 방어적 복사를 하고, getter에서도 복사본이나 변경 불가 컬렉션을 돌려줘야 합니다. List.copyOf는 변경 불가한 복사본이지만 Collections.unmodifiableList는 원본을 감싼 읽기 전용 뷰라서 원본이 바뀌면 같이 바뀝니다. copyOf도 요소를 복제하지는 않는 얕은 복사라서 요소 자체가 가변이면 소용이 없습니다.

```java
final class Order {
    private final List<String> items;
    private final Date created;
    Order(List<String> items, Date created) {
        this.items = List.copyOf(items);              // 변경 불가 복사본(null 요소는 NPE)
        this.created = new Date(created.getTime());   // 가변 타입은 방어적 복사
    }
    List<String> items() { return items; }
    Date created() { return new Date(created.getTime()); }
}
```

(공식 문서) List 문서의 "Unmodifiable Lists" 절은 `List.of`·`List.copyOf`가 만든 리스트가 수정 불가이고 null 요소를 허용하지 않지만, 요소 자체가 가변이면 리스트 내용이 바뀌어 보일 수 있다고 한다. `List.copyOf`는 이후 원본이 바뀌어도 반영되지 않고 null 요소가 있으면 NPE이며, 이미 변경 불가한 리스트면 보통 복사하지 않는다고 한다. `Collections.unmodifiableList`는 변경 불가한 뷰이고 조회가 원본을 "read through"한다고 한다. Record API 문서도 record의 생성자·접근자를 직접 쓰는 주된 이유로 가변 컴포넌트의 방어적 복사를 든다.
(실험 확인) 위 `Order`는 원본 리스트에 요소를 추가하고 `Date`를 바꿔도 영향이 없었고, `items().add`는 `UnsupportedOperationException`이었다. 반대로 리스트를 그대로 저장한 클래스는 원본 변경이 `[a, b, c]`처럼 그대로 보였고, `unmodifiableList` 뷰는 원본에 추가한 요소가 보였지만 `List.copyOf`는 만든 시점의 복사본이었다(위 `Order`에서 확인). `StringBuilder` 요소의 `List.copyOf`는 요소를 바꾸면 복사본에서도 `[x!]`로 보였다.
(보충) 클래스를 final로 막고 필드를 private final로 두며 setter 없이 새 객체를 돌려준다는 설계 체크리스트 자체는 공식 문서의 규칙이 아니라 일반적인 설계 지침이다. 생성자 안에서 `this`를 다른 곳에 넘기지 않아야 완전히 만들어지기 전의 객체가 노출되지 않는다는 점, 상속을 막는 이유(하위 클래스가 상태를 바꾸는 메서드를 추가할 수 있음)도 같은 종류의 지침이며 따로 확인하지 않았다.
