**모범 답변 (30~60초)**
가장 안전한 순서로 말씀드리면 첫째, 아예 공유하지 않는 것입니다. 지역 변수나 스레드마다 따로 쓰는 객체는 동기화가 필요 없습니다. 둘째, 공유해야 한다면 불변으로 만드는 것입니다. 생성자에서 final 필드를 설정하고 생성이 끝나기 전에 this를 다른 스레드에 보이지 않게 하면, 데이터 레이스로 참조가 넘어가도 다른 스레드는 완전히 초기화된 final 값을 봅니다. 셋째, 바뀌는 상태는 synchronized나 락, 원자 클래스, 동시성 컬렉션으로 보호합니다. 이때 읽고 판단하고 쓰는 check-then-act는 하나의 임계 구역이나 원자 연산으로 묶어야 합니다.

(공식 문서) JLS 17.5는 final 필드로 동기화 없이 스레드 안전한 불변 객체를 구현할 수 있고, 생성자 종료 시점에 freeze가 일어나 생성이 끝난 뒤 참조를 본 스레드는 final 필드의 올바른 값을 본다고 한다. 단 생성 중에 객체 참조를 다른 스레드가 볼 수 있는 곳에 쓰지 말라는 조건이 붙는다. `Collections` 문서는 `unmodifiableList`가 지정한 리스트의 수정 불가 뷰를 돌려준다고 하고, `ThreadLocal` 문서는 각 스레드가 변수의 독립적으로 초기화된 자기 복사본을 가진다고 한다.
(실험 확인) 4스레드가 각각 200000번 일반 `int c++`를 하면 기대값 800000이 아니라 798187(처음 실행에서는 797875)이 나왔고, `synchronized` 메서드로 바꾸면 정확히 800000이었다. 불변 `record` 하나를 4스레드가 반복해 읽는 동안 값은 항상 일관됐다. 다른 스레드는 `ThreadLocal`에 넣은 main의 값을 보지 못했다(스레드 한정).
(보충) 스레드 한정·불변·락 보호의 우선순위는 문서가 정한 규칙이 아니라 일반적인 설계 관행이다.
