**모범 답변 (30~60초)**
핀닝은 가상 스레드가 블로킹되어도 캐리어 플랫폼 스레드에서 내려오지 못하고 그 스레드를 붙잡고 있는 현상입니다. Java 21~23에서는 synchronized 메서드나 블록 안에서 블로킹하면 핀닝되어, 캐리어가 부족해지면 확장성이 떨어지거나 심하면 교착까지 갈 수 있었습니다. Java 24의 JEP 491로 가상 스레드가 모니터를 캐리어와 무관하게 획득·보유·해제할 수 있게 되어, 25에서는 synchronized 안의 블로킹이나 모니터 대기, Object.wait 때문에 핀닝되는 일이 거의 없어졌습니다. 다만 네이티브 프레임이 스택에 있는 경우나 클래스 초기화 대기 같은 일부는 남아 있습니다.

(공식 문서) JEP 491(Release 24, Closed/Delivered)이 위 변화를 설명한다. 이전에는 JVM이 모니터 보유자로 가상 스레드가 아닌 캐리어 플랫폼 스레드를 기록해 핀닝이 필요했다고 하고, 남는 사례로 네이티브 메서드나 FFM이 자바 코드를 되부르며 블로킹하는 경우, 클래스 로딩과 클래스 초기화 중 블로킹, 다른 스레드의 초기화를 기다리는 경우를 든다. `jdk.VirtualThreadPinned` JFR 이벤트는 다른 핀닝 상황을 위해 유지되고, `jdk.tracePinnedThreads` 시스템 속성은 제거되어 설정해도 효과가 없다고 한다. JEP 444(Java 21)는 synchronized 블록·메서드 안에서 블로킹하면 핀닝된다고 했다. Java 25 가상 스레드 가이드는 네이티브 메서드나 외부 함수를 실행 중일 때 핀닝된다고 설명한다.
(실험 확인) 같은 방식으로 Java 25에서 스케줄러를 `-Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1`(캐리어 하나)로 제한하고, 서로 다른 락의 `synchronized` 안에서 1초 자는 가상 스레드 2개를 실행하자 약 1007ms에 끝났다(핀닝됐다면 약 2초). 같은 모니터를 다투는 3개의 가상 스레드(각 300ms)는 약 915ms로 직렬 실행됐다. 같은 코드를 Java 21(Temurin 21.0.12.1, Corretto 21.0.11)에서 돌리자 약 2010ms로 핀닝이 확인됐고 Java 24(Corretto 24.0.2)에서는 약 1010ms였다. 서로 다른 두 클래스의 static 초기화 블록 안에서 1초 자는 가상 스레드 2개는 캐리어 하나에서 Java 21, 24, 25 모두 약 2010ms로, 클래스 초기화 중 블로킹이 아직 핀닝된다는 JEP 문서와 일치했다. Java 22와 23은 이 PC에 없어 직접 확인하지 못했다.
(보충) Java 22·23도 21과 같다는 설명은 JEP 444(21)와 JEP 491(24)을 합친 추론이다. 8과 11, 17에는 가상 스레드 자체가 없어 이 문제도 없다.
