**모범 답변 (30~60초)**
submit은 작업의 예외를 반환된 Future 안에 담아 두기 때문에, get을 호출하지 않으면 아무 곳에도 출력되지 않고 조용히 사라진 것처럼 보입니다. get을 부르면 원인 예외를 감싼 ExecutionException이 던져집니다. 같은 예외를 execute로 던지면 풀 스레드의 처리되지 않은 예외로 기본 처리에 따라 스택 트레이스가 표준 오류에 출력됩니다. 종료는 shutdown이 새 작업만 거절하고 이미 제출된 작업은 끝까지 실행하고, shutdownNow가 실행 중 작업을 멈추려 시도하고(보통 인터럽트) 아직 시작 안 한 작업 목록을 돌려줍니다. Java 19부터의 close는 shutdown 후 종료까지 기다립니다.

(공식 문서) Future 문서는 계산이 예외를 던지면 `get()`이 ExecutionException을 던지고 예외로 끝나도 `isDone()`은 true라고 한다. `ThreadGroup.uncaughtException` 문서는 스레드·그룹·기본 핸들러에 처리자가 없으면 스레드 이름과 스택 트레이스를 표준 오류에 출력한다고 한다. ExecutorService 문서는 `shutdown`이 이전에 제출된 작업을 실행하게 두고 새 작업을 받지 않으며 `shutdownNow`는 실행 중인 작업을 멈추려 시도하고 대기 중이던 작업 목록을 돌려주며(일반 구현은 `Thread.interrupt()`로 취소하므로 인터럽트에 응답하지 않는 작업은 끝나지 않을 수 있다), 쓰지 않는 서비스는 종료해야 자원이 회수된다고 한다. `close()`는 Since 19이며 shutdown 후 종료를 기다리고, 대기 중 인터럽트되면 `shutdownNow`처럼 동작한다.
(실험 확인) `submit`한 작업의 예외는 출력되지 않았고 `isDone()`은 true, `get()`은 ExecutionException(원인 IllegalStateException)이었다. `execute`한 작업의 예외는 `Exception in thread "pool-1-thread-1"`으로 출력됐다. Java 21에서도 `close()`가 있고 같은 순서로 동작했다. `shutdown` 후 `submit`은 RejectedExecutionException, `shutdownNow()`는 실행 중 작업을 인터럽트하고 대기 중이던 작업 1개를 목록으로 돌려줬으며, try-with-resources의 `close()`는 작업이 끝난 뒤에 반환됐다.
