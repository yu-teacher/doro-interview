**모범 답변 (30~60초)**
데드락은 스레드들이 서로 상대가 쥔 락을 기다리며 영원히 멈추는 상태입니다. 일반적으로 상호 배제, 점유하며 대기, 비선점, 순환 대기 네 조건이 모두 있을 때 생기므로 하나만 깨도 막을 수 있습니다. 실무에서는 모든 스레드가 락을 같은 순서로 잡게 해 순환 대기를 없애는 것이 기본이고, tryLock에 시간 제한을 줘서 못 얻으면 이미 잡은 락을 놓고 물러나는 방법도 있습니다. 락을 잡은 채 외부 호출을 하지 않는 것도 중요합니다. 이미 생겼다면 ThreadMXBean의 findDeadlockedThreads로 탐지할 수 있지만, 진단용이고 플랫폼 스레드만 대상입니다.

(공식 문서) ThreadMXBean 문서가 `findDeadlockedThreads()`와 `findMonitorDeadlockedThreads()`로 실행 중인 애플리케이션의 데드락을 찾을 수 있고 `getThreadInfo`로 어떤 락을 기다리는지 알 수 있다고 한다. 전자는 객체 모니터와 ownable synchronizer를 함께 보고 후자는 객체 모니터만 보며, 둘 다 플랫폼 스레드 사이클만 찾고(가상 스레드가 낀 사이클은 못 찾는다고 한다) 문제 해결용일 뿐 동기화 제어용이 아니고 비쌀 수 있으며 데드락이 없으면 null을 돌려준다. ReentrantLock 문서는 시간 제한이 있는 `tryLock`을 제공한다.
(실험 확인) 두 스레드가 락 A, B를 반대 순서로 잡자 둘 다 BLOCKED였고 `findDeadlockedThreads()`가 2개 스레드를 돌려줬으며 각자 상대가 락의 소유자임을 보였다. 같은 순서로 잡은 쌍은 정상 종료했다. 반례로 `ReentrantLock` 두 개를 반대 순서로 잡은 플랫폼 스레드 쌍은 상태가 WAITING이었고 `findDeadlockedThreads()`는 2개를 찾았지만 `findMonitorDeadlockedThreads()`는 null이었다. 같은 상황의 가상 스레드 쌍은 둘 다 null이었다. `tryLock(300ms)`를 쓴 쌍은 3초 안에 끝났고 한쪽 이상이 포기했다(어느 쪽이 포기하는지는 실행마다 다르다).
(보충) 네 가지 필요 조건(Coffman 조건)은 JDK 문서가 아니라 일반 운영체제 이론이며, 락 순서 통일과 외부 호출 금지는 일반적인 설계 관행이다.
