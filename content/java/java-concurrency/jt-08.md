**모범 답변 (30~60초)**
wait, notify, notifyAll은 그 객체의 모니터를 가진 스레드만 호출할 수 있어서, synchronized 밖에서 부르면 IllegalMonitorStateException이 납니다. wait는 모니터를 풀고 대기 집합에서 기다리다가, 깨어나면 모니터를 다시 얻은 뒤에 돌아옵니다. 깨어났다고 조건이 참이라는 보장은 없습니다. 다른 스레드가 먼저 조건을 바꿔 놓았을 수도 있고, 문서가 말하는 spurious wakeup처럼 알림 없이 깨어날 수도 있습니다. 그래서 while 루프에서 조건을 다시 검사하는 것이 문서가 권장하는 방식입니다. 대기 중이 아닐 때 보낸 notify는 사라지므로, 알림 자체가 아니라 공유 상태 변수를 기준으로 판단해야 합니다.

(공식 문서) Object 문서는 `wait`/`notify`가 모니터 소유자만 호출할 수 있어 아니면 IllegalMonitorStateException이라고 하고, 알림·인터럽트·시간 초과 없이도 깨어나는 spurious wakeup이 있어 조건을 검사하고 아니면 계속 대기해야 하며 권장 방식이 while 루프라고 한다. `notify`는 이 객체를 기다리는 스레드가 있으면 그중 하나만 임의로 골라 깨운다고 하며, 대기 스레드가 없을 때 보낸 알림이 보존된다는 말은 없다. 깨어난 스레드는 다른 스레드와 같은 조건으로 모니터를 다시 경쟁해서 얻는다고 한다.
(실험 확인) 락 없이 `wait()`/`notify()`를 부르면 IllegalMonitorStateException이었다. 상태 변수와 `while`을 쓴 소비자는 생산자의 `notifyAll()` 후 값을 받았다. 대기 전에 보낸 `notify()`는 유실되어 `wait(500)`이 시간 초과(약 505ms)로 돌아왔다. 대기 스레드 3개 중 `notify()` 한 번 뒤 300ms 안에 깨어난 것은 1개였다.
