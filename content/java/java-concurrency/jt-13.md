**모범 답변 (30~60초)**
작업이 들어오면 먼저 실행 중인 스레드가 corePoolSize보다 적으면 놀고 있는 스레드가 있어도 새 스레드를 만듭니다. core가 다 찼으면 큐에 넣고, 큐가 가득 찼을 때에야 maximumPoolSize까지 스레드를 더 만듭니다. 그것도 다 찼거나 풀이 종료됐다면 RejectedExecutionHandler가 처리하는데, 기본 AbortPolicy는 예외를 던지고 CallerRunsPolicy는 제출한 스레드가 직접 실행해 유입 속도를 늦춥니다. DiscardPolicy는 조용히 버리고 DiscardOldestPolicy는 큐의 가장 오래된 작업을 버립니다. 그래서 큐 크기를 무한으로 두면 max는 의미가 없어집니다.

(공식 문서) ThreadPoolExecutor 문서가 core→큐→max 순서의 동작, 큐 전략(직접 전달·무한 큐·유한 큐), 유한 큐와 유한 max에서의 거부, 네 가지 기본 정책의 동작을 설명한다. 무한 큐를 쓰면 core 스레드 수를 넘게 만들지 않아 max가 효과 없다고도 한다.
(실험 확인) core 2, max 4, 용량 2인 `ArrayBlockingQueue`에 오래 걸리는 작업 7개를 넣자 작업 1·2는 스레드, 3·4는 큐, 5·6은 추가 스레드(풀 크기 3, 4)로 가고 7은 RejectedExecutionException이었다. core 1, 큐 1에 `CallerRunsPolicy`를 쓰면 세 번째 작업이 `main` 스레드에서 실행됐다.
