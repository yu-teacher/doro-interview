**모범 답변 (30~60초)**
ThreadLocal 값은 스레드가 살아 있는 동안 남는데, 풀의 스레드는 작업이 끝나도 죽지 않고 재사용됩니다. 그래서 한 요청에서 set한 값을 지우지 않으면 같은 스레드가 처리하는 다음 요청이 그 값을 보게 되어 다른 사용자의 정보가 새거나 메모리가 계속 붙들립니다. 작업 시작에서 set하고 finally에서 반드시 remove해야 합니다. InheritableThreadLocal은 부모 스레드의 값을 스레드를 만들 때 한 번 복사할 뿐이라 이미 만들어진 풀 스레드에는 이후 변경이 전달되지 않습니다. Java 25부터 정식인 ScopedValue는 값을 실행 범위에만 묶어 범위가 끝나면 풀리게 하지만, 이미 만들어진 풀 스레드로 값을 넘겨 주지는 않습니다.

(공식 문서) ThreadLocal 문서는 스레드가 살아 있고 ThreadLocal 인스턴스에 접근 가능한 동안 값 복사본에 대한 참조가 유지되며 스레드가 사라지면 가비지 수집 대상이 된다고 한다. ScopedValue 문서(Since 25)는 ThreadLocal이 호출된 먼 메서드에서도 값을 바꿀 수 있고 메서드가 끝난 뒤에도 값이 남고 상속이 비싸다는 이유로, 한 방향 전달에는 ScopedValue를 선호하라고 한다. 가상 스레드 가이드는 가상 스레드도 ThreadLocal을 지원하지만 수백만 개일 수 있으므로 신중히 쓰라고 한다. `ScopedValue` 문서는 바인딩이 스레드별이고 스레드 사이 공유는 `StructuredTaskScope`(프리뷰)로 시작한 자식 스레드 같은 구조화된 경우로 한정된다고 하며, `Thread` 문서는 상속 가능한 스레드 로컬의 초기값을 자식 스레드가 만들어지는 시점의 부모 값에서 받는다고 한다. JEP 506은 25에서 `ScopedValue`를 확정했고, `Executors.newFixedThreadPool` 문서는 풀의 스레드가 명시적으로 shutdown할 때까지 존재하며 작업이 끝나도 재사용된다고 한다.
(실험 확인) 고정 풀(스레드 1개)에서 한 작업이 `set("alice")`만 하고 끝나자 다음 작업이 `alice`를 읽었고, `finally`에서 `remove()`한 뒤에는 null이었다. 일반 ThreadLocal은 새 스레드에서 null, InheritableThreadLocal은 부모 값이었다. 풀의 첫 작업이 `v1`을 봤고, main이 `v2`로 바꾼 뒤 두 번째 작업은 여전히 `v1`을 읽었다. 가상 스레드에서도 ThreadLocal이 동작했다. `ScopedValue.where(U, "alice").run(...)` 안에서 `isBound()`는 같은 스레드에서 true였지만 풀 스레드에 `submit`한 작업에서는 false였고 범위를 벗어나면 false였다.
(보충) 스레드 풀에서의 값 누수가 개인 정보 노출이나 메모리 점유로 이어진다는 시나리오와 `set` 직후 `try`/`finally`에서 `remove`하는 처리 요령은 문서의 직접 서술이 아니라 일반적인 설명이다. 풀 스레드에는 바인딩이 전달되지 않는다는 점은 `ScopedValue` 문서의 서술과 실험으로 확인했다.
