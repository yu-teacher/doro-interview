**모범 답변 (30~60초)**
newFixedThreadPool은 스레드 수만 고정이고 작업 대기열은 용량 제한이 없는 큐를 씁니다. 그래서 처리 속도보다 제출 속도가 빠르면 작업이 큐에 끝없이 쌓여 메모리를 먹고, 거부 정책도 작동하지 않습니다. newCachedThreadPool은 반대로 JDK 구현상 core가 0이고 최대 스레드 수가 사실상 무제한이며 직접 전달 큐를 쓰기 때문에, 작업이 몰리면 스레드가 작업 수만큼 만들어질 수 있습니다. 그래서 운영 환경에서는 ThreadPoolExecutor를 직접 만들어 유한한 큐와 최대 스레드 수, 거부 정책, 이름 있는 ThreadFactory를 명시하는 편이 안전합니다.

(공식 문서) Executors 문서가 `newFixedThreadPool`은 공유되는 무한 큐(unbounded queue)에서 작업을 가져가고 `newCachedThreadPool`은 필요한 만큼 새 스레드를 만들어 재사용한다고 한다. ThreadPoolExecutor 문서는 캐시 풀을 "unbounded thread pool"로 부르고, 직접 전달 큐는 무한 maximumPoolSize가 필요해 스레드가 무한히 늘 수 있으며, 무한 큐는 core 스레드 수를 넘게 만들지 않아 max가 무의미하다고 설명한다. 거부는 종료됐을 때, 또는 최대 스레드 수와 큐 용량이 모두 유한한 채 포화일 때 일어난다고 하므로 무한 큐에서는 포화로 인한 거부가 일어나지 않는다.
(실험 확인) `newFixedThreadPool(2)`에 오래 걸리는 작업 1000개를 넣자 스레드는 2개, 큐에는 998개가 쌓였고 큐는 `LinkedBlockingQueue`(남은 용량 약 21억)였다(`ThreadPoolExecutor`로 형변환해 확인했으며 이 값들은 `Executors` 문서가 아니라 OpenJDK(Corretto 25.0.3) 구현에서 읽은 것이다). `newCachedThreadPool()`에 500개를 넣자 스레드가 500개 생겼고 core 0, max 2147483647, keepAlive 60초, 큐는 `SynchronousQueue`였다.
(보충) 이것이 메모리 부족이나 스레드 고갈로 이어질 수 있다는 운영상의 결론과 유한 큐와 거부 정책 조합 권장은 문서의 직접 서술이 아니라 일반적인 판단이다.
