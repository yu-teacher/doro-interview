**모범 답변 (30~60초)**
ConcurrentHashMap은 get, put 같은 개별 연산이 스레드 안전하고 조회에 락이 없지만, 여러 호출을 묶은 복합 연산까지 원자적으로 만들어 주지는 않습니다. get으로 읽은 값을 바탕으로 put하면 그 사이 다른 스레드가 끼어들어 갱신을 잃으므로 merge, compute, computeIfAbsent처럼 한 번의 원자 연산으로 표현해야 하고, 이때 함수는 짧아야 하며 맵을 수정하면 안 됩니다. synchronizedMap도 같은 한계가 있고 순회할 때는 직접 동기화해야 합니다. null 키와 값은 허용되지 않고 반복자는 예외 없이 약한 일관성입니다. CopyOnWriteArrayList는 쓸 때마다 복사하고 반복자는 스냅샷이라 읽기가 압도적일 때 알맞습니다.

(공식 문서) ConcurrentHashMap 문서는 조회에 락이 없고 전체 테이블을 잠그는 방법은 지원하지 않으며, `get`은 대체로 갱신과 겹쳐 최근 완료된 갱신을 반영하고 반복자는 생성 시점 이후의 상태를 반영하며 ConcurrentModificationException을 던지지 않고 한 스레드에서만 쓰도록 설계됐다고 한다. null 키·값은 허용하지 않고, `computeIfAbsent`는 호출 전체가 원자적이고 함수는 키가 없을 때 한 번만 호출되며 계산이 짧아야 하고 맵을 수정하면 안 된다. `java.util.concurrent` 패키지 문서는 동기화(synchronized) 클래스는 하나의 배타 락으로 보호되고 동시성(concurrent) 컬렉션은 그렇지 않으며 반복자가 예외 없이 약하게 일관된 순회를 한다고 한다. `Collections.synchronizedMap` 문서는 반환된 맵으로만 접근해야 직렬 접근이 보장되고 뷰를 순회할 때 사용자가 직접 동기화해야 한다고 하고, CopyOnWriteArrayList 문서는 순회가 쓰기보다 훨씬 많을 때 적합하고 스냅샷 방식 반복자는 ConcurrentModificationException을 던지지 않는다고 한다.
(실험 확인) 4스레드가 각 100000번 키 하나를 증가시키면 기대값 400000에 대해 `synchronizedMap` get+put은 218549(처음 실행에서는 204881), `ConcurrentHashMap` get+put은 370052(365936), `merge`는 400000이었다. 8스레드의 `computeIfAbsent` 함수 호출은 1번이었다. `null` 키·값 `put`은 NPE(`HashMap`은 null 키 허용)였고, `ArrayList`는 순회 중 수정에서 ConcurrentModificationException이 났지만 `ConcurrentHashMap`과 `CopyOnWriteArrayList`는 나지 않았으며 후자는 3개만 순회했다.
