**모범 답변 (30~60초)**
ReentrantLock은 synchronized와 기본 동작과 의미는 같은 재진입 상호 배제 락이지만 기능이 더 많습니다. 락을 못 얻으면 바로 돌아오는 tryLock이나 시간 제한을 주는 tryLock, 대기 중 인터럽트에 응답하는 lockInterruptibly, 공정성 옵션을 쓸 수 있고, 한 락에 Condition을 여러 개 만들 수 있습니다. 대신 블록 구조가 아니어서 lock 직후 try를 열고 finally에서 unlock을 직접 불러야 하고, 빠뜨리면 락이 영영 안 풀립니다. 이런 기능이 필요 없으면 synchronized가 간단하고 실수도 적습니다. 공정 락은 처리량이 크게 떨어질 수 있다고 문서가 경고합니다.

(공식 문서) ReentrantLock 문서가 synchronized와 같은 기본 동작·의미에 확장 기능이 있다고 하고, 공정 모드가 기아를 막는 대신 처리량이 낮아질 수 있으며 시간 제한 없는 `tryLock()`은 공정성 설정을 따르지 않는다고 한다. lock 직후 `try`를 열고 `finally`에서 `unlock`을 호출하라는 권장 패턴도 문서에 있다. locks 패키지 문서는 `Condition`을 한 `Lock`에 여러 개 연결할 수 있고 `Lock`은 블록 구조가 아닌 곳에서도 쓸 수 있다고 한다. JEP 491은 `ReentrantLock`이 `synchronized`와 같게 동작하고 try-finally와 함께 써야 하며, 새 코드에서는 `synchronized`가 더 편하고 실수가 적으니 유연성이 필요할 때 `ReentrantLock`을 쓰라고 한다.
(실험 확인) 같은 스레드가 `lock()`을 두 번 하면 보유 횟수가 2였고 `unlock()`을 두 번 해야 풀렸다. 다른 스레드의 `tryLock(200ms)`와 `tryLock()`은 둘 다 false였다. `lockInterruptibly()` 대기는 인터럽트로 끝났지만 `synchronized` 진입 대기 스레드는 인터럽트돼도 BLOCKED로 남았다. 락 없이 `unlock()`하면 IllegalMonitorStateException이었다.
(보충) 버전 차이: JEP 444(Java 21)는 가상 스레드가 `synchronized` 안에서 블로킹되면 고정(pinning)된다고 했고 JEP 491(Release 24)이 이를 해소해서, 핀닝을 피하려고 `ReentrantLock`으로 바꾸라던 권고는 24부터 필요 없다(jt-20 참고). 21~23이 해당 구간이라는 점은 두 문서를 합친 추론이다. `unlock`을 빠뜨리면 락이 영영 풀리지 않는다는 결과는 일반 설명이다.
