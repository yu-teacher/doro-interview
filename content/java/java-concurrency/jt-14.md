**모범 답변 (30~60초)**
thenApply는 결과 값을 다른 값으로 바꾸는 map이고, thenCompose는 결과로 또 하나의 CompletableFuture를 돌려주는 함수를 받아 중첩 없이 이어 붙이는 flatMap입니다. 그래서 비동기 호출을 연달아 이을 때는 thenCompose를 씁니다. Async가 붙은 메서드를 Executor 없이 부르면 ForkJoinPool.commonPool에서 실행되는데(API 문서는 공통 풀의 병렬도가 1 이하면 작업마다 새 스레드를 쓴다고 서술합니다), 블로킹이 있거나 격리가 필요한 작업에는 Executor를 직접 넘겨야 합니다. 예외가 나면 이후 단계는 건너뛰고 CompletionException으로 전파되며, exceptionally나 handle에서 복구합니다. join은 CompletionException을, get은 ExecutionException을 던집니다.

(공식 문서) CompletableFuture 문서는 async 메서드를 Executor 인자 없이 쓰면 `ForkJoinPool.commonPool()`을 쓰고, 비async 의존 작업은 완료시킨 스레드나 완료 메서드를 호출한 다른 스레드에서 실행될 수 있다고 한다. 취소는 예외 완료의 한 형태이고 `cancel`은 `completeExceptionally(new CancellationException())`와 같다고 한다. `defaultExecutor()`(Since 9) 문서는 공통 풀이 병렬 스레드를 둘 이상 지원하면 그것을 쓰고 아니면 async 작업마다 스레드 하나를 쓰는 Executor를 쓴다고 한다. 예외로 끝난 단계에 의존하는 단계는 원인 예외를 담은 CompletionException으로 예외 완료되고(CompletionStage 문서), `get`은 같은 원인의 ExecutionException을, `join`은 CompletionException을 던지며 취소됐을 때는 CancellationException을 던진다.
(실험 확인) `thenApply`로 Future를 반환하면 `CompletableFuture<CompletableFuture<Integer>>`가 되고 `thenCompose`는 한 겹으로 풀려 2를 얻었다. `supplyAsync`는 `ForkJoinPool.commonPool-worker-1`에서(병렬도 14, 코어 15), Executor를 주면 그 풀 스레드에서 실행됐다. 실패한 Future는 `get()`이 ExecutionException, `join()`이 CompletionException을 던졌고 `supplyAsync`가 던진 예외를 같은 단계의 `exceptionally`가 받으면 CompletionException이었다. 반례로 `completeExceptionally(IOException)`으로 직접 완료한 단계의 `exceptionally`는 원본 IOException을 받았고, 그 단계에 의존하는 다음 단계는 CompletionException(원인 IOException)을 받았다. 취소한 Future는 `join()`과 `get()` 모두 CancellationException이었다. 이미 완료된 Future의 `thenApply`는 호출자인 main 스레드에서 실행됐다. `orTimeout`은 TimeoutException으로 완료됐다.
(보충) `thenApply`를 map, `thenCompose`를 flatMap에 빗댄 설명과, 블로킹 작업에는 Executor를 직접 넘기라는 권고는 문서의 직접 서술이 아니라 일반적인 설명이다.
