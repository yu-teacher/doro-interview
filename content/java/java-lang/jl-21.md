**모범 답변 (30~60초)**
equals와 hashCode에 쓰이는 필드를 키로 넣은 뒤에 바꾸면, 객체는 컬렉션에 그대로 들어 있지만 바뀐 해시코드로는 더 이상 찾지 못할 수 있습니다. 컬렉션은 넣을 때의 해시코드로 위치를 정했는데 조회할 때는 바뀐 해시코드로 위치를 찾기 때문입니다. 그 결과 contains나 get이 false나 null을 주고, size에는 여전히 포함되며 순회하면 보이고 remove로도 지우기 어려워 사실상 누수가 됩니다. Map과 Set 문서는 이런 경우 동작이 정해져 있지 않다고 경고합니다. 그래서 키는 String이나 Integer, 불변 객체로 쓰는 것이 안전합니다.

```java
M m = new M(5);        // equals/hashCode 가 id 기반
Set<M> s = new HashSet<>();  s.add(m);
m.id = 6;
s.contains(m);          // false  (같은 객체인데도)
s.remove(m);            // false
s.size();               // 1
s.iterator().next().id  // 6     (순회하면 보임)
```

(공식 문서) Map API는 equals 비교에 영향을 주는 방식으로 키 객체의 값이 바뀌면 맵의 동작이 명시되지 않는다고 밝히고, 변경 가능한 객체를 키로 쓸 때 큰 주의를 요구한다. Set API도 요소에 대해 같은 경고를 한다. Object.hashCode 계약은 equals에 쓰인 정보가 바뀌지 않는 한 같은 값을 돌려줘야 한다고 하므로, 정보를 바꾸면 이 일관성 보장이 사라진다.
(실험 확인) 위 코드는 HotSpot(Corretto 25.0.3)에서 `contains` false, `remove` false, `size` 1, 순회로 id 6이 보이는 결과였다. 값을 5로 되돌리면 다시 `contains`가 true였고, `HashMap`에서도 키를 바꾸면 `get`이 바뀐 키와 원래 값의 새 키 모두 null이었다. 같은 버킷으로 가는 값(5에서 21)으로 바꿔도 `contains`와 `remove`는 false였고, `iterator().remove()`로는 지워졌으며, 바꾼 뒤 같은 객체를 다시 `add`하면 true가 반환되어 size가 2가 됐다.
(보충) 바뀐 뒤에 못 찾는 구체적인 이유는 HashMap 내부 구현에 의존하는 설명이고 문서는 동작이 명시되지 않는다고만 한다. 위 실험에서 같은 버킷으로 가는 값(16개 버킷에서 5와 21)으로 바꿔도 찾지 못한 것은, 해시값까지 저장해 비교하기 때문이라고 추정하지만 소스를 읽어 확인하지는 않았다.
