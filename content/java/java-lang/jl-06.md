**모범 답변 (30~60초)**
unchecked 예외는 RuntimeException과 그 하위 클래스, 그리고 Error와 그 하위 클래스이고, 나머지 Throwable 하위 클래스는 모두 checked 예외입니다. checked 예외가 발생할 수 있는 코드는 컴파일러가 검사해서, try-catch로 잡거나 메서드에 throws로 선언하지 않으면 컴파일 오류가 납니다. 반대로 unchecked 예외는 이런 강제가 없습니다. JLS는 Error가 여러 지점에서 생길 수 있고 복구가 어려워 검사에서 빠진다고 설명하고, 던질 가능성이 없는 checked 예외를 catch하는 것도 오류로 막습니다(Exception과 Throwable은 예외).

```java
void f() { throw new IOException("x"); }        // error: unreported exception IOException
void g() { try { } catch (IOException e) { } }  // error: exception IOException is never thrown in body of corresponding try statement
// RuntimeException.class.getSuperclass() -> Exception, Error.class.getSuperclass() -> Throwable
```

(공식 문서) JLS 11.1.1은 unchecked 예외 클래스를 RuntimeException 계열과 Error 계열로, checked 예외 클래스를 그 외의 모든 예외 클래스(Throwable과 그 하위 중 위 둘을 제외한 것)로 정의한다. 11.2는 checked 예외가 결과가 될 수 있으면 throws 절에 그 클래스나 상위 클래스를 선언하거나 처리해야 한다고 한다. 11.2.3은 catch 절의 checked 예외 E1을 try 블록이 던질 수 없으면(E1이 Exception이거나 그 상위 클래스인 경우는 제외) 컴파일 오류라고 하고, 11.2는 Error 계열이 많은 지점에서 발생할 수 있고 복구가 어렵거나 불가능해서 검사에서 제외된다고 설명한다.
(실험 확인) 위 두 메서드는 javac 25에서 주석의 오류 메시지로 컴파일에 실패했다. `RuntimeException.class.getSuperclass()`는 `Exception`, `Error.class.getSuperclass()`는 `Throwable`이었고, 아무것도 던지지 않는 try에 `catch (Exception e)`나 `catch (Throwable t)`를 붙인 코드와 `catch (Error e)`, `catch (RuntimeException r)`를 붙인 코드는 컴파일됐다.
(보충) 언제 어느 쪽으로 정의할지(복구 가능하면 checked, 프로그래밍 오류면 unchecked)는 널리 쓰이는 설계 지침이고 공식 사양이 강제하는 것은 아니다. JLS 11.1.1은 컴파일 타임 검사를 활용하려면 새 예외 클래스를 대부분 checked로 정의하는 것이 보통이라고만 적는다.
