**모범 답변 (30~60초)**
문자열 리터럴과 값이 컴파일 시점 상수인 표현식의 결과는 intern된, 즉 풀에서 공유되는 하나의 인스턴스입니다. 그래서 같은 내용의 리터럴끼리는 ==가 true입니다. new String은 항상 새 객체를 만들기 때문에 내용이 같아도 리터럴과 ==가 false이고, 런타임에 계산된 연결 결과도 새 객체입니다. intern 메서드는 풀에 같은 내용이 있으면 그 인스턴스를, 없으면 이 객체를 풀에 넣고 돌려주므로 intern한 결과끼리는 equals가 같을 때 ==도 같습니다. 다만 비교는 어디까지나 equals로 해야 합니다.

```java
String s1 = "hello", s3 = new String("hello"), lo = "lo";
final String flo = "lo";
s1 == s3                // false
s1 == ("hel" + "lo")    // true  (상수 표현식)
s1 == ("hel" + lo)      // false (런타임 연결)
s1 == ("hel" + flo)     // true  (final 변수는 상수 변수)
s1 == ("hel" + lo).intern()  // true
s3.intern() == s1       // true
```

(공식 문서) JLS 3.10.5는 문자열 리터럴과 상수 표현식(15.29)의 값인 문자열이 String.intern을 실행한 것처럼 유일한 인스턴스를 공유한다고 한다. 4.12.4는 상수 변수를 상수 표현식으로 초기화한 기본 타입이나 String 타입의 final 변수로 정의하고, 15.29는 상수 변수를 가리키는 단순 이름이 상수 표현식이 될 수 있다고 한다. 15.18.1은 연결 결과가 상수 표현식이 아니면 새로 만들어진 String이라고 하고, `String(String)` 생성자 API는 인자의 복사본인 새 String을 초기화한다고 한다. String.intern API는 풀에 equals가 같은 문자열이 있으면 그 풀의 문자열을 돌려주고, 없으면 이 객체를 풀에 추가하며, 따라서 `s.intern() == t.intern()`이 true인 것은 `s.equals(t)`일 때뿐이라고 한다.
(실험 확인) 위 여섯 개 식의 결과는 주석과 같았다.
(보충) 풀이 JVM 메모리의 어느 영역에 있는지는 사양이 정하지 않는 구현 사항이라 여기서는 다루지 않았다. 문자열 풀을 이용해 비교를 `==`로 최적화하는 것은 권장하지 않는다.
