**모범 답변 (30~60초)**
제네릭은 불공변이라 List<Integer>를 List<Number>에 대입할 수 없습니다. 이 제약을 풀면서 안전을 지키려고 와일드카드를 씁니다. ? extends Number는 Number의 어떤 하위 타입 리스트든 받을 수 있지만, 실제 원소 타입을 모르니 null 말고는 넣을 수 없고 꺼내기만 할 수 있습니다. ? super Integer는 Integer의 어떤 상위 타입 리스트든 받아서 Integer를 넣을 수 있지만 꺼내면 Object로만 다룹니다. 그래서 생산자는 extends, 소비자는 super를 쓰라는 PECS 규칙으로 외웁니다. 배열은 공변이라 컴파일되고 런타임에 ArrayStoreException이 납니다.

```java
List<Number> ln = new ArrayList<Integer>();        // error: incompatible types
List<? extends Number> p = new ArrayList<Integer>(List.of(1, 2));
Number n = p.get(0);                                // OK
p.add(Integer.valueOf(1));                          // error: Integer cannot be converted to CAP#1
List<? super Integer> c = new ArrayList<Number>();
c.add(3);  Object o = c.get(0);                     // 넣기 OK, 꺼내면 Object
Object[] oa = new String[1]; oa[0] = 1;             // 런타임 ArrayStoreException
```

(공식 문서) JLS 4.5.1은 ? extends B로 상한, ? super B로 하한을 지정한다고 하고, 포함 관계 규칙(? extends T <= ? extends S는 T <: S일 때 등)을 정의한다. 이 규칙에서 List<Integer>와 List<Number> 사이에는 포함 관계가 없고, 4.10.2는 C<S>의 직접 상위 타입으로 S가 T를 포함하는 C<S>를 든다. 4.10.3은 참조 타입 배열이 공변이라고 하고, JLS 10.5는 배열 요소 대입을 런타임에 검사해 맞지 않으면 ArrayStoreException을 던진다고 한다.
(실험 확인) 위 각 줄은 javac 25와 실행 결과가 주석과 같았다. `p.add(null)`은 컴파일됐고 `p.add(Integer.valueOf(1))`은 `Integer cannot be converted to CAP#1` 오류였으며, `? super Integer` 리스트에서 `Integer i = c.get(0)`은 `CAP#1 cannot be converted to Integer` 오류였다.
(보충) PECS(Producer Extends, Consumer Super)라는 이름은 널리 쓰이는 암기용 별칭이고 JLS의 용어는 아니다.
