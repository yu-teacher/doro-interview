**모범 답변 (30~60초)**
double은 이진 부동소수점이라 0.1이나 0.2 같은 값을 정확히 표현하지 못하고 가장 가까운 근삿값을 저장합니다. 그래서 더한 결과도 0.3이 아니라 0.30000000000000004 쪽이 되어 ==가 false입니다. NaN은 자기 자신과도 ==가 false라는 점도 알아 둘 것입니다. 정확한 십진 계산이 필요한 금액에는 BigDecimal을 쓰되, 문서가 권하는 대로 double 생성자 대신 문자열 생성자로 만듭니다. 또 BigDecimal.equals는 값뿐 아니라 scale까지 같아야 true라서 2.0과 2.00은 다르고, 값만 비교하려면 compareTo를 씁니다.

```java
0.1 + 0.2                 // 0.30000000000000004
0.1 + 0.2 == 0.3          // false
new BigDecimal(0.1)       // 0.1000000000000000055511151231257827021181583404541015625
new BigDecimal("0.1").add(new BigDecimal("0.2"))   // 0.3
new BigDecimal("2.0").equals(new BigDecimal("2.00"))     // false
new BigDecimal("2.0").compareTo(new BigDecimal("2.00"))  // 0
Double.NaN == Double.NaN  // false
```

(공식 문서) JLS 15.4는 부동소수점 산술이 실수 산술의 근사이며 기본 반올림 정책이 가장 가까운 표현 가능한 값으로 맞추는 round to nearest라고 하고, 15.21.1은 NaN이 피연산자인 `==`는 false라고 한다. Double API는 십진수 0.1이 이진 소수로는 반복되는 소수라 정확히 표현되지 않아 0.1f != 0.1d라고 설명한다. BigDecimal(double) 생성자 문서는 `new BigDecimal(0.1)`이 정확히 0.1이 아니라 0.1000000000000000055511151231257827021181583404541015625이며 결과가 다소 예측하기 어려우므로 문자열 생성자를 쓰라는 취지로 안내하고, double을 꼭 써야 하면 정적 메서드 valueOf(double)을 쓰라고 한다. BigDecimal.compareTo 문서는 값이 같고 scale만 다른 두 값(2.0과 2.00)을 같다고 본다고 한다. BigDecimal.equals 문서는 값과 scale이 모두 같아야 같다고 하며 2.0과 2.00이 다르다고 직접 예를 든다. 같은 문서는 BigDecimal의 자연 순서가 equals와 일관되지 않으므로 SortedSet, SortedMap 키로 쓸 때 주의하라고 한다.
(실험 확인) 위 출력은 모두 주석과 같았다. `BigDecimal.valueOf(0.1)`은 `0.1`이었다.
(보충) 금액 계산에서 반올림 모드와 scale을 명시해야 하는 문제(나눗셈 등)는 이 질문 범위 밖이라 다루지 않았다.
