**모범 답변 (30~60초)**
Object 계약이 equals로 같은 두 객체는 hashCode도 반드시 같은 값을 돌려줘야 한다고 정하기 때문입니다. HashMap이나 HashSet 같은 해시 기반 컬렉션은 먼저 해시코드로 찾을 위치를 정하고 그다음에 equals로 비교하므로, equals만 재정의하고 hashCode를 그대로 두면 내용이 같은 객체인데도 서로 다른 해시코드가 나와 contains나 get이 실패합니다. 반대로 equals가 다른 객체끼리 해시코드가 같아도 규칙 위반은 아니며 충돌이 늘어 성능만 나빠집니다. 필드 기반으로 만들 때는 Objects.hash를 쓸 수 있습니다.

```java
class K { int id; K(int i){id=i;}
  public boolean equals(Object o){ return o instanceof K k && k.id==id; } }   // hashCode 미재정의
Set<K> s = new HashSet<>(); s.add(new K(1));
s.contains(new K(1));   // false, 그런데 new K(1).equals(new K(1)) 는 true
// hashCode()를 Integer.hashCode(id)로 재정의하면 contains -> true
```

(공식 문서) Object.hashCode API의 일반 계약은 세 가지다. 같은 객체에서 반복 호출하면 equals에 쓰이는 정보가 바뀌지 않는 한 같은 값을 돌려주고, equals로 같은 두 객체는 같은 해시코드를 내야 하며, equals로 다른 객체가 서로 다른 해시코드를 낼 필요는 없지만 다르게 내면 해시 테이블 성능에 도움이 된다. equals는 반사·대칭·추이·일관성을 지키고 null과는 false여야 한다. Objects.hash와 hashCode는 간단한 해시코드를 만드는 데 쓸 수 있다고 API 노트가 안내한다. HashMap API는 버킷을 쓰는 해시 테이블 기반이며 같은 hashCode를 가진 키가 많으면 성능이 확실히 나빠진다고 한다.
(실험 확인) 위 K로 `contains`는 false였고, hashCode를 재정의한 같은 모양의 클래스에서는 true였다. 단 K의 false는 기본 hashCode가 객체마다 거의 항상 다른 값을 내는 HotSpot 동작 덕분이고, 우연히 해시코드가 같으면 true가 될 수도 있어 규칙 위반의 결과가 항상 같지는 않다.
(보충) 해시 컬렉션이 해시코드로 위치를 정한 뒤 equals로 비교한다는 동작 순서는 해시 테이블의 일반적인 설명이고, Object나 HashMap API 문서에 단계별로 적혀 있지는 않다.
