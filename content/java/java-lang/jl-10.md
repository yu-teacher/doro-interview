**모범 답변 (30~60초)**
상수 표현식으로 박싱하는 -128부터 127까지의 값은 JLS가 항상 같은 객체가 되도록 요구하고, Integer.valueOf도 이 범위를 항상 캐시하기 때문입니다. 그래서 127끼리는 같은 인스턴스라 ==가 true지만, 128은 그 범위 밖이라 박싱할 때마다 새 객체가 만들어져도 괜찮아서 HotSpot에서는 ==가 false가 됩니다. 범위 밖은 사양이 동일성에 대해 아무것도 약속하지 않으므로 이 동작에 기대면 안 됩니다. 래퍼 객체는 equals로 비교하세요. 한쪽이 int 기본 타입이면 언박싱되어 숫자로 비교되므로 ==가 true입니다. 또 Long.equals에 int를 넘기면 타입이 달라 false입니다.

```java
Integer x1=127, x2=127, y1=128, y2=128;
x1 == x2            // true
y1 == y2            // false
y1.equals(y2)       // true
Integer big = 1000; int p = 1000;  big == p   // true (언박싱 후 숫자 비교)
Long L = 127L;  L.equals(127)  // false (127은 Integer로 박싱됨)   L.equals(127L) // true
```

(공식 문서) JLS 5.1.7은 박싱되는 값이 boolean·byte·char·short·int·long 타입 상수 표현식의 결과이고 그 값이 true·false, '\u0000'~'\u007f' 문자, -128~127 정수 중 하나일 때 임의의 두 박싱 변환 결과가 항상 `==`이라고 하고, 그 밖의 값은 동일성에 대한 가정을 허용하지 않는다고 설명한다. Integer.valueOf API는 -128~127은 항상 캐시하고 그 밖의 범위는 캐시할 수도 있다고 하며, 새 인스턴스가 필요 없으면 생성자보다 valueOf를 쓰라고 권장한다. JLS 15.21.1은 한쪽이 숫자 타입이고 다른 쪽이 숫자로 변환 가능하면 이항 숫자 승격(언박싱 포함)을 한다고 한다. Long.equals API는 인자가 null이 아니고 Long 객체일 때만 true라고 한다.
(실험 확인) 위 결과는 모두 주석과 같았다. `Integer.valueOf(128) == Integer.valueOf(128)`도 이 JDK(HotSpot, Corretto 25.0.3)에서는 false였다. 상수가 아닌 `int k=128; Integer a=k, b=k`도 false, `int k=127`은 true였고, `Long` 127L/128L은 true/false, `Character` '\u007f'/'\u0080'은 true/false, `Integer` -128/-129는 true/false였다. `-XX:AutoBoxCacheMax=1000`을 주고 실행하면 128과 1000의 `==`가 모두 true가 되었다(이 옵션은 HotSpot 구현 사항이며 API 문서에는 없다).
