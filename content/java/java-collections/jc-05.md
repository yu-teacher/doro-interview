**모범 답변 (30~60초)**
Comparable은 클래스 자신이 compareTo로 정의하는 자연 순서이고, 이걸 구현하면 Collections.sort나 TreeMap, TreeSet이 별도 설정 없이 그 순서를 씁니다. Comparator는 비교 로직을 객체 밖에서 compare로 따로 정의하는 것이라, Comparable이 없는 클래스를 정렬하거나 상황마다 다른 정렬 기준을 쓸 때 사용합니다. Comparator.comparing과 thenComparing을 체이닝하면 여러 기준을 조합할 수 있습니다. Comparable 문서는 자연 순서를 equals와 일관되게 만들 것을 강하게 권장하고, Comparator 문서는 일관되지 않은 기준을 정렬 컬렉션에 쓸 때 주의하라고 합니다.

```java
record R(String n, int age) {}
rs.sort(Comparator.comparingInt(R::age).thenComparing(R::n));
// [R[n=c, age=20], R[n=a, age=30], R[n=b, age=30]]
```

(공식 문서) Comparable 문서는 자연 순서가 있으면 정렬 메서드와 정렬 컬렉션이 별도 comparator 없이 쓰고, equals와 일관되는 것이 "강하게 권장(필수는 아님)"이라고 한다. Comparator 문서는 정렬 메서드나 정렬 컬렉션에 넘겨 순서를 제어하며 자연 순서가 없는 객체에도 쓸 수 있다고 한다. Collections.sort 문서는 이 정렬이 안정(stable)임을 보장한다고 하고(Collections 개요는 알고리즘이 mergesort일 필요는 없지만 stable이어야 한다고 한다), Comparator 문서는 equals와 일관되지 않은 기준을 정렬 컬렉션에 쓰면 "strangely" 동작한다고 경고한다.
(실험 확인) 위 코드의 출력은 주석과 같았다. 나이만으로 정렬하면 b, a 순서가 유지되어 안정 정렬이었고, 자연 순서가 없는 객체를 `TreeSet`에 넣거나 `Collections.sort`하면 ClassCastException이 났다. 또 `(x, y) -> x - y`로 `[-1, Integer.MAX_VALUE]`를 정렬하니 `[2147483647, -1]`로 틀렸고(`Integer.MAX_VALUE - (-1) < 0`이 true인 오버플로), `Integer.compare`는 1을 돌려줬다.
(보충) 뺄셈으로 compare를 구현하지 말고 Integer.compare 같은 메서드를 쓰라는 것은 위 실험에 근거한 일반적인 권고이며 문서에 직접 적힌 규칙은 아니다.
