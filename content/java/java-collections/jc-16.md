**모범 답변 (30~60초)**
TreeSet과 TreeMap은 equals가 아니라 compareTo나 Comparator의 결과가 0이면 같은 요소로 취급합니다. 그래서 정렬 기준이 equals와 일관되지 않으면 Set과 Map의 일반 계약을 어기는 이상한 동작이 나옵니다. 대표 예가 BigDecimal로, 4.0과 4.00은 equals로는 다르지만 compareTo로는 0이라서 HashSet에는 둘 다 들어가도 TreeSet에는 하나만 들어갑니다. 반대로 equals는 같은데 Comparator가 0이 아니라고 하면 둘 다 들어갑니다. 그래서 정렬 기준에는 구분에 필요한 필드를 모두 넣거나 동점 처리 기준을 추가해야 합니다.

(공식 문서) TreeMap·TreeSet 문서는 정렬 순서가 equals와 일관되어야 Map/Set 인터페이스를 올바르게 구현하며, 일관되지 않아도 동작은 명확히 정의되지만 일반 계약은 지키지 못한다고 한다. Comparable 문서는 BigDecimal이 일관되지 않은 예외이고 `4.0`과 `4.00`이 그 예라고 하며, `!a.equals(b) && a.compareTo(b) == 0`인 두 요소를 넣으면 두 번째 add가 false를 돌려준다고 한다. Comparator 문서는 반대 경우(`a.equals(b)`이지만 compare가 0이 아님)에는 둘 다 들어간다고 한다.
(실험 확인) `new BigDecimal("4.0")`과 `"4.00"`을 넣으니 HashSet size 2, TreeSet size 1이었고(`equals` false, `compareTo` 0), `String.CASE_INSENSITIVE_ORDER`로 만든 TreeSet에 `"Apple"`과 `"apple"`을 넣으면 size 1에 `[Apple]`이었다.
