**모범 답변 (30~60초)**
LinkedHashMap을 access-order 생성자(세 번째 인자 true)로 만들면 순서가 삽입 순이 아니라 마지막 접근 순이 되어, 가장 오래 쓰지 않은 엔트리가 맨 앞에 옵니다. 여기에 removeEldestEntry를 오버라이드해 크기가 한도를 넘으면 true를 돌려주면 새 엔트리를 넣을 때 가장 오래된 엔트리가 자동 제거되어 LRU 캐시가 됩니다. 문서에 따라 put, get, getOrDefault, compute, merge 같은 메서드가 접근으로 취급됩니다. 이 클래스는 동기화되지 않으므로 여러 스레드에서 쓰려면 외부 동기화가 필요합니다.

```java
var lru = new LinkedHashMap<String, Integer>(16, 0.75f, true) {
    @Override protected boolean removeEldestEntry(Map.Entry<String, Integer> e) {
        return size() > 3;
    }
};
// a,b,c 삽입 → get("a") → d 삽입 ⇒ {c=3, a=1, d=4}
```

(공식 문서) LinkedHashMap 문서는 access-order 생성자가 LRU 캐시 구성에 적합하고, removeEldestEntry로 오래된 매핑을 자동 제거할 수 있으며, put·putIfAbsent·get·getOrDefault·compute·computeIfAbsent·computeIfPresent·merge가 접근으로 간주된다고 한다. 또 access-order 맵에서는 get만 해도 구조적 변경이며, 클래스가 동기화되지 않는다고 밝힌다.
(실험 확인) 위 코드의 출력은 주석과 같았다. access-order 맵에서 키 순회 중 `get`을 호출하면 ConcurrentModificationException이 났고, 삽입 순서 맵에서는 같은 코드가 정상이었다. access-order 맵에서 `getOrDefault`·`merge`는 해당 키를 맨 뒤로 옮겼고 `containsKey`·`entrySet` 순회는 순서를 바꾸지 않았다.
(보충) 운영 환경 캐시라면 크기 제한 외에 만료와 스레드 안전성이 필요해 전용 캐시 라이브러리가 흔히 쓰인다는 것은 일반적인 설명이며 문서로 확인하지 않았다.
