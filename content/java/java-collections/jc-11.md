**모범 답변 (30~60초)**
ArrayList나 HashMap 같은 범용 컬렉션의 이터레이터는 만들어진 뒤 컬렉션이 구조적으로 변경되면, 이터레이터 자신의 remove를 통한 경우를 빼고 ConcurrentModificationException을 던지는 fail-fast 방식입니다. 구조적 변경은 요소의 추가·삭제이고 기존 값 교체는 해당하지 않습니다. 단일 스레드에서 for-each 중에 list.remove를 호출해도 발생합니다. 다만 보장이 아니라 best-effort라서 이 예외에 의존한 로직을 짜면 안 되고 버그 탐지용으로만 봐야 합니다. 순회 중 삭제는 Iterator.remove나 removeIf를 쓰고, 동시 접근이 필요하면 CopyOnWriteArrayList 같은 동시성 컬렉션을 씁니다.

```java
for (Iterator<Integer> it = list.iterator(); it.hasNext();)
    if (it.next() % 2 == 0) it.remove();      // 안전
list.removeIf(i -> i % 2 == 0);                // 안전
```

(공식 문서) ConcurrentModificationException 문서는 단일 스레드가 순회 중 컬렉션을 직접 수정해도 발생하고, fail-fast는 best-effort이며 정확성을 이 예외에 맡기면 안 된다고 한다. ArrayList·HashMap 문서는 구조적 변경을 요소 추가·삭제로 정의하고 값만 바꾸는 set 등은 해당하지 않는다고 하며, Iterator.remove 문서는 순회 중 다른 방식의 변경 시 동작이 규정되지 않는다고 하며, Collection.removeIf 문서는 조건에 맞는 요소를 제거하고 기본 구현은 이터레이터의 remove로 지운다고 한다.
(실험 확인) `[1,2,3,4]`에서 for-each 중 첫 요소(1)를 remove하면 예외가 났지만, 끝에서 두 번째 요소(3)를 remove하면 예외 없이 끝나고 결과는 `[1, 2, 4]`였다(`hasNext()`가 false가 되어 순회가 조용히 끝남). 이것이 best-effort의 실례다. 순회 중 `add`는 예외, `Iterator.remove`와 `removeIf` 결과는 `[1, 3]`이었다. HashMap은 순회 중 새 키 put은 예외였고 이미 있는 키의 값 교체는 예외 없이 끝났다.
