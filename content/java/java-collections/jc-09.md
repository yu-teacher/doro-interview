**모범 답변 (30~60초)**
용량은 버킷 수, 로드 팩터는 테이블이 얼마나 차도 되는지의 기준이며, 엔트리 수가 둘의 곱을 넘으면 버킷이 두 배로 늘고 재해시됩니다. 기본값은 용량 16, 로드 팩터 0.75이고 문서는 시간과 공간 사이의 좋은 절충이라고 설명합니다. 저장할 개수를 대략 안다면 초기 용량을 예상 개수 나누기 로드 팩터보다 크게 잡아 리사이징을 아예 피할 수 있고, 반대로 너무 크게 잡으면 순회 비용이 버킷 수에 비례해 손해입니다. Java 19부터는 HashMap.newHashMap(예상 개수)이 이 계산을 대신해 줍니다.

```java
Map<String, Integer> m = HashMap.newHashMap(12); // Java 19+, 12개까지 리사이징 없음(아래 실험)
```

(공식 문서) HashMap 문서는 기본 로드 팩터 0.75가 시간·공간 절충으로 좋고, 초기 용량이 최대 엔트리 수를 로드 팩터로 나눈 값보다 크면 rehash가 일어나지 않으며, 용량을 너무 크게(또는 로드 팩터를 너무 낮게) 잡으면 순회 성능이 나빠진다고 한다. `newHashMap(int numMappings)`는 Since 19로, 기본 로드 팩터 0.75에서 예상 개수를 리사이징 없이 담을 만한 용량으로 만든다고 설명한다. 버전 차이: 18 이하에서는 `new HashMap<>((int) (n / 0.75f) + 1)` 같은 식을 직접 써야 했다.
(실험 확인) 리플렉션으로 본 테이블 길이(HotSpot 구현 관찰): `new HashMap<>(12)`에 12개를 넣어도 16, `HashMap.newHashMap(12)`도 12개 후 16, 기본 생성자는 13번째에서 32, `new HashMap<>(100)`은 첫 put 뒤 128이었다. `HashMap.newHashMap(n)`은 시험한 n(1, 6, 7, 12, 13, 24, 25, 100) 모두 n개를 넣는 동안 테이블이 커지지 않았고, `(int) (n / 0.75f) + 1` 식은 n=12에서 32로 더 크게 잡았다.
(보충) `new HashMap<>((int) (n / 0.75f) + 1)` 식은 문서의 "용량 > 최대 엔트리 / 로드 팩터" 문장을 코드로 옮긴 일반적인 관용구이며, 이 식 자체는 문서에 나오지 않는다.
