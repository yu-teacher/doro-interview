**모범 답변 (30~60초)**
Collections.synchronizedMap은 기존 맵의 메서드를 동기화하는 래퍼라서 개별 호출은 안전하지만, 순회할 때는 사용자가 직접 그 맵 객체에 synchronized를 걸어야 하고 그러지 않으면 동작이 비결정적일 수 있습니다. ConcurrentHashMap은 조회가 락 없이 갱신과 겹쳐 실행될 수 있고, 반복자는 ConcurrentModificationException을 던지지 않으며, null 키와 null 값을 허용하지 않습니다. 둘 다 get 다음 put 같은 복합 동작은 원자적이지 않으므로 merge나 compute 같은 원자 메서드를 써야 합니다. 동시 접근이 많으면 보통 ConcurrentHashMap을 씁니다.

(공식 문서) Collections.synchronizedMap은 반환 맵의 컬렉션 뷰를 이터레이터·스트림으로 순회할 때 반드시 그 맵에 수동 동기화해야 하고 어기면 비결정적 동작이 나올 수 있다고 한다. ConcurrentHashMap 문서는 조회가 일반적으로 블로킹하지 않고, 전체 테이블을 막는 잠금은 지원하지 않으며, 반복자는 생성 시점 이후의 어떤 상태를 반영하고 CME를 던지지 않고, size·isEmpty·containsValue는 동시 갱신 중이면 모니터링용 추정치일 뿐이며, null 키·값은 허용하지 않는다고 한다. merge는 전체가 원자적으로 수행된다고 한다.
(실험 확인) 스레드 4개가 각각 50,000번 카운터를 올렸을 때(기대값 200,000), `synchronizedMap`의 get+put은 63,040~68,216, `ConcurrentHashMap`의 get+put은 71,578~73,380으로 갱신이 유실됐고(2회 실행, 값은 실행마다 다름), 두 맵 모두 `merge`는 정확히 200,000이었다. ConcurrentHashMap은 순회 중 새 키를 put해도 예외가 없었고(synchronizedMap으로 감싼 HashMap은 같은 코드에서 ConcurrentModificationException), `put(key, null)`·`put(null, 1)`·`get(null)` 모두 NullPointerException이었다.
(보충) `synchronizedMap`의 merge가 원자적이라는 점은 위 실험으로만 확인했으며 문서에서 직접 확인하지 않았다. 또 "동시 접근이 많으면 ConcurrentHashMap"이라는 선택 기준은 일반적인 권고다.
