**모범 답변 (30~60초)**
아닙니다. PriorityQueue는 우선순위 힙 기반이라 poll이나 peek이 돌려주는 head만 자연 순서나 Comparator 기준으로 가장 작은 요소임이 보장되고, iterator와 toString 같은 순회 결과는 특정 순서로 나온다고 보장되지 않습니다. 정렬된 순서가 필요하면 poll을 반복해서 꺼내거나, 문서가 제시한 대로 Arrays.sort(pq.toArray())로 정렬합니다. 동점 요소 중 어느 것이 head가 되는지도 임의입니다. offer와 poll은 O(log n)이고 remove(Object)와 contains는 선형 시간이며, null은 넣을 수 없습니다.

(공식 문서) PriorityQueue 문서는 head가 가장 작은 요소이고 동점은 임의로 깨지며, Iterator와 Spliterator가 특정 순서의 순회를 보장하지 않으므로 순서가 필요하면 `Arrays.sort(pq.toArray())`를 고려하라고 한다. null 요소와, 자연 순서를 쓸 때 비교 불가능한 객체(ClassCastException 가능)는 허용하지 않고, 구현 노트로 enqueue/dequeue는 O(log n), remove(Object)·contains는 선형, peek·size는 상수 시간이라고 한다. toString은 AbstractCollection에서 물려받으며, 그 문서는 이터레이터가 돌려주는 순서대로 요소를 나열한다고 하므로 toString 순서도 이터레이터 순서를 따른다.
(실험 확인) `new PriorityQueue<>(List.of(5,1,4,2,3))`의 `toString()`은 `[1, 2, 4, 5, 3]`으로 정렬 상태가 아니었고, `poll()`을 반복한 순서는 `1 2 3 4 5`였다. `add(null)`은 NullPointerException이었다. 이 `toString` 순서는 이 실행에서 관찰한 결과일 뿐 보장된 형태가 아니다.
