**모범 답변 (30~60초)**
키의 hashCode로 버킷을 정하고, 해시가 겹쳐 한 버킷에 엔트리가 여러 개 들어가면 그 안에서 equals로 찾습니다. 엔트리 수가 로드 팩터(기본 0.75)와 현재 용량의 곱을 넘으면 버킷 수를 약 두 배로 늘리며 다시 해시하는 리사이징이 일어납니다. 충돌이 심하면 Java 8부터는 JEP 180에 따라 한 버킷이 연결 리스트 대신 균형 트리로 바뀌어 최악 성능이 O(n)에서 O(log n)으로 개선되고, API 문서는 키가 Comparable이면 비교 순서로 충돌 영향을 줄일 수 있다고 합니다. 트리화 임계값 같은 세부는 문서에 명시되어 있지 않습니다.

(공식 문서) HashMap 문서는 해시가 버킷에 고르게 퍼진다는 가정에서 get·put이 상수 시간이고, 로드 팩터를 넘으면 rehash로 버킷 수가 대략 두 배가 되며, 같은 hashCode를 가진 키가 많으면 성능이 떨어지고 키가 Comparable이면 비교 순서를 쓸 수 있다고 한다. JEP 180(Java 8, 구현 변경)은 버킷의 항목이 임계값을 넘으면 연결 리스트에서 균형 트리로 바꿔 최악 성능을 O(n)에서 O(log n)으로 개선하며 이 효과는 Comparable을 구현한 키에 대한 것이라고 설명하고, 이 개선을 LinkedHashMap에도 적용하며 Hashtable과 WeakHashMap에는 적용하지 않는다고 한다. 버전 차이: 7 이하에서는 충돌 버킷이 연결 리스트뿐이었고 8부터 트리화가 들어갔다.
(실험 확인) 아래는 OpenJDK 계열(HotSpot, Corretto 25.0.3)에서 `HashMap.table` 길이를 리플렉션(`--add-opens`)으로 본 결과로, 구현 의존 관찰이다. 생성 직후 0(지연 할당), 첫 put 뒤 16, 12개까지 16, 13번째 put에서 32였다. 또 모든 키의 hashCode를 1로 고정하고 20,000개를 넣고 읽는 데 Comparable이 아닌 키는 약 0.87~0.95초, Comparable인 키는 3~21ms였다(2회 측정). 기본 생성자 맵은 13번째 put에서 32, 25번째에서 64, 49번째에서 128로 두 배씩 늘었다.
