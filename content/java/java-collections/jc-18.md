**모범 답변 (30~60초)**
계산 함수 안에서 같은 맵을 수정하면 안 됩니다. HashMap 문서는 매핑 함수가 계산 중에 이 맵을 수정하면 안 되고, 감지하면 best-effort로 ConcurrentModificationException을 던진다고 합니다. ConcurrentHashMap도 계산 중에 같은 맵을 갱신해선 안 되며, 끝나지 않을 재귀 갱신을 감지하면 IllegalStateException을 던진다고 합니다. 그래서 computeIfAbsent 안에서 자기 자신을 재귀 호출하는 메모이제이션은 HashMap에서는 CME로 실패하고, ConcurrentHashMap은 입력에 따라 예외가 나거나 우연히 끝나기도 해서 믿을 수 없습니다. 이 경우 get으로 확인하고 계산한 뒤 put하는 방식으로 나눠 씁니다.

```java
static long fib(Map<Integer, Long> m, int n) {          // HashMap: n>=3이면 CME, ConcurrentHashMap: n=20에서 IllegalStateException(작은 n은 통과)
    if (n < 2) return n;
    return m.computeIfAbsent(n, k -> fib(m, k - 1) + fib(m, k - 2));
}
static long fib2(Map<Integer, Long> m, int n) {         // 안전: 계산과 put 분리
    if (n < 2) return n;
    Long c = m.get(n); if (c != null) return c;
    long r = fib2(m, n - 1) + fib2(m, n - 2); m.put(n, r); return r;
}
```

(공식 문서) HashMap의 computeIfAbsent·computeIfPresent·compute·merge 문서가 "should not modify this map during computation"과 CME를 best-effort로 던진다는 점을, ConcurrentHashMap의 computeIfAbsent 문서가 `IllegalStateException`(감지 가능한 재귀 갱신)과 계산은 짧고 단순해야 하며 같은 맵의 다른 매핑을 갱신하면 안 된다는 점을 근거로 한다. HashMap 문서의 사용 예시에는 `map.computeIfAbsent(key, k -> new HashSet<V>()).add(v)`처럼 값만 만드는 용도가 실려 있다.
(실험 확인) 스레드 하나에서 `fib(…, n)`을 돌렸다. HashMap(TreeMap, LinkedHashMap도 같음)은 n=1, 2에서는 맵을 건드리지 않아 정상이었고 n=3부터 n=30까지 모두 ConcurrentModificationException이었다. ConcurrentHashMap은 n=3~10에서는 예외 없이 정상 값(n=10은 55)을 돌려줬고 n=20, 30에서 IllegalStateException이었다. `get`/`put` 방식(`fib2`)은 n=20에서 두 맵 모두 6765를 돌려줬다(Java 25). HashMap에서 매핑 함수 안에 다른 키를 put하면 CME, 이미 있는 키의 값만 바꾸면 예외 없이 끝났다(구현 관찰이며 문서는 "수정하지 말라"까지만 말한다). 문서가 "감지할 수 있을 때"만이라고 하므로 이 예외가 항상 나는 것은 아니다.
(보충) 계산과 put을 나누는 우회는 일반적인 권고이며 문서가 제시한 것은 아니다. 나눈 방식은 같은 키를 여러 스레드가 동시에 계산하면 중복 계산이 생길 수 있어 동시 환경에서는 별도 고려가 필요하다는 점도 일반적인 설명이다.
