**모범 답변 (30~60초)**
리소스 오너는 보호된 자원에 대한 접근을 허락할 수 있는 주체로 사람이면 최종 사용자이고, 리소스 서버는 그 자원을 가진 API 서버로 액세스 토큰을 받아 응답합니다. 클라이언트는 리소스 오너를 대신해 자원을 요청하는 애플리케이션이고, 인가 서버는 리소스 오너를 인증하고 동의를 받은 뒤 클라이언트에 액세스 토큰을 발급합니다. 핵심은 사용자가 자기 비밀번호를 클라이언트에 주지 않고도 토큰으로 범위와 기간이 제한된 접근만 위임한다는 점입니다. 여기서 클라이언트는 서버 앱일 수도 있어서, 브라우저 쪽 앱만 뜻하는 말은 아닙니다.

(공식 문서) RFC 6749 1.1은 리소스 오너, 리소스 서버, 클라이언트, 인가 서버 네 역할을 정의한다. 클라이언트라는 용어는 서버, 데스크톱 등 특정 구현 방식을 뜻하지 않는다고 하고, 인가 서버와 리소스 서버는 같은 서버일 수도 별개일 수도 있으며 둘 사이의 상호작용은 사양의 범위 밖이라고 한다. 1.2는 클라이언트가 인가 승인을 받아 액세스 토큰을 얻고 그 토큰으로 리소스 서버에 요청하는 추상 흐름을 보여 준다.
(공식 문서) RFC 6749 1은 전통적 클라이언트-서버 모델에서 서드파티에 자격 증명을 공유하면 서드파티가 비밀번호를 저장해야 하고 접근 범위·기간을 제한할 수 없다는 등의 문제가 생긴다고 한다. OAuth는 클라이언트와 리소스 오너의 역할을 분리하고, 클라이언트가 특정 스코프와 수명 등을 나타내는 문자열인 액세스 토큰으로 접근하게 해 이를 해결한다고 설명한다.
