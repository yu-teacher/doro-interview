**모범 답변 (30~60초)**
SSRF는 서버가 사용자가 준 URL을 검증 없이 가져오는 기능을 악용해, 방화벽 안쪽의 내부 서비스나 클라우드 메타데이터 같은 의도하지 않은 곳으로 서버가 요청을 보내게 만드는 공격입니다. 방어는 애플리케이션과 네트워크 양쪽에서 겹쳐 합니다. 가능하면 스킴·호스트·포트를 허용 목록으로 제한하고, 리다이렉트를 따라가지 않고, 원본 응답을 그대로 사용자에게 돌려주지 않습니다. 웹훅처럼 목적지를 미리 알 수 없어 허용 목록을 쓸 수 없는 경우에는 해석한 IP가 내부·루프백·링크 로컬 주소가 아닌지 확인하고 검증한 IP로만 연결해야 하고, 검사만 따로 하면 DNS 재바인딩을 막지 못합니다. 네트워크 쪽은 기본 거부 방화벽과 분리로 피해를 줄입니다.

```
127.0.0.1        loopback=True  private=True
169.254.169.254  link_local=True  private=True     (클라우드 메타데이터 주소로 알려진 대역)
8.8.8.8          global=True
2130706433 : ipaddress 모듈은 거부, inet_aton 은 127.0.0.1 로 해석
```

(원저자 자료) OWASP Top 10:2021 A10 페이지는 SSRF를 사용자 제공 URL을 검증하지 않고 원격 자원을 가져올 때 생기며 방화벽·VPN·ACL 뒤에서도 공격자가 조작한 요청을 보내게 만든다고 설명한다. 예방으로는 네트워크 분리와 기본 거부 방화벽, 입력 검증, 스킴·포트·목적지의 긍정 허용 목록, 원본 응답 비전달, 리다이렉트 비활성화, DNS 재바인딩과 검사 시점-사용 시점 경쟁에 대한 주의를 들고, 차단 목록이나 정규식으로 막으려 하지 말라고 한다.
(원저자 자료) SSRF Prevention Cheat Sheet는 허용 목록을 쓸 수 있는 경우와 아무 외부 주소로나 요청해야 하는 경우를 나눈다. 두 번째 경우에는 허용 목록을 쓸 수 없으므로 차단 목록이 이 상황의 최선책이지만 완벽한 방어는 아니라고 하면서(별도 절은 차단 목록을 최후 수단이라 부르며 우회되기 쉬우니 허용 목록을 우선하라고 한다), 해석한 모든 IP(A, AAAA)가 공개 주소인지 확인하고 검증한 IP로만 연결하며 리다이렉트 지원을 끄라고 한다. 도메인 허용 목록만으로는 DNS 재바인딩을 막지 못한다고 하고, 클라우드 메타데이터 서비스(AWS IMDS 등)가 SSRF의 표적이 되므로 IMDSv2 전환을 권고한다. IP 파서 라이브러리가 16진·8진·정수 표기 우회에 노출되는지 점검한 결과도 싣는다.
(실험 확인) Python 3.14 `ipaddress`로 리터럴 IP를 분류하고, `socket.inet_aton`이 정수·16진·8진 표기를 받아들이는 반면 `ipaddress`는 거부함을 확인했다. 순수 파싱이며 네트워크 접속은 하지 않았다. Top 10 A10 페이지는 차단 목록에 기대지 말라고 하고 치트 시트는 허용 목록을 쓸 수 없을 때의 차선으로 두므로 두 자료의 강도가 다르다. 실험은 파서마다 해석이 다르다는 사실만 보인 것이고 방어 코드의 완전성을 확인한 것은 아니다.
