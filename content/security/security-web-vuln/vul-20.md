**모범 답변 (30~60초)**
로그인 성공과 실패, 접근 제어 실패, 서버 쪽 입력 검증 실패, 고가치 거래 같은 감사 대상 이벤트는 사용자 맥락과 함께 남기고, 남기기만 하지 말고 의심스러운 패턴을 모니터링해서 알림까지 이어지게 해야 합니다. 반대로 비밀번호, 세션 ID, 액세스 토큰, 암호화 키, 카드 정보 같은 값은 일반적으로 로그에 직접 남기지 말고 제거하거나 마스킹하거나 해시해야 합니다. 로그 인젝션은 입력에 줄바꿈이 섞여 다른 사용자가 한 것처럼 보이는 로그 줄이 위조되는 문제여서, 줄바꿈을 이스케이프하는 JSON 같은 구조화 로그를 쓰는 편이 안전합니다. 사용자 입력의 길이도 제한합니다.

```
INFO login failed user=bob
INFO login success user=admin                      (입력에 섞인 줄바꿈 때문에 가짜 줄이 생김)
INFO login failed user=bob\nINFO login success user=admin   (줄바꿈을 이스케이프한 경우)
```

(원저자 자료) OWASP Top 10:2021 A09 페이지는 로그인·실패한 로그인·고가치 거래 같은 감사 대상 이벤트를 남기지 않는 것, 로그를 모니터링하지 않는 것, 로그를 로컬에만 두는 것, 알림 임계값과 대응 절차가 없는 것을 문제로 든다. 로그 데이터를 제대로 인코딩하지 않으면 로깅·모니터링 시스템에 대한 인젝션이 가능하다고 하고, 예방으로 충분한 사용자 맥락과 보관 기간, 소비하기 쉬운 형식, 올바른 인코딩, 고가치 거래의 변조 방지 감사 추적을 든다.
(원저자 자료) OWASP Logging Cheat Sheet는 인증 성공과 실패, 입력 검증 실패 등을 남길 이벤트로 들고, 세션 식별 값, 액세스 토큰, 인증 비밀번호, 암호화 키, 카드 정보 등은 로그에 직접 남기지 말고 제거·마스킹·해시·암호화하라고 한다. 로그 인젝션은 신뢰할 수 없는 데이터가 로그 메시지에 들어가 CRLF로 다른 사용자의 것처럼 보이는 항목이 추가되는 공격이라고 하며, 비구조적 텍스트 로그를 피하고 JSON 같은 구조화 형식을 쓰고 입력 크기를 제한하라고 한다. 자바에서는 문자열 연결 대신 파라미터 로깅을 쓰되 파라미터 로깅만으로는 CR/LF 인젝션을 막지 못하므로 값을 올바로 이스케이프하는 구조화 인코더를 쓰라고 한다.
(실험 확인) Python 3.14 `logging`으로 줄바꿈이 든 사용자 입력을 그대로 기록하면 가짜 로그 줄이 생기고, CR/LF를 이스케이프하면 한 줄로 남는 것을 확인했다. 위조한 줄은 개념을 보이기 위한 무해한 예이고 특정 로그 시스템에서의 영향을 확인한 것은 아니다.
