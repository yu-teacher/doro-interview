**모범 답변 (30~60초)**
AIP-158은 페이지 토큰을 URL 안전하지만 사용자가 해석할 수 없는 불투명 문자열로 만들라고 합니다. 사용자가 분해하기 시작하면 내부 구현이 API의 일부가 돼 바꿀 때 호환성이 깨지기 때문이고, Base64 인코딩만으로는 충분한 가림막이 아니라고 경고합니다. 토큰은 어디서 이어 읽을지만 알려야 하고 권한을 주면 안 되므로 토큰이 있어도 요청마다 인가를 확인해야 합니다. Microsoft 가이드라인은 페이징이 안정된 정렬 순서를 전제로 하니 정렬 기준에 키를 덧붙여 항상 같은 순서가 되게 하라고 합니다. 정렬 값이 같은 항목이 많으면 마지막 값만 기준으로 삼을 때 일부를 건너뛰기 때문에 `id` 같은 유일한 값을 함께 씁니다.

(공식 문서) AIP-158 Opacity 절은 토큰이 불투명하고 사용자가 해석할 수 없어야(must) 하며 Base64만으로는 부족하다고 경고하고, 토큰은 이어 읽을 위치만 나타내야 하고 어떤 형태의 권한도 주면 안 되며 인가는 토큰 유무와 상관없이 요청마다 해야 한다고 한다. Microsoft 가이드라인 9.8.3은 두 방식 모두 항목의 안정된 순서가 전제이고, 서버가 지정된 정렬에 키 같은 추가 정렬을 덧붙여 항상 일관된 순서를 보장해야 하며(MUST), 마지막으로 읽은 레코드 ID를 인코딩하는 것을 권고(SHOULD)한다고 한다.
(실험 확인) Node 24 메모리 모형에서 `t`가 같은 항목 4개(id 1~4)를 `t`로만 정렬해 2개씩 읽을 때, 1페이지 `[4, 3]` 뒤에 `t`가 더 작은 항목만 찾았더니 다음 페이지가 `[5]`가 돼 id 2, 1이 건너뛰어졌다. `(t, id)` 쌍을 기준으로 하면 `[2, 1]`이 나왔다. 또 `{"lastId":8}`을 Base64url로 만든 토큰은 누구나 해독할 수 있었고, HMAC-SHA256 서명을 붙인 토큰은 값을 바꾸면 검증에 실패했다.
(보충) 서명으로 토큰 변조를 막는 방법은 일반적인 설계이며 AIP-158이 이 방식을 지시한 것은 아니다. 정렬 값이 같을 때 일부를 건너뛰는 이유도 문서가 설명한 것이 아니라 위 실험 모형으로 확인한 것이고, 문서는 정렬에 키 같은 추가 정렬을 덧붙이라는 데까지만 말한다.
