**모범 답변 (30~60초)**
오프셋은 앞에서 n개를 건너뛴 다음부터라는 개수로 위치를 정하기 때문입니다. 1페이지를 받은 뒤 앞쪽에 새 항목이 들어오면 전체가 한 칸씩 뒤로 밀려 2페이지 첫 항목이 1페이지 마지막 항목과 같아져 중복되고, 이미 본 앞쪽 항목이 삭제되면 한 칸씩 당겨져 항목 하나가 건너뛰어집니다. 커서 방식은 마지막으로 본 항목 다음부터라는 식으로 항목 자체를 기준으로 삼기 때문에 앞쪽의 변경에 영향을 덜 받는 편입니다. 다만 완전한 보장은 아닙니다. Microsoft 가이드라인은 서버가 순서를 일관되게 강제해도 생성·삭제로 결과가 빠지거나 반복될 수 있어 클라이언트가 대비해야 한다고 명시하는데, 이는 서버 주도 토큰 방식도 다루는 같은 절의 내용입니다.

(공식 문서) Microsoft 가이드라인(폐기 표시가 붙은 판) 9.8.3은 클라이언트 주도(`$top`·`$skip`)와 서버 주도(연속 토큰) 페이징 모두 안정된 순서가 전제라고 하고, 이어서 서버가 일관된 정렬을 강제해도 다른 리소스의 생성·삭제로 결과가 빠지거나 반복될 수 있으며 클라이언트가 이런 불일치를 처리할 준비를 해야 한다고 한다. 서버가 마지막으로 읽은 레코드의 ID를 인코딩하는 것을 권고(SHOULD)한다. AIP-158은 페이지 토큰이 이어 읽을 위치를 나타낸다고 한다.
(보충) 오프셋이 밀리는 원리와 키셋 방식이 앞쪽 변경에 덜 흔들리는 이유는 문서가 그렇게 설명한 것이 아니라 일반적인 설명이며, 아래 실험 모형으로 확인한 범위에서만 말한다.
(실험 확인) Node 24 메모리 모형에서 id 12~1을 5개씩 읽었다. 1페이지 `[12, 11, 10, 9, 8]` 뒤에 새 항목 13이 앞에 들어오자 오프셋 2페이지는 `[8, 7, 6, 5, 4]`로 8이 중복됐고, 마지막 id 8보다 작은 것을 읽는 키셋 방식은 `[7, 6, 5, 4, 3]`으로 중복이 없었다. 반대로 1페이지 뒤에 이미 본 11이 삭제되자 오프셋 2페이지는 `[6, 5, 4, 3, 2]`로 7이 빠졌고 키셋은 `[7, 6, 5, 4, 3]`으로 빠진 것이 없었다. 실제 DB가 아닌 배열 모형이며 동시 수정이 중간에 끼어드는 모든 경우를 보인 것은 아니다.
