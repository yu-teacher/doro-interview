**모범 답변 (30~60초)**
필드를 더하는 일은 보통 호환되지만, 페이징은 동작 자체를 바꾸기 때문입니다. 컬렉션에 75건이 있고 클라이언트가 전부 한 번에 받는 코드를 이미 배포했다고 합시다. 나중에 기본 페이지 크기를 50으로 넣으면 이 코드는 앞의 50건만 받고 다음 페이지를 가져와야 한다는 사실도 모릅니다. 기본 크기를 100으로 높여도 컬렉션이 커지면 같은 문제가 생깁니다. 또 자동 페이지네이션을 지원하는 클라이언트 라이브러리는 페이징 메서드를 다른 시그니처로 만들기 때문에 그쪽도 깨집니다. 그래서 AIP-158은 처음부터 페이징 필드를 두고 무한이 아닌 기본값을 실제로 구현하라고 하며, Azure 가이드라인도 나중에 추가하면 깨지는 변경이라고 경고합니다.

(공식 문서) AIP-158은 컬렉션을 반환하는 RPC는 처음부터 페이징을 제공해야 하며 기존 메서드에 페이징을 추가하는 것은 하위 호환이 깨지는 변경이라고 한다. 이유로 75건짜리 컬렉션 예시와, 클라이언트 라이브러리가 자동 페이지네이션을 위해 페이징 메서드를 다른 시그니처로 표현한다는 점을 든다. 필드를 보여 주는 것만으로는 안 되고 무한이 아닌 기본값으로 실제 구현해야 하며, 초기에 작은 컬렉션이라면 전부 가져온 뒤 메모리에서 나누는 구현도 합리적이라고 한다. Azure 가이드라인은 컬렉션이 커질 가능성이 조금이라도 있으면 페이징을 지원하라(SHOULD)고 하고, 나중에 페이징을 추가하는 것은 깨지는 변경이라고 적는다.
(실험하지 않았다) 문서 근거만으로 적었다.
