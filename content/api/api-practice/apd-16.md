**모범 답변 (30~60초)**
대체로 호환으로 보지만 조건이 붙습니다. AIP-180은 새 메서드나 필드를 같은 메이저 버전에 더하는 것을 허용하면서도, 이전 표면만 아는 코드가 전과 똑같이 취급돼야 한다고 합니다. 특히 응답에 쓰이는 enum은 새 값이 추가될 수 있음을 문서에 적고, 클라이언트 코드가 새 값을 잘 처리하지 못할 수 있으니 조심하라고 합니다. Microsoft 가이드라인은 서비스가 호환성의 정의를 스스로 문서화해야 한다며, Azure는 응답에 JSON 필드를 추가하는 것도 하위 호환이 아니라고 정의하고 Office 365는 허용한다고 소개합니다. 또 응답에 필드를 더하는 서비스는 이를 문서에 밝혀야 하고 클라이언트는 모르는 필드를 무시해야 한다고 정합니다. enum 값도 같은 태도로 모르는 값을 견디게 쓰는 편이 안전합니다.

(공식 문서) AIP-180은 새 구성요소(필드, enum 값 등)를 같은 메이저 버전에 추가할 수 있다(may)고 하되, 이전 표면을 모르는 코드가 계속 같은 취급을 받아야 한다고 한다. 요청에만 쓰는 enum에는 값을 자유롭게 더할 수 있고, 응답이나 리소스에 쓰이면서 새 값이 생길 것으로 예상되는 enum은 이를 문서화해야 하며(should) 값은 더할 수 있으나 적절한 주의가 필요하다고 한다. Microsoft 가이드라인 12.3은 호환성을 팀이 비즈니스 필요에 따라 정의할 수 있다며 Azure는 응답 JSON 필드 추가를 하위 호환이 아닌 것으로, Office 365는 더 느슨하게 허용한다고 적고, 서비스가 이를 명시적으로 정의해야 한다고 한다.
Microsoft 가이드라인 6.1은 서비스가 버전 번호를 올리지 않고 응답에 필드를 더할 수 있으며, 그 경우 문서에 분명히 밝혀야 하고 클라이언트는 알 수 없는 필드를 무시해야(MUST) 한다고 한다.
(보충) 모르는 enum 값도 견디게 클라이언트를 쓰라는 조언은 AIP-180의 주의 문구와 위 무시 규칙에서 이끌어낸 일반적인 설명이며 문서가 enum에 대해 직접 그렇게 말한 것은 아니다.
(실험 확인) Node 24 모형에서 v1 스키마만 아는 엄격한 클라이언트는 응답에 `note` 필드가 늘자 `unknown field` 오류를, 새 enum 값 `ARCHIVED`에는 `unknown enum` 오류를 냈고, 모르는 값을 `UNKNOWN`으로 받아 넘기는 관대한 클라이언트는 둘 다 처리했다. 이는 내가 만든 모형이며 특정 JSON 라이브러리의 기본 동작을 확인한 것은 아니다.
