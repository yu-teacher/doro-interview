**모범 답변 (30~60초)**
클라이언트가 쿼리 모양을 정하기 때문에 순환하는 깊은 중첩, 별칭으로 부풀린 요청, 배치 요청이 서비스 거부 공격이 될 수 있습니다. 공식 보안 가이드는 여러 겹의 방어를 제안합니다. 첫째 목록 필드는 페이지네이션으로 최대 개수를 제한하고, 둘째 연산의 깊이와 넓이(최상위 필드·별칭·배치 개수)를 제한합니다. 셋째 필드에 가중치를 매겨 비용을 추정하는 쿼리 복잡도 분석을 하고, 넷째 요청 수만 세는 네트워크 계층보다 비즈니스 로직 계층의 속도 제한을 권장합니다. 자사 클라이언트만 쓰는 API라면 신뢰하는 문서만 허용하는 방식도 있습니다.

(공식 문서) Security 페이지의 Demand control 절이 위 방어를 설명한다. 허용 목록 방식인 trusted documents는 자사 클라이언트만 쓰는 API에 맞고 공개 API에는 쓸 수 없다고 한다. 목록 필드는 페이지네이션해 한 번에 반환되는 개수를 제한하고, 깊이 제한은 실행 전에 오류로 거부하며 목록 중첩에는 더 작은 별도 한도를 권장한다. 필드 별칭 수와 배치된 연산 수에도 상한이 필요하다고 한다. 깊이·넓이·배치 제한은 특정 필드가 계산상 비싸다는 것을 표현하지 못하고, 클라이언트가 필드를 고르므로 서버가 사전에 부하를 알기 어려워 요청 수만 세는 네트워크 계층 대신 비즈니스 로직 계층의 속도 제한이 일반적으로 권장된다고 한다. 복잡도 분석은 스키마에 가중치를 부여해 비용을 추정한다고 한다.
(공식 문서) Performance 페이지도 페이지네이션, 깊이·넓이 제한, 속도 제한이 한 연산이 서버 자원에 과부하를 주는 것을 막는다고 요약한다. Security 페이지는 전문을 읽었고 권장 한계 수치 없이 원칙만 서술한다. 실제 서버에 적용해 보는 실험은 하지 않았다.
