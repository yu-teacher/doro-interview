**모범 답변 (30~60초)**
무상태는 서버가 요청과 요청 사이에 클라이언트의 대화 맥락을 저장해 두고 쓰지 않는다는 제약입니다. 그래서 각 요청에 그 요청을 이해하는 데 필요한 정보가 모두 들어 있어야 하고, 세션 상태는 클라이언트가 가집니다. Fielding은 이로써 가시성, 신뢰성, 확장성이 좋아지지만 요청마다 반복 데이터가 늘고 서버의 통제력이 줄어드는 비용이 있다고 설명합니다. 서버 저장소에서 세션을 찾아 쓰는 쿠키 로그인은 논문 6장이 REST 모델에 맞지 않는다고 평가한 방식입니다. 반대로 요청마다 `Authorization` 헤더에 자격 증명을 실어 보내면 이 정의에 더 가깝습니다.

(원저자 자료) 논문 5.1.3은 각 요청이 서버에 저장된 맥락 없이 이해될 수 있는 모든 정보를 담아야 하고 세션 상태는 전적으로 클라이언트가 가진다고 한다. 이 제약이 가시성(모니터링이 한 요청만 보면 됨), 신뢰성(부분 실패 복구가 쉬움), 확장성(서버가 요청 사이에 자원을 쥐지 않음)을 높이는 대신, 반복 데이터로 네트워크 성능이 떨어지고 클라이언트 구현에 일관성이 좌우되어 서버의 통제력이 줄어드는 트레이드오프가 있다고 쓴다. 5.2.2는 이 제약의 기능을 네 가지로 든다. 커넥터가 요청 사이에 애플리케이션 상태를 쥘 필요가 없고, 요청을 병렬로 처리할 수 있고, 중개자가 요청을 단독으로 이해할 수 있고, 캐시 재사용 여부에 영향을 주는 정보가 모든 요청에 들어 있게 된다는 것이다. 6.3.4.2는 사이트 전체에 붙는 HTTP 쿠키가 브라우저의 실제 애플리케이션 상태와 어긋날 수 있고(뒤로 가기 이후 쿠키가 현재 맥락을 잘못 나타냄) 의미를 충분히 식별하지 않은 채 데이터를 전달하므로 REST에 어긋난다고 평가한다. 이는 저자의 평가이다.
(원저자 자료) Google AIP-121도 리소스 지향 API가 상태 없는 프로토콜 위에서 동작해야 한다고 하고, 개별 요청의 기본 동작이 다른 요청과 독립적이며 서버는 여러 클라이언트가 공유할 수 있는 데이터의 영속화를, 클라이언트는 애플리케이션 상태 유지를 맡는다고 설명한다.
(보충) 요청마다 `Authorization`에 자격 증명을 싣는 방식이 더 가깝다는 것은 논문이 직접 한 말이 아니라 위 정의에서 이끌어 낸 해석이다. 토큰을 검증할 때마다 서버가 저장소를 조회하면 그 부분은 다시 서버 상태에 기대므로 상황에 따라 판단해야 한다. 실제 서비스가 이 제약을 얼마나 엄격히 따르는지는 읽은 자료에서 확인하지 못했다. 이 질문은 개념 설명이라 실험하지 않았다.
