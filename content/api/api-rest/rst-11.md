**모범 답변 (30~60초)**
400은 요청 문법이 깨졌거나 프레이밍이 잘못되는 등 클라이언트 오류로 서버가 처리할 수 없을 때 넓게 쓰는 코드입니다. 422는 내용 형식과 문법은 맞는데 담긴 지시를 처리할 수 없을 때 쓰고, RFC 9457의 유효성 검증 오류 예시도 422를 씁니다. 반면 Microsoft Graph 가이드의 필수 필드 누락 예시는 400에 해당하는 `badRequest`를 씁니다. 409는 이미 있는 값과 겹치는 중복 생성처럼 대상 리소스의 현재 상태와 충돌해 사용자가 해결하고 다시 보낼 수 있을 때, 412는 `If-Match` 같은 조건 헤더가 거짓일 때 씁니다. 400과 422 중 무엇을 택하든 팀 안에서 일관되게 정하는 것이 중요합니다.

(공식 문서) RFC 9110 15.5.1은 400을 서버가 클라이언트 오류로 인식되는 것(잘못된 요청 구문, 잘못된 메시지 프레이밍, 기만적인 요청 라우팅 등) 때문에 처리할 수 없거나 처리하지 않겠다는 뜻으로 정의한다. 15.5.21은 422를 서버가 요청 내용의 미디어 타입을 이해하고 구문도 맞지만 담긴 지시를 처리하지 못한다는 뜻으로 정의하고, 그래서 415가 부적절한 경우라고 한다. 15.5.10은 409를 대상 리소스의 현재 상태와의 충돌로 요청을 완료할 수 없고 사용자가 충돌을 해결해 다시 보낼 수 있는 상황에 쓰며 충돌 원인을 알아볼 정보를 담으라고 하고, 버전 관리 중인 리소스에 대한 PUT이 앞선 변경과 충돌하는 예를 든다. 15.5.13은 412를 요청 헤더의 조건이 서버에서 거짓으로 평가됐다는 뜻으로 정의한다.
(공식 문서) RFC 9457 3절의 유효성 오류 예시는 422와 `errors` 확장 멤버를 쓴다.
(원저자 자료) Microsoft Graph REST API Guidelines의 오류 처리 절은 최상위 `code`가 HTTP 상태 설명을 camelCase로 바꾼 것과 일치해야 한다고 하고, 필수 필드 누락 예시에 `badRequest`와 `innererror`의 세부 코드를 쓴다. 같은 절은 권한이 부족하면 403, 제한 초과면 429를 쓰라고 한다.
(보충) 중복 생성에 409를 쓰는 것은 RFC 9110 15.5.10 본문이 든 예시가 아니라 일반적인 관행이다. 400과 422 사이는 표준이 하나로 정하지 않아 가이드라인마다 다르다는 정리는 위 두 자료를 비교한 것이다. 이 질문은 문서 근거만 사용했고 실험하지 않았다.
