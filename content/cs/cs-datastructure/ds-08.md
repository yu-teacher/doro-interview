**모범 답변 (30~60초)**
amortized O(1)은 add 한 번이 항상 O(1)이라는 뜻이 아니라, n번 연달아 추가했을 때 전체 비용이 O(n)이어서 한 번당 평균이 상수라는 뜻입니다. 용량이 가득 차면 더 큰 배열을 새로 만들어 복사하느라 그 한 번은 O(n)이 들지만, 용량을 일정 비율로 키우면 그런 비싼 연산이 드물게만 일어나 비용이 전체로 분산됩니다. Java 문서는 add가 amortized 상수 시간이라고 하되 성장 정책 자체는 규정하지 않습니다. 개수를 미리 안다면 ensureCapacity로 재할당 횟수를 줄일 수 있습니다.

(공식 문서) NIST DADS는 amortized cost를 "n개 연산으로 이루어진 모든 열의 최악 실행 시간이 O(n·f(n))을 넘지 않을 때 O(f(n))"이라고 정의한다. Java `ArrayList` 문서는 `add`·`addLast`가 amortized 상수 시간이며 n개 추가에 O(n)이 걸린다고 하고, 성장 정책의 세부는 "amortized 상수 시간"이라는 점 외에는 규정하지 않으며 대량 추가 전 `ensureCapacity`로 재할당을 줄일 수 있다고 한다. C++ 표준 초안도 `vector`가 끝에서의 삽입·삭제를 (amortized) 상수 시간에 지원한다고 적는다.
(실험 확인) 파이썬으로 용량이 가득 차면 두 배로 키우는 배열을 시뮬레이션했더니 원소 100만 개를 추가하는 동안 재할당 복사는 총 1,048,575번(추가당 약 1.05번)이었고 한 번의 최악 추가는 524,288개를 복사했다. 비용이 1을 넘는 추가는 20번뿐이었다. 1.5배로 키우는 경우도 복사는 2,099,753번(추가당 약 2.1번)이었다. 가득 찰 때마다 용량을 10씩만 늘리면 같은 100만 개에 복사가 약 5.0×10¹⁰번(추가당 약 5만 번)이었다. 별도로 CPython 3.14.0에서 `list.append`를 100만 번 하는 동안 `sys.getsizeof` 값이 바뀐 횟수는 86번(1,000번 추가 시 28번)이었다. 위 시뮬레이션은 증가 방식별 비용을 센 모형이며 Java `ArrayList`의 실제 성장 정책(문서에 규정 없음)이 아니다. CPython 값은 CPython 구현의 관찰이며 Java 구현과 같다는 뜻은 아니다.
