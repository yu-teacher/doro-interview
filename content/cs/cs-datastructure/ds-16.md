**모범 답변 (30~60초)**
해시 코드가 바뀌는 방식으로 키의 필드를 바꾸는 것은 Map 문서상 동작이 명세되지 않은 일입니다. HashMap 구현에서는 항목이 저장 당시의 해시로 자리 잡은 채 남고 바뀐 해시와 어긋나서, 옛 값으로든 새 값으로든 조회가 실패해 get이 null을 돌려줍니다. 그렇다고 항목이 지워지는 것은 아니어서 크기와 순회에는 남는 유령 항목이 됩니다. equals만 재정의하고 hashCode를 그대로 두면 값이 같은 객체가 서로 다른 해시를 가져 마찬가지로 조회에 실패할 수 있습니다. 그래서 키는 불변 객체로 쓰고 equals와 hashCode를 함께 재정의합니다.

(공식 문서) `Map` 문서는 가변 객체를 키로 쓰면 각별히 주의해야 하며, 키로 들어 있는 동안 `equals` 비교에 영향을 주는 방식으로 값을 바꾸면 맵의 동작이 명세되지 않는다고 한다. `Object.hashCode` 문서는 `equals`에 쓰이는 정보가 바뀌지 않는 한 같은 객체의 해시 코드는 일관되어야 하고, `equals`로 같은 두 객체는 같은 해시 코드를 가져야 한다고 하며, 해시 코드는 `HashMap` 같은 해시 테이블을 위한 것이라고 한다. `Object.equals`의 API Note는 `equals`를 재정의할 때 `hashCode`도 재정의하는 것이 일반적으로 필요하다고 적는다.
(실험 확인) Corretto 25.0.3에서 `hashCode`가 필드 `x`인 키 `k(x=1)`를 `put`한 직후 `get(k)`은 값을 돌려줬다. `k.x = 2`로 바꾸자 `get(k)`은 null, `containsKey(new P(1))`과 `containsKey(new P(2))`는 모두 false였고 `size()`는 여전히 1이었으며 `keySet()` 순회로는 그 키(x=2)가 나왔다. 해시를 1에서 17로 바꿔 16칸 테이블에서 같은 버킷 번호(1)가 되게 해도 `get(k)`은 null이었다. `equals`만 재정의한 클래스를 `HashSet`에 넣고 값이 같은 새 객체로 `contains`하니 1,000번 시도 모두 false였다(기본 `hashCode`는 객체마다 달라지는 값이라 보장되는 동작은 아니고 우연히 같으면 결과가 달라질 수 있다).
(원저자 자료) Open Data Structures 5.1절의 체이닝 해시 테이블은 원소를 넣을 때 hash(x)가 가리키는 칸의 리스트에 넣고, 찾거나 지울 때도 hash(x) 칸의 리스트만 훑는다고 설명한다. 5.3절은 같은 두 객체의 해시 코드가 같아야 하며, 그래야 저장해 둔 x와 같은 y를 나중에 조회했을 때 찾을 수 있다고 한다.
(보충) 저장한 뒤 키의 해시가 달라지거나 `equals`만 재정의해 해시가 어긋나면 조회가 다른 칸을 보게 되어 실패한다는 것은 위 책 서술에서 이끈 추론이며 책이 이 상황을 직접 다루지는 않는다(같은 칸이 되어도 실패한 위 실험 결과는 이 단순 모델로 설명되지 않는다). 저장된 해시값을 먼저 비교하는 구현 같은 `HashMap`의 내부 구현 세부는 일반적인 구현 설명이며 위 책의 단순한 모델에는 없다. 위 실험은 그 현상만 보여준다.
