**모범 답변 (30~60초)**
그냥 다시 보내는 것은 권장되지 않습니다. 타임아웃은 요청이 서버에 닿지 않았다는 뜻이 아니라 응답을 못 받았다는 뜻일 뿐이라 서버에서는 이미 처리됐을 수 있습니다. 표준은 클라이언트가 비멱등 메서드 요청을 자동으로 재시도하지 말라고 하고, 요청이 실제로는 멱등하다는 것을 알거나 원래 요청이 적용되지 않았음을 확인할 방법이 있을 때만 예외라고 합니다. POST를 안전하게 재시도하려면 서버가 중복을 걸러 줘야 합니다. 클라이언트가 요청마다 고유한 식별자를 만들어 헤더나 본문에 실어 보내고, 서버가 그 식별자를 저장해 두었다가 같은 식별자가 다시 오면 처리를 반복하지 않고 처음 결과를 돌려주는 설계를 씁니다.

```
식별자 없이: 요청 1초 타임아웃 -> 같은 POST 재시도 (서버 처리 2초)
  결과: 서버의 승인 건수 = 2   (둘 다 처리됨)
X-Request-Id: k1 을 붙여: 첫 요청은 타임아웃, 처리 완료 후 같은 키로 재시도
  재시도 응답: replayed=true, 승인 건수 증가 없음 (처음 결과 재사용)
```

(공식 문서) RFC 9110 9.2.2는 비멱등 메서드 요청을 클라이언트가 자동 재시도해서는 안 되며(SHOULD NOT) 예외는 요청이 사실상 멱등하다는 것을 알거나 원래 요청이 적용되지 않았음을 감지할 수단이 있을 때라고 한다. 또 일부 클라이언트가 응답 일부라도 받기 전에 연결이 닫히면 POST를 재시도하는 위험한 접근을 한다고 적고, 프록시는 비멱등 요청을 자동 재시도하면 안 된다(MUST NOT)고 한다. 9.3.3은 POST를 대상 리소스가 자기 규칙대로 처리하는 메서드로 설명한다.
(실험 확인) 위 블록은 Python 3.14 연습용 서버와 curl 8.7.1(-m 1 로 1초 타임아웃)로 확인했다. 클라이언트가 응답을 못 받은 요청도 서버에서는 2초 뒤 처리가 끝났다.
(보충) 요청 식별자를 헤더나 본문에 실어 서버가 중복을 거르는 설계는 일반적인 실무 방식이다. 위 실험의 X-Request-Id 는 내가 정한 이름이고 HTTP 표준 헤더가 아니며, 이번에 읽은 RFC 어디에도 이 방식을 규정한 문장은 없다. 식별자 저장 기간, 동시에 같은 키가 올 때의 처리, 요청 내용이 다른 같은 키 처리는 설계마다 따로 정해야 한다.
