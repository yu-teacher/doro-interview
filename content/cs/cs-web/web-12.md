**모범 답변 (30~60초)**
HTTP/2는 하나의 연결 안에서 요청과 응답을 각각 독립된 스트림으로 만들고, 프레임을 서로 끼워 보내는 멀티플렉싱을 합니다. 그래서 느린 응답 하나가 같은 연결의 다른 응답을 막는 애플리케이션 계층의 HOL 블로킹이 풀리고, 클라이언트는 호스트·포트 쌍마다 연결을 하나만 여는 것이 권장됩니다. 메시지는 텍스트가 아니라 바이너리 프레임으로 보내고, 헤더는 HPACK으로 압축해서 반복되는 헤더를 표 인덱스로 줄입니다. 하지만 아래 전송 계층은 여전히 TCP라서 패킷 하나가 유실되면 그 연결의 모든 스트림이 같이 멈추는 TCP 수준의 HOL 블로킹은 해결하지 못한다고 표준이 직접 밝히고 있습니다.

```
같은 연결에서 /slow(1.5초 지연)와 /fast 를 동시에 요청
  HTTP/1.1 파이프라이닝: 두 응답 모두 1503ms 에 도착
  HTTP/2             : /fast 4ms, /slow 1503ms 에 완료

같은 900바이트 쿠키 헤더가 든 요청을 한 연결에서 3번 전송 (클라이언트->서버 바이트)
  HTTP/2 : 676 -> 19 -> 19    (동일 헤더는 동적 표 인덱스로 대체)
  HTTP/1.1 텍스트 요청 : 매번 955 바이트
```

(공식 문서) RFC 9113 1절은 HTTP/1.1 파이프라이닝이 동시성을 부분적으로만 해결해 애플리케이션 계층 head-of-line 블로킹이 남아 HTTP/1.x 클라이언트는 여러 연결을 쓴다고 하고, HTTP/2는 같은 연결에서 메시지를 끼워 보내고 필드를 효율적으로 부호화하며 이진 프레이밍을 쓰지만 "TCP head-of-line blocking is not addressed by this protocol"이라고 적는다. 5절은 스트림이 한 연결 안에서 독립적인 양방향 프레임 순서열이고 여러 스트림이 동시에 열려 프레임이 섞인다고 하며, 5.1.2는 SETTINGS_MAX_CONCURRENT_STREAMS 로 동시 스트림 수를 제한한다고 한다. 9.1은 클라이언트가 같은 호스트·포트 쌍에 HTTP/2 연결을 둘 이상 열지 말아야(SHOULD NOT) 한다고 한다. 4.3은 필드 섹션 압축이 별도 문서에 정의됐다고 하고, RFC 7541 1절은 그 문서가 HPACK이며 중복 필드를 없애고 DEFLATE 방식이 받은 CRIME 공격을 피하도록 설계됐다고 설명한다.
(실험 확인) Node v24.16.0 의 http2 모듈로 평문(h2c) 서버와 클라이언트를 만들어 로컬에서 쟀다. 바이트 수는 TCP 프록시로 클라이언트에서 서버로 가는 양을 센 값이다. 쿠키 값은 'c=' 뒤에 abcdefghij 를 반복해 900자로 자른 것이다. 연결을 여는 데 쓴 초기 바이트는 42바이트였고, HTTP/1.1 의 955바이트는 같은 쿠키로 내가 만든 요청 문자열(GET, Host, Cookie 세 줄)의 길이다. 첫 요청이 줄어든 이유는 따로 분해해 확인하지 않았다. 이 수치는 이 헤더 조합에서 나온 값이고 일반적인 압축률이 아니다.
