**모범 답변 (30~60초)**
안전하다는 건 클라이언트가 서버 상태 변경을 요청하지도 기대하지도 않는 읽기 전용 의미라는 뜻이고, GET이 여기에 속합니다. 멱등하다는 건 같은 요청을 여러 번 보냈을 때 서버에 미치는 의도된 효과가 한 번 보냈을 때와 같다는 뜻이고, 표준이 정의한 메서드 중에서는 PUT, DELETE와 안전한 메서드가 멱등입니다. POST는 그 목록에 없어서 같은 요청을 반복하면 주문이 두 건 생기는 식으로 효과가 쌓일 수 있습니다. 이 구분이 중요한 이유는 연결이 끊겨 응답을 못 받았을 때, 멱등한 요청은 자동으로 다시 보내도 되지만 비멱등 요청은 자동 재시도하지 말라고 권고되기 때문입니다.

```
PUT    /items/1 x2 -> 201, 200   (두 번 뒤 상태는 한 번 뒤와 같음)
DELETE /items/1 x2 -> 204, 404   (두 번 뒤에도 항목은 없음)
POST   /orders  x2 -> 201 Location:/orders/1, 201 Location:/orders/2   (주문 2건)
```

(공식 문서) RFC 9110 9.2.1은 안전 메서드를 클라이언트가 서버 상태 변경을 요청하지도 기대하지도 않는 읽기 전용 의미의 메서드로 정의하고, 이 표준이 정의한 메서드 중 GET, HEAD, OPTIONS, TRACE를 안전하다고 한다. 서버가 요청마다 접근 로그를 남기는 정도의 부수 효과는 안전 판정과 무관하다고 한다. 9.2.2는 같은 요청을 여러 번 보낸 의도된 효과가 한 번 보낸 효과와 같은 메서드를 멱등이라 하고, PUT, DELETE, 안전한 메서드가 멱등이라고 한다. 같은 절은 응답을 읽기 전에 통신이 실패했을 때 멱등한 요청은 재시도할 수 있고, 비멱등 요청은 실제로 멱등하다는 것을 알거나 원래 요청이 적용되지 않았음을 확인할 방법이 없으면 자동 재시도하지 말라고(SHOULD NOT) 한다. 9.3.3은 POST를 대상 리소스가 자기 규칙대로 본문을 처리하게 하는 메서드로 설명한다.
(실험 확인) Python 3.14 http.server 로 만든 연습용 서버에 curl 8.7.1 로 같은 요청을 두 번씩 보낸 결과가 위 블록이다. 서버가 메서드 의미를 지키도록 내가 짠 것이므로 의미를 지켰을 때의 모습을 보여 줄 뿐, 모든 서버가 그렇다는 증거는 아니다.
