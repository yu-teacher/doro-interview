**모범 답변 (30~60초)**
기준이 두 개입니다. 하나는 영구냐 임시냐로, 301과 308이 영구 이동이고 302와 307이 임시 이동입니다. 다른 하나는 자동 재요청 때 메서드를 바꿔도 되느냐입니다. 301과 302는 역사적인 이유로 사용자 에이전트가 POST를 GET으로 바꿔 다시 요청해도 되고, 실제 관행도 GET으로 수렴했습니다. 반면 307과 308은 메서드를 바꾸면 안 된다고 못 박아서 POST가 POST 그대로, 본문도 유지된 채 따라갑니다. 그래서 POST를 유지한 채 옮기려면 영구는 308, 임시는 307을 쓰고, 301과 308 응답은 명시적 캐시 지시가 없어도 휴리스틱으로 캐시될 수 있다는 점도 알아 둬야 합니다.

```
curl -L -d 'x=1' (curl 8.7.1, 같은 /final 로 리다이렉트)
301 -> final got method=GET  body=''
302 -> final got method=GET  body=''
303 -> final got method=GET  body=''
307 -> final got method=POST body='x=1'
308 -> final got method=POST body='x=1'
```

(공식 문서) RFC 9110 15.4는 301과 302가 원래 HTTP/1.0에서 메서드 유지로 정의됐지만 초기 사용자 에이전트가 POST를 POST로 따를지 GET으로 따를지 갈렸고 관행이 GET으로 바꾸는 쪽으로 수렴했으며, 그래서 307과 308이 메서드 유지 리다이렉트를 명확히 하려고 추가됐다고 설명한다. 15.4.2와 15.4.3은 301과 302에서 사용자 에이전트가 POST를 GET으로 바꿔도 된다(MAY)고 하고, 바꾸기 싫으면 각각 308, 307을 쓰라고 한다. 15.4.8은 307에서 사용자 에이전트가 자동 리다이렉션 시 메서드를 바꾸면 안 된다(MUST NOT)고 하고, 15.4.9는 308이 영구 이동이며 307보다 최근(2014년 6월)에 나와 모든 곳에서 인식되지 않을 수 있다고 적는다. 301과 308은 휴리스틱 캐시 가능(heuristically cacheable)이라고 명시한다. 15.4는 자동 리다이렉션 때 원 요청 메시지를 다시 보내되 열거된 수정만 하라고(SHOULD) 하고 메서드가 GET 이나 HEAD 로 바뀔 때만 콘텐츠 관련 필드를 지우라고 하므로, 307·308 이 본문을 유지하는 것은 이 서술을 따른 해석이다(본문 유지를 직접 명시한 문장은 아니다).
(실험 확인) 위 블록은 curl 8.7.1 의 동작이다. -d 만 주고 -X POST 를 같이 주지 않았을 때의 결과이며, --post301 --post302 옵션을 주면 301/302도 POST와 본문을 유지했다. -X POST 를 함께 주면 본문은 버려지는데 메서드 문자열만 POST로 남는 것을 관찰했다. 이것은 curl 구현 동작이지 표준 요구가 아니다.
