**모범 답변 (30~60초)**
멱등의 정의가 같은 요청을 여러 번 보냈을 때 서버에 미치는 의도된 효과가 한 번 보냈을 때와 같다는 것이지, 응답이 같다는 뜻이 아니기 때문입니다. DELETE를 처음 보내면 리소스가 사라지고 204 같은 성공 응답이 오고, 두 번째에는 이미 없으니 404가 올 수 있습니다. 그래도 두 경우 모두 요청이 의도한 결과, 즉 그 리소스가 없는 상태는 같습니다. 표준도 서버가 요청마다 로그를 남기는 식의 부수 효과를 가져도 멱등 판정과 무관하다고 하고, 재시도했을 때 응답은 달라질 수 있음을 인정합니다. 그래서 응답을 못 받고 연결이 끊겼을 때 DELETE는 자동으로 재시도해도 안전합니다.

```
DELETE /items/1 -> 204
DELETE /items/1 -> 404
GET    /items/1 -> 404    (어느 쪽이든 최종 상태는 "없음")
```

(공식 문서) RFC 9110 9.2.2는 멱등을 같은 요청 여러 번의 의도된 효과가 한 번과 같은 것으로 정의하고, 이 속성은 사용자가 요청한 것에만 적용되며 서버는 각 요청을 따로 로그에 남기거나 개정 이력을 남기는 등 비멱등 부수 효과를 가질 수 있다고 한다. 같은 절은 통신 실패로 응답을 못 읽은 경우 멱등 요청을 재시도할 수 있고 "though the response might differ", 즉 재시도하면 응답이 달라질 수 있다고 한다. 9.3.5는 DELETE를 대상 리소스와 현재 기능의 연결을 제거하라는 요청(UNIX rm 과 비슷)이라 하고 성공 시 202, 204, 200 중 하나를 권한다. 15.5.5는 404가 현재 표현을 찾지 못했거나 있음을 공개하지 않으려는 뜻이라고 한다.
(실험 확인) 위 블록은 Python 3.14 연습용 서버에 curl 8.7.1 로 보낸 결과다. 두 번째가 404 인 것은 내 서버가 정한 응답이고, 서버에 따라 두 번째에도 204 를 줄 수 있다.
