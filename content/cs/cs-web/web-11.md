**모범 답변 (30~60초)**
HTTP/1.1은 기본이 지속 연결이라서, Connection: close를 보내지 않으면 응답 뒤에도 TCP 연결을 유지하고 그 위에서 요청을 계속 보냅니다. 파이프라이닝은 응답을 기다리지 않고 요청 여러 개를 연달아 보내는 방식인데, 서버는 응답을 반드시 요청이 들어온 순서대로 보내야 합니다. 그래서 앞 요청 처리가 오래 걸리면 뒤 요청의 응답이 준비돼 있어도 그 뒤에서 기다리는 Head-of-Line 블로킹이 생깁니다. 이를 피하려고 클라이언트가 연결을 여러 개 여는데, 표준은 연결마다 서버 자원을 쓰고 혼잡을 키울 수 있으니 보수적으로 열라고 합니다. 비멱등 메서드 뒤에는 응답을 받기 전까지 파이프라이닝을 하지 말라는 권고도 있습니다.

```
한 연결에 GET /slow(1.5초 지연), GET /fast 를 연달아 전송 (HTTP/1.1 파이프라이닝)
  두 응답이 도착한 시각: /slow 1503ms, /fast 1503ms   (fast 가 slow 뒤에서 대기)
curl 한 번에 URL 2개 -> "Re-using existing connection" (연결 1개 재사용)
```

(공식 문서) RFC 9112 9.3은 HTTP/1.1이 기본적으로 지속 연결을 쓰고, close 연결 옵션이 있으면 현재 응답 뒤 연결이 유지되지 않는다고 한다. 지속 연결에서는 모든 메시지가 스스로 길이를 정의해야 하고, 서버는 요청 본문을 모두 읽거나 연결을 닫아야 한다. 9.3.2는 클라이언트가 응답을 기다리지 않고 요청 여러 개를 보낼 수 있고, 서버가 안전한 메서드의 파이프라인 요청은 병렬로 처리할 수 있어도 응답은 요청 순서대로 보내야 한다(MUST)고 하며, 사용자 에이전트는 비멱등 메서드 뒤에서 최종 응답을 받을 때까지 파이프라이닝하지 말아야(SHOULD NOT) 한다고 한다. 9.4는 여러 연결을 쓰는 이유가 요청 하나의 긴 처리나 큰 전송이 같은 연결의 뒤 요청을 막는 head-of-line 블로킹을 피하기 위해서이며, 연결마다 서버 자원이 들고 혼잡 부작용이 있으니 보수적으로 열라고 한다. RFC 9113 1절은 HTTP/1.1 파이프라이닝이 동시성을 일부만 해결하고 여전히 애플리케이션 계층 head-of-line 블로킹이 있다고 설명한다.
(실험 확인) Node v24.16.0 http 서버와 원시 TCP 소켓으로 한 연결에 두 요청을 연달아 보낸 결과가 위 블록이다. 이 서버는 두 핸들러를 거의 동시에(5ms) 시작했는데도 완성된 /fast 응답을 /slow 응답 뒤로 미뤄 보냈다. 같은 요청을 연결 두 개로 나눠 보내면 /fast 3ms, /slow 1503ms 였다. 이 서버 구현이 요청 순서대로 응답한 결과이고, 파이프라이닝 지원 여부는 서버마다 다를 수 있다.
