**모범 답변 (30~60초)**
PUT은 요청 본문을 대상 리소스의 새 상태 전체로 보고 생성하거나 교체하는 메서드라서, 같은 요청을 반복해도 결과가 같은 멱등입니다. PATCH는 본문이 전체 상태가 아니라 현재 리소스를 어떻게 바꿀지 적은 변경 명세이고, RFC 5789 정의상 안전하지도 멱등하지도 않지만 멱등하게 보낼 수는 있습니다. 예를 들어 값을 끝에 덧붙이는 패치는 두 번 보내면 결과가 달라집니다. POST는 대상 리소스가 자기 규칙대로 본문을 처리하는 가장 일반적인 방식이고, 서버가 URI를 골라 주는 생성은 PUT이 아니라 POST로 구현하라고 표준이 말합니다. 기준 상태가 필요한 패치는 ETag와 If-Match로 충돌을 막도록 권고됩니다.

```
PUT   /items/2 'A'   -> 201                       (이후 값 "A")
PATCH /items/2 'B'   -> 200, 값 "AB"              (덧붙이기 패치)
PATCH /items/2 'B'   -> 200, 값 "ABB"             (같은 요청을 또 보내면 결과가 달라짐)
```

(공식 문서) RFC 9110 9.3.4는 PUT이 대상 리소스의 상태를 본문이 정의한 상태로 생성하거나 교체하라고 요청하는 것이며, PUT의 의도는 멱등이라고 한다. 또 서버가 클라이언트 대신 URI를 고르는 상태 변경 요청은 PUT이 아니라 POST로 구현하는 것이 SHOULD라고 한다. 9.3.3은 POST를 대상 리소스가 본문을 자기 고유의 의미에 따라 처리하게 하는 메서드로 설명한다. RFC 5789 2절은 PATCH가 현재 리소스를 수정하는 방법을 담은 변경 집합이라는 점이 PUT과 다르다고 하고, PATCH가 안전하지도 멱등하지도 않지만 멱등하게 보낼 수 있다고 하며, 서버는 전체 변경을 원자적으로 적용해야 한다고 한다. 기준 상태가 필요한 패치 형식에는 강한 ETag를 If-Match로 보내는 조건부 요청을 쓰라고 한다. RFC 5789 는 RFC 2616 기준으로 쓰였고, RFC 9110 에는 PATCH 정의가 없으며 참조만 있다.
(실험 확인) 위 블록은 Python 3.14 로 만든 연습용 서버에 curl 8.7.1 로 보낸 결과다. 덧붙이기 패치 의미는 내 서버의 구현이고, 표준이 PATCH 의미를 정한 것은 아니다.
