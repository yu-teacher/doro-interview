**모범 답변 (30~60초)**
모놀리스는 서버 쪽 애플리케이션 전체가 하나의 단위로 빌드되고 배포되는 구조입니다. 마이크로서비스는 하나의 애플리케이션을 작은 서비스 여러 개로 나눈 방식으로, 서비스마다 자기 프로세스에서 돌고 HTTP API 같은 가벼운 수단으로 통신하며, 비즈니스 기능 단위로 나뉘어 자동화된 배포로 독립 배포됩니다. 모놀리스는 작은 변경에도 전체를 다시 배포하고 확장도 전체 단위로 해야 해서 불편해지기 쉽습니다. 마이크로서비스는 독립 배포와 뚜렷한 모듈 경계를 얻는 대신 원격 호출 비용, 장애 처리, 최종 일관성 같은 분산 시스템의 복잡도를 떠안습니다.

(원저자 자료) Fowler·Lewis의 "Microservices"(2014-03-25)는 마이크로서비스를 각자 프로세스에서 돌며 가벼운 수단(흔히 HTTP 리소스 API)으로 통신하고, 비즈니스 역량을 중심으로 나뉘어 자동화된 배포로 독립 배포되는 작은 서비스의 묶음으로 설명한다. 저자들은 정식 정의는 없으며 관찰한 공통 특징을 서술한 것이고 모든 특징이 항상 있는 것은 아니라고 밝힌다. 같은 글은 모놀리스를 단일 논리 실행 단위로 보고, 변경 주기가 묶이고 모듈 구조를 지키기 어려워지며 확장이 전체 단위라는 불만이 커졌다고 쓴다. 또 서비스는 프로세스 밖 컴포넌트라서 원격 호출이 인프로세스 호출보다 비싸 API가 더 거칠어져야 하고, 책임을 옮기는 일도 어려워진다고 지적한다.
(원저자 자료) Richardson의 microservices.io "Monolithic Architecture"는 모놀리스를 단일 배포 단위와 단일 DB 구조로 정의한다. 모든 연산이 로컬이라 대개 ACID 트랜잭션으로 구현할 수 있고 상호작용이 단순하고 효율적인 반면, 컴포넌트가 하나라 크기와 복잡도 때문에 이해·유지가 어렵고 팀 자율성과 배포 파이프라인 속도가 떨어질 수 있다고 한다. 저자는 이 단점이 규모와 팀 수가 커질수록 심해진다고 쓴다.
