**모범 답변 (30~60초)**
JPA는 트랜잭션 안에서 조회하거나 저장한 영속 엔티티의 스냅샷을 들고 있다가, 플러시 시점에 변경을 감지해서 UPDATE를 날립니다. 실험으로 확인했습니다. `@Transactional` 메서드에서 엔티티를 `save`한 뒤 필드만 `update("second")`로 바꾸고 별도 저장은 하지 않았는데, 메서드가 끝나 커밋될 때 UPDATE가 나가서 DB에서 이름이 "second"로 조회됩니다. 즉 더티 체킹은 영속성 컨텍스트가 살아 있는 트랜잭션 안에서 변경을 감지하는 기능입니다.

(보충) 위 동작 원리(스냅샷 비교와 플러시)는 JPA/Hibernate의 일반적 동작 설명이며, transaction 장 문서에서 확인한 내용은 아니다. 실험이 보여주는 것은 "트랜잭션 안에서 별도 save 없이도 값이 반영된다"는 결과이고, "트랜잭션 밖에서는 동작하지 않는다"는 이 실험으로 확인한 것이 아니다.

```java
@Transactional
public Long dirtyChecking(String email) {
    Member saved = memberRepository.save(Member.builder().name("first").email(email).build());
    saved.update("second");   // 별도 save 없음
    return saved.getId();     // 커밋 후 DB 조회: name == "second"
}
```
