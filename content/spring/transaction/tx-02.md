**모범 답변 (30~60초)**
선언적 방식은 `@Transactional`을 메서드나 클래스에 붙이면 프록시가 메서드 앞뒤로 트랜잭션을 열고 닫아 주는 방식이라 비즈니스 코드가 깔끔합니다. 프로그래밍 방식은 `TransactionTemplate`의 `execute` 콜백 안에서 직접 경계를 잡는 방식입니다. 공식 문서는 템플릿을 쓰면 획득, 커밋, 롤백은 템플릿이 처리하고 우리는 해야 할 작업만 표현하면 된다고 설명합니다. 메서드 일부만 트랜잭션으로 묶고 싶을 때, 트랜잭션 이름이나 설정을 호출마다 다르게 주고 싶을 때, 프록시 제약(자기 호출 등)을 피하고 싶을 때 프로그래밍 방식이 유리합니다. 다만 Spring 트랜잭션 API에 코드가 결합된다는 단점이 있어서 기본은 선언적으로 가는 게 일반적입니다.

```java
// 프로그래밍 방식 (공식 문서의 패턴을 람다로 단순화)
private final TransactionTemplate tx;

public SimpleService(PlatformTransactionManager tm) {
    this.tx = new TransactionTemplate(tm);
}

public Long place(Order order) {
    return tx.execute(status -> {
        try {
            orderRepository.save(order);
            return order.getId();
        } catch (BusinessException e) {
            status.setRollbackOnly();   // 예외 없이 롤백 표시
            return null;
        }
    });
}
```

(공식 문서) `TransactionTemplate`은 상태를 갖지 않아 thread-safe하며 인스턴스를 여러 곳에서 공유할 수 있다. 다른 격리 수준 등이 필요하면 별도 인스턴스를 만든다. 템플릿 사용은 Spring 트랜잭션 인프라에 코드를 묶는다고 문서가 명시한다.
