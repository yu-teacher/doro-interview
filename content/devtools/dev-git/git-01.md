**모범 답변 (30~60초)**
Subversion 같은 도구는 파일마다 변경분(델타)의 목록을 관리하지만, Git은 커밋할 때마다 그 순간의 프로젝트 모습을 스냅샷으로 기록합니다. 다만 바뀌지 않은 파일은 새로 저장하지 않고 이전에 저장한 것을 가리키는 링크만 남기기 때문에, 바뀐 파일만 새로 저장됩니다. 모든 데이터는 내용에서 계산한 체크섬으로 식별됩니다. 또 히스토리가 로컬 저장소에 통째로 있어서 대부분의 명령을 네트워크 없이 실행하므로, 오프라인에서도 커밋하고 과거 버전과 비교할 수 있습니다.

(공식 문서) Pro Git 한국어판 1.3절은 CVS·Subversion 계열이 파일별 변화를 시간순으로 관리하는 델타 기반인 반면 Git은 데이터를 파일 시스템 스냅샷의 연속으로 취급하고, 파일이 달라지지 않았으면 새로 저장하지 않고 이전 파일에 대한 링크만 저장한다고 설명한다. 같은 절에 거의 모든 명령이 로컬 데이터만 쓰고, 저장 전에 항상 체크섬(SHA-1)을 구해 그 값으로 데이터를 관리한다는 설명이 있다. 3.1절도 커밋이 스테이징 영역 데이터의 스냅샷을 가리키는 커밋 개체를 저장한다고 한다.
(실험 확인) Git 2.50.1(Apple Git-155, macOS)의 임시 저장소에서 a.txt만 고쳐 두 번째 커밋을 만들자, 고치지 않은 `sub/c.txt`의 blob과 `sub` 트리의 ID가 두 커밋에서 같았다. 즉 두 스냅샷이 바뀌지 않은 객체를 공유한다. 내용이 같은 다른 파일 이름(`a_copy.txt`)도 같은 blob ID였다. `git init --object-format=sha256`으로 만든 저장소는 커밋 ID가 64자리였고 기본 저장소는 40자리였다.
