**모범 답변 (30~60초)**
`ExternalName` Service는 셀렉터도 ClusterIP도 없이, 클러스터 DNS가 `externalName`에 적힌 외부 호스트 이름을 가리키는 CNAME 레코드를 돌려주게 하는 유형입니다. 프록시나 포워딩은 전혀 설정하지 않고 리다이렉션이 DNS 수준에서만 일어나서, 나중에 DB를 클러스터로 옮기면 Service만 바꾸면 됩니다. 문제는 HTTP나 HTTPS 같은 호스트 이름을 쓰는 프로토콜입니다. 클라이언트가 쓴 이름과 실제 서버 이름이 달라서 `Host` 헤더를 서버가 못 알아보거나, TLS 서버가 클라이언트가 접속한 이름에 맞는 인증서를 못 줄 수 있습니다. 그리고 IP처럼 생긴 문자열은 IP가 아니라 DNS 이름으로 취급됩니다.

(공식 문서) Service 페이지는 ExternalName이 Service를 `spec.externalName`의 DNS 이름으로 매핑하고, 클러스터 DNS가 그 값의 CNAME 레코드를 반환하며 어떤 종류의 프록시도 설정되지 않는다고 한다. 리다이렉션이 프록시나 포워딩이 아니라 DNS 수준에서 일어나고, 나중에 DB를 클러스터로 옮길 때 selector를 추가하고 type을 바꾸면 된다고 한다. HTTP와 HTTPS에서는 클라이언트가 쓰는 호스트명이 참조 대상과 달라 Host 헤더를 원 서버가 인식하지 못하거나 TLS 인증서가 맞지 않을 수 있다고 경고하고, IPv4 주소처럼 생긴 문자열은 숫자로 된 DNS 이름으로 취급되어 해석되지 않는다고 한다. ExternalName은 Kubernetes DNS 서버로만 접근할 수 있다.
(실험 확인) 2026-10-27 v1.36.1에서 `type: ExternalName`, `externalName: db.example.com`인 Service `ext`는 `kubectl get svc`에서 CLUSTER-IP가 `<none>`, EXTERNAL-IP가 `db.example.com`이었다. 클러스터 DNS에 `nslookup -type=CNAME ext...`를 하자 `ext.exp-networkv.svc.cluster.local canonical name = db.example.com`이 나왔다. `externalName: "1.2.3.4"`인 Service는 만들어졌지만 DNS 조회가 NXDOMAIN이었다. 외부 접속은 실험 범위 밖이라 HTTP Host 불일치는 문서 근거다.
