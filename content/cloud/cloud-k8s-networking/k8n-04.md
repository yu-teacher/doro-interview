**모범 답변 (30~60초)**
클러스터 DNS(보통 CoreDNS)가 Service마다 `서비스이름.네임스페이스.svc.cluster.local` 형태의 이름을 만들고, 일반 Service는 이 이름을 ClusterIP로 해석해 줍니다. Pod의 DNS 검색 목록에 자기 네임스페이스가 들어 있어서 같은 네임스페이스의 Service는 `api`처럼 이름만으로 부를 수 있습니다. 다른 네임스페이스의 Service는 `api.prod`처럼 네임스페이스를 붙이거나 전체 이름을 써야 하고, 이름만 쓰면 못 찾습니다. 그래서 설정 파일에는 IP 대신 이 DNS 이름을 적습니다. `cluster.local`은 흔한 예일 뿐이고 클러스터 도메인은 클러스터마다 다를 수 있습니다.

(공식 문서) DNS for Services and Pods 페이지는 일반 Service에 `my-svc.my-namespace.svc.cluster-domain.example` 형태의 A/AAAA 레코드가 만들어져 클러스터 IP로 해석된다고 한다. 네임스페이스를 지정하지 않은 쿼리는 Pod 자신의 네임스페이스로 한정되고, 다른 네임스페이스의 Service는 `data.prod`처럼 네임스페이스를 붙이면 되며, 검색 목록에 의해 `data`가 `data.test.svc.cluster.local`로 확장된다고 설명한다. Service 페이지는 DNS 서버(CoreDNS 등)가 API를 감시하며 Service마다 레코드를 만든다고 한다. Debug Services 페이지는 `cluster.local`이 클러스터 도메인이며 다른 클러스터에서는 달라질 수 있다고 한다.
(실험 확인) 2026-10-27 v1.36.1에서 네임스페이스 exp-networkv의 Service `web`을 같은 네임스페이스 Pod에서 `wget http://web:8080`으로 호출하면 성공했다. 다른 네임스페이스(exp-networkv-b) Pod에서는 `web`이 `bad address`로 실패했고 `web.exp-networkv`, `web.exp-networkv.svc`, `web.exp-networkv.svc.cluster.local`은 모두 성공했다. `nslookup`으로 전체 이름을 조회하면 Service의 ClusterIP(10.106.66.234)가 나왔다. 이 클러스터의 도메인은 `cluster.local`이었다.
