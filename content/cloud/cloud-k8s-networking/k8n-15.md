**모범 답변 (30~60초)**
`Gateway`는 하나의 `GatewayClass`를 참조하고, 그 클래스에 적힌 컨트롤러가 이 게이트웨이를 구현합니다. `HTTPRoute`는 `parentRefs`로 붙일 `Gateway`를 가리키고, 호스트명·경로 같은 매칭 조건과 `backendRefs`로 Service를 지정합니다. 게이트웨이도 리스너의 `allowedRoutes`로 어떤 라우트를 받을지 걸러서, 라우트와 게이트웨이가 서로 신뢰하는 양방향 구조입니다. 기본값은 같은 네임스페이스의 라우트만 받는 것이라 다른 네임스페이스에서 붙이려면 `allowedRoutes`를 설정해야 합니다. 이 리소스들은 쿠버네티스에 내장되지 않은 CRD라서 먼저 설치해야 합니다.

(공식 문서) Gateway API 페이지는 이 API가 CRD로 정의된 애드온이며, 안정 kind로 GatewayClass, Gateway, HTTPRoute, GRPCRoute가 있다고 한다. Gateway는 정확히 하나의 GatewayClass와 연결되고, 클래스는 구현 컨트롤러 이름을 담는다. 라우트는 `parentRefs`로 Gateway에 연결되고 Gateway가 리스너에 붙을 수 있는 라우트를 걸러 양방향 신뢰 모델을 이룬다고 한다. 기본적으로 Gateway는 같은 네임스페이스의 라우트만 받으며 다른 네임스페이스는 `allowedRoutes`를 설정해야 한다고 한다. Gateway API에는 Ingress kind가 없어 일회성 변환이 필요하다고 하고, 역할 지향(인프라 제공자, 클러스터 운영자, 앱 개발자) 설계를 소개한다.
(실험 확인) 2026-10-27 v1.36.1 Docker Desktop 클러스터에서 `kubectl get crd`가 비어 있었고 `kubectl api-resources`에도 Ingress와 IngressClass만 있었다. `HTTPRoute` 매니페스트를 적용하자 `no matches for kind "HTTPRoute" ... ensure CRDs are installed first`로 거부되어, Gateway API 리소스는 기본으로 설치되어 있지 않았다. 설치와 라우팅 동작은 실험하지 않았다.
