**모범 답변 (30~60초)**
Ingress 규칙은 선택적인 `host`와 경로 목록으로 이뤄지고, 요청의 호스트와 경로가 모두 맞아야 해당 규칙의 백엔드, 즉 Service 이름과 포트로 보냅니다. 각 경로에는 `pathType`이 필수입니다. `Exact`는 대소문자를 구분해 경로가 정확히 같을 때만 맞고, `/foo`는 `/foo/`와 맞지 않습니다. `Prefix`는 경로를 슬래시로 나눈 요소 단위로 앞부분이 같을 때 맞아서 `/foo/bar`는 `/foo/bar/baz`와는 맞고 `/foo/barbaz`와는 맞지 않습니다. 여러 경로가 맞으면 가장 긴 경로가 이기고, 같으면 `Exact`가 우선합니다. 이 규칙을 실제로 처리하는 것은 Ingress 컨트롤러입니다.

(공식 문서) Ingress 페이지는 HTTP 규칙이 선택적 host와 경로 목록(각각 service.name과 port)을 가지며 host와 path가 모두 요청과 맞아야 한다고 한다. 각 path에는 pathType이 필수이고 없으면 검증에 실패한다고 한다. Exact는 대소문자 구분 정확 일치, Prefix는 `/`로 나눈 요소 단위 접두 일치이며 예시 표에서 `/foo/bar`가 `/foo/bar/baz`와 맞지만 `/foo/barbaz`와는 맞지 않고 Exact `/foo`는 `/foo/`와 맞지 않는다고 보인다. 여러 경로가 맞으면 가장 긴 경로, 같으면 Exact 우선이라고 한다. 호스트 와일드카드 `*.foo.com`은 `bar.foo.com`과 맞고 `baz.bar.foo.com`과는 맞지 않는다고 한다. Ingress 페이지는 컨트롤러 없이 리소스만 만들면 효과가 없다고 하고, Ingress Controllers 페이지는 Ingress가 동작하려면 컨트롤러가 실행 중이어야 한다고 한다. 또 Ingress 페이지는 프로젝트가 Gateway를 권장하고 Ingress API는 동결(frozen)되었다고 쓴다.
(실험 확인) 2026-10-27 v1.36.1 Docker Desktop 클러스터에는 Ingress 컨트롤러 Pod와 IngressClass가 없었다. host와 `pathType: Prefix` 경로를 가진 Ingress를 만들면 API는 정상 승인했고 `kubectl describe ingress`가 백엔드 `web:8080`을 Pod IP들로 풀어 보여 주었지만, ADDRESS는 비었고 이벤트도 없었다. `pathType` 없이 만든 Ingress는 `pathType must be specified`로, `path: foo`(슬래시 없음)는 `must be an absolute path`로 거부되었다. 실제 라우팅 동작은 컨트롤러가 없어 확인하지 못했고 pathType 매칭 규칙은 문서 근거다.
