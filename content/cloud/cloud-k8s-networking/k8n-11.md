**모범 답변 (30~60초)**
kube-proxy는 노드마다 떠서 API 서버의 Service와 EndpointSlice 변경을 감시하고, 노드의 커널 규칙을 맞춰 둡니다. ClusterIP와 포트로 들어오는 트래픽을 가로채 백엔드 Pod 중 하나로 보내는 규칙입니다. 리눅스에서는 기본적으로 iptables 모드로, 엔드포인트마다 규칙을 만들어 기본적으로 무작위로 고르고, 목적지 주소 변환으로 Pod에 전달합니다. nftables 모드도 있고 ipvs 모드는 폐지 예정입니다. ClusterIP는 어떤 호스트도 소유하지 않는 가상 IP이고, ExternalName과 headless Service는 kube-proxy가 처리하지 않습니다. DNS 라운드 로빈 대신 프록시를 쓰는 건 DNS 캐시 때문입니다.

(공식 문서) Virtual IPs and Service Proxies 페이지는 모든 노드가 kube-proxy를 실행하고(대체 구현이 없다면), ExternalName이 아닌 Service에 대해 가상 IP 메커니즘을 구현한다고 한다. Service와 EndpointSlice를 감시해 clusterIP와 port로 오는 트래픽을 엔드포인트로 리다이렉트하도록 노드를 구성하고 제어 루프가 규칙을 동기화한다. 리눅스 모드는 iptables, ipvs, nftables이고 문서 기준 v1.37의 기본은 iptables이며 향후 nftables로 바뀔 예정이라 명시 설정을 권한다. ipvs는 v1.35부터 deprecated이고 v1.43에서 제거될 예정이다. iptables 모드는 엔드포인트마다 규칙을 만들어 기본적으로 무작위로 백엔드를 고른다. 프록시를 쓰는 이유로 DNS 구현이 TTL을 무시하고 결과를 캐시하는 오랜 역사를 든다. Service 페이지는 headless Service를 kube-proxy가 처리하지 않는다고 한다. Debug Services 페이지는 kube-proxy 로그의 `Using iptables Proxier` 줄이 iptables 모드를 뜻한다고 하고, iptables 모드에서 Service 포트마다 `KUBE-SERVICES` 규칙과 `KUBE-SVC-<hash>` 체인, 엔드포인트마다 `KUBE-SEP-<hash>` 체인이 있고 `statistic --mode random` 확률 규칙으로 고른 뒤 `DNAT`한다는 예를 보인다.
(실험 확인) 2026-10-27 v1.36.1 Docker Desktop 클러스터는 kube-system에서 `kube-proxy` DaemonSet이 돌았고 그 로그에 `Using iptables Proxier`가 있었다. kube-proxy 설정의 `mode`는 빈 문자열(기본값)이어서 iptables가 선택되었다. iptables 규칙 내용 자체는 조회하지 않았다.
