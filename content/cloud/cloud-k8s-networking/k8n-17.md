**모범 답변 (30~60초)**
kubelet이 Pod마다 `/etc/resolv.conf`를 만드는데, `nameserver`는 클러스터 DNS Service의 IP이고, `search`에는 Pod의 네임스페이스, `svc.cluster.local`, `cluster.local`이 순서대로 들어갑니다. 그래서 `api` 같은 짧은 이름이 검색 목록으로 확장되어 풀립니다. `options ndots:5`는 점이 5개보다 적은 이름을 먼저 검색 목록으로 확장해 시도하라는 뜻이라, 외부 도메인도 몇 번의 실패한 조회를 거칠 수 있습니다. `dnsPolicy`의 기본은 `ClusterFirst`이고 클러스터 도메인이 아닌 쿼리는 상위 DNS로 넘깁니다. 이름이 `Default`인 정책은 기본값이 아니고 노드 설정을 상속하며, `hostNetwork` Pod는 `ClusterFirstWithHostNet`을 줘야 합니다.

(공식 문서) DNS for Services and Pods 페이지는 kubelet이 Pod의 resolv.conf를 설정하고 예시로 `nameserver`, `search <namespace>.svc.cluster.local svc.cluster.local cluster.local`, `options ndots:5`를 보인다. 검색 목록으로 `data`가 `data.test.svc.cluster.local`로 확장된다고 한다. dnsPolicy는 `Default`(노드 설정 상속, 기본값이 아님), `ClusterFirst`(클러스터 도메인과 맞지 않는 쿼리는 상위 DNS로 전달, 지정하지 않으면 이것), `ClusterFirstWithHostNet`(hostNetwork Pod용, 아니면 Default처럼 동작), `None`(dnsConfig로 직접)이라고 한다. Debug Services 페이지는 `nameserver`가 클러스터의 DNS Service를 가리켜야 하고(kubelet `--cluster-dns`), 검색 목록이 로컬 네임스페이스, 전체 네임스페이스(`svc.cluster.local`), 클러스터(`cluster.local`) 순이어야 하며, `ndots`는 DNS 클라이언트 라이브러리가 검색 경로를 고려할 만큼 높아야 하는데 쿠버네티스가 만드는 모든 이름을 덮도록 기본 5라고 한다.
(보충) `ndots:5`가 점 5개 미만인 이름을 검색 목록으로 먼저 확장해 시도하라는 뜻이고 그래서 외부 도메인 조회에 실패 시도가 늘 수 있다는 설명은 resolv.conf의 일반 규칙을 옮긴 것으로 위 문서 페이지들이 직접 쓰지는 않는다.
(실험 확인) 2026-10-27 v1.36.1에서 Pod의 resolv.conf는 `nameserver 10.96.0.10`(`kube-system`의 `kube-dns` Service ClusterIP와 같음), `search exp-networkv.svc.cluster.local svc.cluster.local cluster.local`, `options ndots:5`였다. busybox `nslookup web`은 검색 목록의 다른 후보(`web.cluster.local`, `web.svc.cluster.local`)에 대해 NXDOMAIN을 출력한 뒤 `web.exp-networkv.svc.cluster.local`을 ClusterIP로 해석했다. `dnsPolicy`를 지정하지 않은 Pod는 위와 같이 클러스터 DNS를 썼다. `dnsPolicy: Default` Pod와 `hostNetwork: true`만 준 Pod(기본 `ClusterFirst`)는 노드의 네임서버(192.168.65.7)를 받아 클러스터 Service 이름을 해석하지 못했고, `hostNetwork: true`에 `ClusterFirstWithHostNet`을 주면 클러스터 DNS를 썼다. `dnsPolicy: None`에 `dnsConfig`(`ndots` 1)를 주면 그 값대로 resolv.conf가 만들어졌다.
