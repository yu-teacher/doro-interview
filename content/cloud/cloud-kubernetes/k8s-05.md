**모범 답변 (30~60초)**
Pod는 계속 만들어지고 사라져서 IP가 바뀌기 때문에, 호출하는 쪽이 개별 Pod 주소를 알 수 없습니다. Service는 셀렉터로 고른 Pod 묶음 앞에 안정적인 접근점을 두는 추상화입니다. `ClusterIP`는 기본값으로 클러스터 내부 IP만 부여해 클러스터 안에서만 접근됩니다. `NodePort`는 그 위에 모든 노드의 고정 포트를 열어 노드 IP와 그 포트로 밖에서 접근하게 하고, 기본 범위는 30000에서 32767입니다. `LoadBalancer`는 외부 로드 밸런서로 노출하는데, 쿠버네티스가 로드 밸런서를 직접 제공하지는 않고 클라우드 같은 연동 대상이 있어야 합니다. 외부 호스트명을 CNAME으로 매핑하는 `ExternalName`도 있습니다.

(공식 문서) Service 페이지는 Pod가 일시적 리소스이고 Pod마다 자기 IP를 가지므로 백엔드 집합이 바뀐다는 문제를 Service가 푼다고 설명한다. 유형으로 ClusterIP(클러스터 내부 IP, 기본값), NodePort(각 노드의 고정 포트로 노출, 기본 범위 30000-32767, ClusterIP 위에 구성), LoadBalancer(외부 로드 밸런서로 노출하되 쿠버네티스가 로드 밸런싱 컴포넌트를 직접 제공하지는 않음), ExternalName(CNAME 레코드를 돌려주며 프록시는 설정하지 않음)을 소개한다. 유형이 중첩 구조지만 LoadBalancer에서 NodePort 할당을 끄는 예외가 있다고 한다.
(실험 확인) kubectl v1.36.1 클라이언트의 `kubectl create service clusterip|nodeport|loadbalancer web --tcp=80:8080 --dry-run=client -o yaml`(클러스터 없이 출력만)은 각각 `type: ClusterIP`, `NodePort`, `LoadBalancer`와 `port: 80`, `targetPort: 8080`을 담은 매니페스트를 만들었고, `create service externalname`은 `type: ExternalName`과 `externalName`을 만들었다. 이어서 Kubernetes 1.36.1 클러스터에서 `kubectl expose`로 만든 ClusterIP·NodePort·LoadBalancer Service는 EndpointSlice에 같은 Pod 3개의 IP를 담았다. NodePort는 `80:31004/TCP`처럼 30000-32767 범위의 포트를 자동 할당받았고, `nodePort: 40000`을 직접 지정하자 `provided port is not in the valid range. The range of valid ports is 30000-32767`로 거부됐다. ClusterIP의 `nodePort`는 비어 있었고 ClusterIP 주소로는 호스트에서 접속되지 않은 반면(`curl` 코드 000), 노드 포트(`localhost:31004`)는 HTTP 200을 돌려줬다. LoadBalancer는 이 Docker Desktop 환경에서 EXTERNAL-IP가 `localhost`로 채워져 `localhost:8099`가 200을 돌려줬고(`8099:31549/TCP`처럼 NodePort도 함께 할당됐다), 이는 Docker Desktop이 연동 대상 역할을 한 것이다. ExternalName Service는 Pod 안에서 `ext.<네임스페이스>.svc.cluster.local` 조회가 `example.com`의 CNAME으로 응답했다. (2026-10-27 원문 확인)
