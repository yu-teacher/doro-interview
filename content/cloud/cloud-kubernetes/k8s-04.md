**모범 답변 (30~60초)**
Pod는 언제든 사라질 수 있는 일회성 리소스라서 직접 만들면 죽었을 때 아무도 다시 만들어 주지 않습니다. ReplicaSet은 지정한 수의 동일한 Pod가 항상 떠 있게 유지하고, Deployment는 그 ReplicaSet을 관리하면서 선언적 업데이트를 제공합니다. Pod 템플릿을 바꾸면 Deployment가 새 ReplicaSet을 만들어 점진적으로 늘리고 이전 ReplicaSet은 줄여 롤링 업데이트를 하며, 문제가 생기면 이전 리비전으로 롤백할 수 있습니다. 그래서 공식 문서도 ReplicaSet을 직접 다루기보다 Deployment를 쓰라고 권장합니다. 대상 Pod는 셀렉터와 레이블로 연결됩니다.

(공식 문서) Deployments 페이지는 Deployment가 Pod와 ReplicaSet의 선언적 업데이트를 제공하고, 롤아웃 시 새 ReplicaSet을 만들어 늘리면서 이전 것을 줄이며, 롤백·스케일·일시 정지 같은 용도에 쓴다고 설명한다. 또 Deployment가 소유한 ReplicaSet을 직접 관리하지 말라고 한다. ReplicaSet 페이지는 사용자 지정 업데이트 조율이 필요하거나 업데이트가 아예 필요 없는 경우가 아니면 Deployment를 쓰라고 권장하고, ReplicaSet이 Pod를 `metadata.ownerReferences`와 셀렉터로 식별한다고 설명한다. Pods 페이지는 Pod가 비교적 일시적이고 처분 가능한 존재라서 거의 직접 만들지 않는다고 한다.
(실험 확인) kubectl v1.36.1 클라이언트로 `kubectl create deployment web --image=nginx:1.27 --replicas=3 --dry-run=client -o yaml`을 실행하자(클러스터 없이 매니페스트만 출력), `spec.replicas: 3`, `selector.matchLabels`의 `app: web`, 같은 레이블을 가진 `template`이 만들어졌다. 이어서 Kubernetes 1.36.1 클러스터(Docker Desktop 단일 노드)에 적용하자 ReplicaSet 하나와 Pod 3개가 생겼고, ReplicaSet의 `ownerReferences` 종류는 `Deployment`, Pod의 것은 `ReplicaSet`이었다. Pod 하나를 지우자 몇 초 안에 새 Pod가 생겨 3개가 유지됐지만, `kubectl run`으로 직접 만든 Pod는 지운 뒤 다시 생기지 않았다. `kubectl scale`로 replicas를 4로 바꿔도 새 ReplicaSet 없이 기존 ReplicaSet의 개수만 바뀌었고 롤아웃 이력도 그대로였다. 템플릿을 바꾸자(`kubectl set env`) 새 ReplicaSet이 생기고 이전 ReplicaSet은 0개로 줄어 남았다.
