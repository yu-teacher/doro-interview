**모범 답변 (30~60초)**
쿠버네티스 오브젝트는 원하는 상태를 담은 `spec`을 선언하면 컨트롤 플레인이 실제 상태를 맞춰 줍니다. kubectl 관리 방식은 세 가지입니다. 명령형 명령(`kubectl create deployment`)은 라이브 오브젝트를 바로 바꾸지만 이력과 리뷰 수단이 없고, 명령형 오브젝트 구성(`create -f`, `replace -f`)은 파일을 쓰되 어떤 동작을 할지 직접 지정합니다. 선언형 구성(`kubectl apply -f`)은 파일이나 디렉터리를 주면 생성·수정을 kubectl이 알아서 판단하고, 관찰된 차이만 patch로 보내 파일에 없는 필드(다른 작성자가 붙인 레이블 등)를 보존합니다. 파일을 Git에 두고 `kubectl diff`로 확인한 뒤 적용하며, 한 오브젝트에는 한 기법만 써야 합니다.

(공식 문서) Kubernetes Object Management 페이지는 명령형 명령, 명령형 오브젝트 구성, 선언형 오브젝트 구성 세 기법을 비교하고, 한 오브젝트에 한 기법만 쓰라고 경고하며 섞으면 동작이 정의되지 않는다고 한다. 명령형 명령은 변경 이력·감사 추적·리뷰 연계가 없고, `replace`는 파일에 없는 변경을 버리며 LoadBalancer Service의 외부 주소처럼 클러스터가 따로 갱신하는 필드에는 맞지 않는다고 한다. 선언형은 replace 대신 patch API로 관찰된 차이만 써서 다른 작성자의 변경을 보존하고, `kubectl diff -f configs/` 후 `kubectl apply -f configs/`로 디렉터리 단위로 쓸 수 있다고 한다. Objects 페이지는 spec이 원하는 상태, status가 시스템이 갱신하는 현재 상태라고 설명한다.
(실험 확인) kubectl v1.36.1 클라이언트에서 `kubectl create deployment ... --dry-run=client -o yaml`은 클러스터 없이 매니페스트를 출력했지만, 그 파일에 `kubectl apply -f ... --dry-run=client`를 실행하자 API 서버(localhost:8080) 접속 실패로 오류가 났다. 오류 메시지는 스키마 검증용 OpenAPI 문서를 내려받지 못했다는 내용이었다(`--validate=false`를 쓰라는 안내가 붙었다). (이 결과는 클러스터에 접속할 수 없던 상태에서의 것이다.)
(실험 확인) Kubernetes 1.36.1 클러스터(Docker Desktop)에서는 같은 `apply --dry-run=client`가 `(dry run)`으로 성공했다. `kubectl apply -f`로 만든 Deployment에 `kubectl scale`(replicas 5)과 `kubectl label owner=other`를 하고 같은 파일을 다시 apply하자 `owner` 레이블은 남았지만 replicas는 파일 값(3)으로 되돌아갔다. 즉 파일에 적힌 필드는 파일이 이기고 파일에 없는 필드만 보존된다. 파일의 replicas를 4로 고치자 `kubectl diff`가 `-replicas: 3`, `+replicas: 4`(와 `generation` 줄)를 보여 줬고 apply가 4로 바꿨다. `kubectl replace -f`는 파일 값으로 통째로 바꿔 파일에 없던 레이블 `owner`와 어노테이션 `note`가 사라졌고 `last-applied-configuration` 어노테이션도 없어졌다. 이후 apply는 `missing the kubectl.kubernetes.io/last-applied-configuration annotation` 경고를 내고 어노테이션을 자동으로 붙이며 진행했다. `kubectl create deployment`로 만든 오브젝트에 파일을 apply해도 같은 경고가 나왔고(`configured`), 이미 있는 오브젝트에 `create -f`를 하면 `AlreadyExists`였다.
