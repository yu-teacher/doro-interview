**모범 답변 (30~60초)**
Ingress는 클러스터 밖의 HTTP·HTTPS 요청을 호스트명과 경로 규칙에 따라 안쪽 Service로 보내는 규칙을 정의하는 리소스입니다. 그런데 리소스만 만들어서는 아무 효과가 없고, 그것을 실제로 구현하는 Ingress 컨트롤러가 클러스터에 있어야 합니다. 임의의 포트나 HTTP 이외 프로토콜은 다루지 않아 그런 경우는 NodePort나 LoadBalancer Service를 씁니다. Gateway API는 CRD로 제공되는 확장 API 묶음으로, 인프라 제공자·클러스터 운영자·앱 개발자 역할에 맞춰 `GatewayClass`, `Gateway`, `HTTPRoute` 같은 리소스로 나눕니다. 쿠버네티스 프로젝트는 Ingress보다 Gateway를 권장하며 Ingress API는 동결되었습니다.

(공식 문서) Ingress 페이지는 Ingress가 클러스터 밖에서 안쪽 Service로의 HTTP·HTTPS 경로를 규칙으로 관리하고, Ingress 컨트롤러가 이를 충족시키며 컨트롤러 없이 리소스만 만들면 효과가 없다고 한다. 임의의 포트·프로토콜은 노출하지 않으며 그런 경우 NodePort나 LoadBalancer 유형을 쓴다고 하고, 쿠버네티스 프로젝트가 Ingress 대신 Gateway를 권장한다고 쓰며 Ingress API는 동결되어 더 이상 변경이 없지만 제거 계획도 없다고 한다. Gateway API 페이지는 이를 역할 지향·이식 가능·표현력 있는·확장 가능한 API 묶음으로 소개하고, 안정 버전 kind로 GatewayClass, Gateway, HTTPRoute, GRPCRoute를 들며, 헤더 기반 매칭이나 가중치 같은 Ingress에서 어노테이션으로만 가능하던 기능을 표현할 수 있다고 한다. Service 페이지는 Ingress가 Service 유형이 아니라고 설명한다. 클러스터가 없어 실험하지 않았다. (2026-10-27 원문 확인)
