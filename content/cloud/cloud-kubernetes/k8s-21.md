**모범 답변 (30~60초)**
`CrashLoopBackOff`는 컨테이너가 시작하고 실패하고 재시작하기를 반복해서 kubelet이 재시작 지연(백오프)을 적용 중이라는 표시이고, 상태 자체가 아니라 `kubectl`의 표시 필드입니다. 지연은 10초, 20초, 40초처럼 두 배씩 늘어 최대 300초까지 가고, 컨테이너가 10분 넘게 정상 실행되면 초기화됩니다. 원인은 앱 오류로 인한 종료, 잘못된 환경 변수나 누락된 설정 파일 같은 구성 오류, 메모리 같은 자원 부족, 앱이 제때 뜨지 못해서 생기는 프로브 실패 등입니다. 그래서 liveness나 startup 프로브가 너무 빡빡하면 멀쩡한 앱도 죽고 다시 뜨기를 반복합니다. `kubectl logs`와 `kubectl describe pod`로 로그와 이벤트를 먼저 봅니다.

(공식 문서) Pod Lifecycle 페이지는 컨테이너가 종료된 뒤 kubelet이 10초, 20초, 40초 식의 지수 백오프 지연으로 재시작하며 상한이 300초(5분)이고 문제 없이 10분 실행되면 타이머를 초기화한다고 설명한다. `CrashLoopBackOff`는 kubectl이 보여 주는 Status 표시이며 Pod phase와 혼동하지 말라고 하고, 원인으로 애플리케이션 오류, 환경 변수·설정 파일 같은 구성 오류, CPU·메모리 부족, 앱이 제때 서비스를 시작하지 못해 헬스 체크가 실패하는 경우, liveness·startup 프로브 실패를 들며 조사에 `kubectl logs`, `kubectl describe pod`로 이벤트 확인, 설정·리소스 검토를 권한다. Configure Probes 페이지는 시작이 느린 앱에 liveness만 빡빡하게 두는 문제를 startup 프로브로 푼다고 한다. 알파 기능(백오프 감소, 1.37 기준)과 kubelet 설정으로 상한을 조정하는 기능(1.35 beta)이 있다는 항목은 읽었으나 이 답변에는 쓰지 않았다. (2026-10-27 원문 확인)
(실험 확인) Kubernetes 1.36.1 클러스터(Docker Desktop)에서 시작하자마자 종료 코드 1로 끝나는 Pod(`restartPolicy` 기본 Always)를 띄우고 컨테이너 시작 시각(초)을 기록했다. 재시작 간격은 1, 13, 30, 53, 88, 168초였다(앞 간격은 첫 재시작이 거의 즉시이고 이후 대략 10, 20, 40, 80, 160초의 대기에 컨테이너 실행·kubelet 동기화 시간이 더해진 모양이며, 정확한 초는 환경 의존이다). 일곱 번째 시작에서 컨테이너를 630초(10분 초과) 정상 실행한 뒤 종료하자 다음 재시작이 2초, 그다음이 14초 간격으로 돌아와 백오프가 초기화됐다. 300초 상한은 시간이 걸려 확인하지 않았다. `kubectl get pod`의 STATUS는 종료 뒤 `Error`로 보이다가 `CrashLoopBackOff`로 바뀌었는데, 바뀌는 시점은 일정하지 않아 재검증에서는 약 40초 대기의 거의 전부를 `Error`(컨테이너 상태 `terminated`)로 보낸 회차도 있었다. 어느 경우든 `status.phase`는 `Running`이었으며 `CrashLoopBackOff`는 컨테이너 상태의 `waiting.reason`에 있었다. liveness 프로브를 항상 400을 돌려주는 경로로 건 nginx Pod는 이벤트 `Container nginx failed liveness probe, will be restarted` 뒤 재시작이 쌓이며 `CrashLoopBackOff`가 됐고, 직전 종료 상태는 종료 코드 0(`Completed`)이었다. 즉 앱이 멀쩡해도 프로브 설정만으로 재시작 루프가 생겼다. 이벤트에서는 `Back-off restarting failed container ... in pod ...` 경고가 확인됐다.
