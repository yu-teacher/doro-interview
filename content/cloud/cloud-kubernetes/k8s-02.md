**모범 답변 (30~60초)**
클러스터는 컨트롤 플레인과 워커 노드로 나뉩니다. 컨트롤 플레인에서 `kube-apiserver`는 쿠버네티스 API를 제공하는 앞단이고, `etcd`는 클러스터의 모든 데이터를 저장하는 키-값 저장소입니다. `kube-scheduler`는 아직 노드가 정해지지 않은 Pod를 적절한 노드에 배정하고, `kube-controller-manager`는 여러 컨트롤러를 한 프로세스로 실행합니다. 각 노드에서는 `kubelet`이 Pod의 컨테이너가 실행되고 건강한지 보장하고, `kube-proxy`가 Service를 구현하는 네트워크 규칙을 관리하며, 실제 컨테이너 실행은 containerd 같은 컨테이너 런타임이 맡습니다.

(공식 문서) Components 페이지와 Cluster Architecture 페이지는 컨트롤 플레인 구성요소로 kube-apiserver, etcd, kube-scheduler, kube-controller-manager, 선택 사항인 cloud-controller-manager를, 노드 구성요소로 kubelet, kube-proxy, 컨테이너 런타임을 든다. API 서버를 컨트롤 플레인의 프런트엔드로, etcd를 모든 클러스터 데이터의 백킹 스토어로, 스케줄러를 노드가 없는 새 Pod에 노드를 고르는 구성요소로 설명한다. kubelet은 PodSpec에 적힌 컨테이너가 실행되고 건강한지 보장하며 쿠버네티스가 만들지 않은 컨테이너는 관리하지 않는다고 한다. kube-proxy는 선택 사항으로, Service 동작을 자체 구현하는 네트워크 플러그인을 쓰면 필요 없다고 한다. 클러스터가 없어 실험하지 않았다.
