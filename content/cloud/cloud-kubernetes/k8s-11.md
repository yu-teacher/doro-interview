**모범 답변 (30~60초)**
`requests`는 그 컨테이너가 필요로 하는 양으로, 스케줄러가 노드를 고를 때 쓰고 kubelet은 최소 그만큼을 확보해 둡니다. `limits`는 상한으로, kubelet과 컨테이너 런타임이 설정하고 리눅스에서는 커널이 cgroup으로 강제합니다. 초과했을 때 CPU는 스로틀링으로 사용량이 제한될 뿐 컨테이너가 죽지 않습니다. 메모리는 OOM kill로 강제되어 한도를 넘으면 커널이 컨테이너를 종료할 수 있고, 이는 메모리 압박이 감지될 때 반응적으로 일어납니다. limit만 지정하고 request를 안 주면 request가 limit과 같은 값으로 취급됩니다. 노드 여유가 있으면 request보다 더 쓰는 것도 허용됩니다.

(공식 문서) Resource Management for Pods and Containers 페이지는 request를 스케줄러가 노드 선택에 쓰고 kubelet이 최소한 그만큼을 컨테이너용으로 예약한다고 설명한다. limit은 kubelet이 적용하고 커널이 강제하며, CPU limit은 스로틀링으로, 메모리 limit은 OOM 종료로 강제된다고 한다. 메모리 종료는 커널이 메모리 압박을 감지할 때만 일어나므로 반응적이고, 컨테이너 런타임은 CPU 과다 사용으로 Pod나 컨테이너를 종료하지 않는다고 한다. limit만 지정하면 기본 request가 적용되지 않은 경우 limit 값이 request로 복사된다고 한다. 같은 페이지의 트러블슈팅 예시에서 상태 `OOMKilled`, 종료 코드 137이 나타난다. (2026-10-27 원문 확인)
(실험 확인) Kubernetes 1.36.1 클러스터(Docker Desktop, 노드 allocatable CPU 15, 메모리 약 7.6GiB)에서 `requests.cpu: 500m`, `limits.cpu: 100m`처럼 request가 limit보다 크면 API가 `must be less than or equal to cpu limit of 100m`으로 거부했다. limit만 적은 Pod는 저장된 spec에서 request가 limit과 같은 값으로 채워졌다. 메모리 limit 64Mi에서 node가 8MiB씩 계속 할당한 Pod는 48MiB 할당 직후 `OOMKilled`, 종료 코드 137로 끝났다. 반면 request 16Mi, limit 256Mi인 Pod는 request보다 많은 메모리(RSS 약 70MiB)를 쓰고도 정상 종료했다. CPU limit 100m인 컨테이너를 15초간 바쁘게 돌리자 cgroup `cpu.max`가 `10000 100000`이었고 `cpu.stat`의 `nr_throttled`가 `nr_periods`와 같은 141, CPU 사용은 약 1.4초(15초의 약 9%)였으며 컨테이너는 죽지 않고 정상 종료했다. 노드에 없는 크기의 request(CPU 1000, 메모리 1Ti)를 준 Pod는 `Pending`이고 `FailedScheduling: 0/1 nodes are available: 1 Insufficient cpu, 1 Insufficient memory`였다.
