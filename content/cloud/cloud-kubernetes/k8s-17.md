**모범 답변 (30~60초)**
아니요. 기본 설정에서 Secret은 API 서버의 데이터 저장소인 etcd에 암호화 없이 저장됩니다. 매니페스트에서 보이는 base64는 암호화가 아니라 인코딩이라 누구나 되돌릴 수 있습니다. 그래서 API 접근 권한이나 etcd 접근 권한이 있으면 값을 읽을 수 있고, 네임스페이스에 Pod나 Deployment를 만들 수 있는 사람도 그 Pod로 같은 네임스페이스의 Secret을 읽을 수 있습니다. 안전하게 쓰려면 저장 시 암호화를 켜고, RBAC로 Secret 접근을 최소 권한으로 제한하고, 필요한 컨테이너에만 노출하며, 외부 시크릿 저장소 연동을 고려해야 합니다.

(공식 문서) Secrets 페이지의 경고는 Secret이 기본적으로 etcd에 암호화되지 않은 채 저장되고, API 접근 권한자나 etcd 접근 권한자가 읽거나 수정할 수 있으며, 네임스페이스에서 Pod(간접적으로는 Deployment)를 만들 수 있으면 그 네임스페이스의 모든 Secret을 읽을 수 있다고 한다. 안전하게 쓰려면 저장 시 암호화, 최소 권한 RBAC, 특정 컨테이너로 접근 제한, 외부 Secret 저장소 고려를 하라고 한다. 같은 페이지는 base64 값에 대해 가려질 뿐 비밀이 아니라고 하고 TLS 예시 주석에서도 base64가 실질적인 기밀성을 제공하지 않는다고 쓴다. Encrypting Confidential Data at Rest 페이지는 `--encryption-provider-config` 없이 kube-apiserver를 돌리면 저장 시 암호화가 꺼져 있다고 설명한다.
(실험 확인) kubectl v1.36.1 클라이언트의 `kubectl create secret generic db --from-literal=password=... --dry-run=client -o yaml` 출력의 `data.password`는 base64 문자열이었고, `base64 -d`로 원래 평문이 그대로 복원되었다. 클러스터의 etcd 저장 상태는 확인하지 않았다. (2026-10-27 원문 확인)
