**모범 답변 (30~60초)**
CPU는 압축 가능한 자원이라 limit에 다가가면 커널이 CPU 사용을 제한할 뿐 컨테이너를 죽이지 않습니다. 메모리는 한 번 쓴 것을 회수할 수 없어서 limit을 넘으면 커널이 OOM으로 컨테이너를 종료하고, 쿠버네티스에는 `OOMKilled`로 나타나며 공식 문서 예시에서는 종료 코드 137입니다. QoS 클래스는 requests와 limits 설정으로 정해집니다. 모든 컨테이너에 CPU·메모리 request와 limit이 있고 서로 같으면 `Guaranteed`, 일부라도 있으면 `Burstable`, 하나도 없으면 `BestEffort`입니다. 노드 자원이 부족할 때의 축출 순서가 BestEffort, Burstable, Guaranteed 순이고, limit 초과로 죽는 것은 QoS와 별개입니다.

(공식 문서) Resource Management 페이지는 CPU limit이 스로틀링으로, 메모리 limit이 커널의 OOM kill로 강제되며 컨테이너 런타임은 과도한 CPU 사용으로 컨테이너를 종료하지 않는다고 한다. 예시 출력에서 `OOMKilled`와 종료 코드 137이 보인다(종료 코드 137은 문서 예시 값이며 모든 경우에 137이라고 단정하지 않는다). Pod QoS 페이지는 Guaranteed가 모든 컨테이너에 CPU·메모리 request와 limit이 있고 각각 같은 경우, Burstable이 그보다 느슨하지만 request나 limit이 하나라도 있는 경우, BestEffort가 아무것도 없는 경우이며, 노드 압박 시 BestEffort, Burstable, Guaranteed 순으로 축출하고 압박 축출 때는 request를 넘긴 Pod만 후보가 된다고 설명한다. 같은 페이지는 limit을 넘긴 컨테이너가 QoS 클래스와 무관하게 kubelet에 의해 종료·재시작되고, Pod 수준 리소스를 쓰면 Guaranteed 판정이 Pod 수준 request·limit 기준(1.34 beta)이라고 한다.
(보충) 메모리가 "압축 불가능하다"는 설명은 공식 문서에서 확인하지 않은 일반적 설명이고 실험으로도 재현하지 않았다. (2026-10-27 원문 확인)
(실험 확인) Kubernetes 1.36.1 클러스터(Docker Desktop)에서 QoS 클래스를 확인했다. CPU·메모리 request와 limit을 같게 준 Pod는 `Guaranteed`, request만 CPU로 준 Pod와 request와 limit이 다른 Pod는 `Burstable`, 아무것도 안 준 Pod는 `BestEffort`였다. limit만 준 Pod는 request가 limit으로 채워져 `Guaranteed`가 됐고, 메모리 request·limit만 같고 CPU가 없는 Pod는 `Burstable`이었다. 메모리 limit 64Mi 컨테이너는 할당을 이어 가다 `OOMKilled`, 종료 코드 137로 끝났고, CPU limit 100m 컨테이너는 죽지 않고 `nr_throttled`가 쌓였다. Corretto 17에서 메모리 limit 512Mi일 때 `Runtime.maxMemory()`가 123MiB로 컨테이너 limit의 약 1/4였다. 메모리 limit 160Mi에서 `-Xmx1g`로 힙에 300MB까지 할당하는 자바는 110MiB쯤에서 `OOMKilled`(137)가 됐고, `-Xmx64m`으로 힙을 limit보다 작게 잡으면 JVM이 `OutOfMemoryError: Java heap space`로 스스로 종료했다(종료 코드 1, `OOMKilled` 아님). 힙은 `-Xmx64m`인데 `-XX:MaxDirectMemorySize=1g`로 다이렉트 버퍼를 300MB까지 쓰는 자바는 110MiB쯤에서 `OOMKilled`(137)가 되어, 힙이 limit보다 작아도 힙 외 메모리 때문에 죽을 수 있음을 확인했다. 수치는 이 환경의 값이다.
