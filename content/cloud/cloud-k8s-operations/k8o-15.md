**모범 답변 (30~60초)**
앱이 아직 시작 중이라 프로브가 실패하면 kubelet은 이를 죽은 것으로 보고, 실패가 `failureThreshold`만큼 쌓이면 컨테이너를 죽여 재시작합니다. 재시작된 컨테이너도 또 20초가 걸리니 영원히 시작을 못 끝내고 재시작을 반복하는, 앱은 멀쩡한데 프로브가 죽이는 전형적인 실수입니다. 해결은 `startupProbe`를 두는 것으로, `failureThreshold * periodSeconds`가 최악의 시작 시간을 덮도록 정하면 성공할 때까지 liveness가 실행되지 않고, 성공한 뒤에는 liveness가 교착을 빠르게 잡아냅니다. 문서도 시작이 느린 앱의 liveness를 느슨하게 잡으면 빠른 교착 감지가 희생되므로 startup 프로브를 쓰라고 합니다. `initialDelaySeconds`는 고정 지연일 뿐입니다.

```yaml
startupProbe:
  exec: {command: ["cat","/tmp/ready"]}
  periodSeconds: 3
  failureThreshold: 20      # 최대 60초 동안 시작을 기다림
livenessProbe:
  exec: {command: ["cat","/tmp/ready"]}
  periodSeconds: 3
  failureThreshold: 2
```

(공식 문서) Configure Probes 페이지는 시작이 느린 앱에서 교착을 빨리 잡으려는 liveness 파라미터를 훼손하지 않고 설정하기 어렵다고 하고, 같은 검사에 `failureThreshold * periodSeconds`가 최악의 시작 시간을 덮는 startup 프로브를 두라고 한다(예: 30회 곱하기 10초로 300초). startup 프로브가 한 번 성공하면 liveness가 이어받고, 끝내 성공하지 못하면 컨테이너가 죽어 `restartPolicy`를 따른다고 한다. 또 liveness와 readiness가 서로의 성공에 의존하지 않으므로 기다리려면 `initialDelaySeconds`나 startup 프로브를 쓰라고 한다. Pod Lifecycle 페이지는 startup 프로브가 있으면 성공 전까지 다른 프로브가 실행되지 않는다고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 `sleep 20; touch /tmp/ready`로 20초 뒤에야 준비되는 컨테이너에 `cat /tmp/ready` liveness(`initialDelaySeconds: 3`, `periodSeconds: 3`, `failureThreshold: 2`)를 두자 2분 20초 사이 RESTARTS가 3까지 올랐고 이벤트에 `Liveness probe failed: cat: can't open '/tmp/ready': No such file or directory`와 `Container c failed liveness probe, will be restarted`가 반복되었다. 같은 컨테이너에 startup 프로브(`periodSeconds: 3`, `failureThreshold: 20`)와 같은 liveness를 함께 두면 2분 20초 뒤에도 `1/1 Running`, RESTARTS 0이었고 이벤트에는 시작 중의 `Startup probe failed`만 있었다(liveness 실패 이벤트 없음). 반례로 startup 프로브의 예산이 짧으면(`failureThreshold: 3`, `periodSeconds: 3`) 컨테이너가 `Container c failed startup probe, will be restarted`로 죽어 재시작이 반복되었다. `initialDelaySeconds: 25`인 liveness만 둔 경우는 2분 20초 동안 RESTARTS 0이었다(고정 지연으로도 이 앱은 통과하지만 시작 시간이 늘면 다시 깨진다).
