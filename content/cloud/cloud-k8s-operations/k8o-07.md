**모범 답변 (30~60초)**
`OOMKilled`는 컨테이너가 자기 메모리 limit을 넘어 커널이 그 프로세스를 죽인 경우입니다. 파드는 그대로 있고 컨테이너만 종료 코드 137과 reason `OOMKilled`를 남기며, 재시작 정책에 따라 다시 뜹니다. 반면 `Evicted`는 노드 자원 압박이나 임시 스토리지 한도 초과 때 kubelet이 파드 자체를 종료하는 것으로, 파드 phase가 `Failed`, 이유가 `Evicted`가 되고 컨트롤러가 새 파드를 만듭니다. 종료 코드로는 구분되지 않습니다. 축출된 컨테이너도 137이었지만 reason은 `Error`였습니다. describe에서 컨테이너 `Last State`가 `OOMKilled`인지, 파드 `Reason`이 `Evicted`인지로 가릅니다.

(공식 문서) Manage Resources 페이지는 메모리 limit이 OOM kill로 커널에 의해 강제되고(메모리 압박이 감지될 때만 죽으므로 반응적이다), CPU는 스로틀링되며 컨테이너 런타임이 CPU 초과로 컨테이너를 죽이지는 않는다고 설명한다. 컨테이너가 메모리 request를 넘고 노드 메모리가 부족해지면 파드가 축출될 가능성이 높다고도 한다. Node-pressure Eviction 페이지는 축출 때 kubelet이 선택된 파드의 phase를 `Failed`로 설정하고 종료하며, 워크로드 오브젝트가 있으면 컨트롤 플레인이 축출된 파드를 대신할 새 파드를 만든다고 한다. Local ephemeral storage 페이지는 파드가 허용된 임시 스토리지보다 많이 쓰면 kubelet이 축출 신호를 설정해 파드 축출을 유발하고, 컨테이너 단위 격리에서는 쓰기 레이어와 로그 사용량이 limit을 넘으면 파드를 축출 대상으로 표시한다고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 (1) 메모리 limit 50Mi 컨테이너가 200MB 문자열을 만들자 `OOMKilled`, exit code 137이 기록되고 파드 phase는 `Running`인 채 RESTARTS가 올라갔다. 같은 일을 `restartPolicy: Never`로 하면 파드 phase는 `Failed`가 되지만 파드의 `status.reason`은 비어 있고 컨테이너 reason이 `OOMKilled`였다. (2) `ephemeral-storage` limit 20Mi 컨테이너가 /tmp에 50MB를 쓰자 10여 초 만에 파드가 phase `Failed`, reason `Evicted`, 메시지 `Pod ephemeral local storage usage exceeds the total limit of containers 20Mi.`가 되었고 파드 오브젝트가 남았다. 그 파드의 컨테이너 상태는 exit code 137, reason `Error`였다(`OOMKilled`가 아니다). 이때 `kubectl get`의 STATUS 열은 `Evicted`가 아니라 `Error`로 표시되었으므로 STATUS 문구만 믿지 말고 describe나 `-o yaml`로 reason을 확인해야 한다. (3) 같은 설정을 Deployment로 띄우자 축출된 파드는 `Failed`/`Evicted`로 남은 채 컨트롤러가 새 파드를 계속 만들어, 1분 사이 축출된 파드 4개가 쌓이고 새 파드가 `Running`이었다. 노드 메모리 압박으로 인한 축출은 노드 설정을 건드려야 해서 실험하지 않았고 문서 근거로만 적었다.
