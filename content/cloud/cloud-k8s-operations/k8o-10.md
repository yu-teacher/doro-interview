**모범 답변 (30~60초)**
내 로컬 포트로 들어온 TCP 연결을 클러스터 안 파드의 포트로 전달해 주는 명령입니다. Service나 Ingress를 만들지 않고도 DB나 웹 앱에 로컬에서 잠깐 붙어 보거나 디버깅할 때 씁니다. `deployment/이름`이나 `service/이름`을 지정해도 결국 그 리소스가 고른 파드 하나에 연결될 뿐 부하 분산은 하지 않고, 그 파드가 종료되면 포워딩이 끊겨 다시 실행해야 합니다. 지원은 TCP뿐이고, 권한은 파드의 `portforward` 서브리소스에 대한 RBAC로 통제되며 네트워크 수준 통제를 우회할 수 있어서 운영 노출 수단이 아니라 임시 진단용입니다.

```bash
kubectl port-forward deployment/web 8080:80   # 로컬 8080 -> 파드 80
curl localhost:8080/
```

(공식 문서) Use Port Forwarding to Access Applications in a Cluster 페이지는 파드·deployment·service 어느 것을 지정해도 되고 명령이 반환되지 않으며, `kubectl port-forward`가 TCP 포트만 지원하고, 접근 권한이 RBAC로 통제되어 대상 리소스와 `portforward` 서브리소스에 대한 권한(예: pods에 get, pods/portforward에 create)이 필요하며 관리자는 포트 포워딩이 네트워크 통제를 우회할 수 있으니 권한을 신중히 제한해야 한다고 설명한다. kubectl port-forward 레퍼런스는 여러 파드가 일치하면 자동으로 하나가 선택되고 선택된 파드가 종료되면 포워딩 세션이 끝나 명령을 다시 실행해야 한다고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 `kubectl port-forward <파드> 18080:80` 후 `curl localhost:18080/`가 HTTP 200을 반환했고 로그에 `Handling connection for 18080`이 찍혔다(기본으로 `127.0.0.1`과 `[::1]`에만 열렸다). 파드 2개짜리 Deployment를 `deployment/pf`로 지정해 연결하고 요청 10개를 보내자 모두 한 파드의 로그에만 나타났고 다른 파드는 0개였다. 그 파드를 지우자 포워딩이 끝났고(`error forwarding port 80 to pod ...: container not running`, `error: lost connection to pod`) 새로 생긴 파드로 옮겨 가지 않았다. `get pods`만 허용하는 Role로 `--as`를 써서 실행하면 `cannot create resource "pods/portforward"`로 거부되었고, `pods/portforward`에 `create`를 추가하자 같은 명령이 200을 반환했다.
