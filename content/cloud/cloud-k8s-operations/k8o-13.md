**모범 답변 (30~60초)**
`create`는 오브젝트가 없을 때 만드는 명령형이라 이미 있으면 `AlreadyExists`로 실패합니다. `apply`는 선언형으로 없으면 만들고 있으면 패치하며, 적용한 매니페스트를 `last-applied-configuration` 어노테이션에 저장합니다. 다음 apply 때는 지난 적용본, 이번 매니페스트, 실제 상태를 비교해 매니페스트에서 빠진 필드는 지우고 값이 달라진 필드는 덮어쓰되, 매니페스트에 없던 필드를 누가 직접 바꾼 값은 남겨 둡니다. 그래서 매니페스트에 `replicas`가 적혀 있으면 직접 `scale`한 값이 apply로 되돌려지고, 처음부터 적지 않았다면 유지됩니다. 적용 전에는 `kubectl diff`로 바뀔 내용을 미리 봅니다(기본인 클라이언트 측 apply 기준).

(공식 문서) Object Management 페이지는 명령형 객체 설정의 `kubectl create -f`와 선언형의 `kubectl apply`를 구분하고, 선언형은 다른 작성자가 만든 변경을 설정 파일에 병합하지 않아도 유지한다고 하며(patch 연산을 쓰기 때문), 한 오브젝트에는 하나의 관리 기법만 쓰라고 경고한다. Declarative Management 페이지는 apply가 설정 파일, 라이브 설정, `last-applied-configuration` 어노테이션으로 패치를 계산하고, last-applied에는 있는데 파일에서 빠진 필드는 삭제하고 값이 다른 필드는 설정한다고 설명한다. 같은 페이지의 예시는 `kubectl scale`로 바꾼 replicas가 last-applied에 없으면 이후 apply에서 유지된다고 보여 주고, `kubectl diff`가 apply가 만들 변경을 미리 보여 준다고 한다. kubectl diff 레퍼런스는 종료 코드 0이 차이 없음, 1이 차이 있음, 1 초과가 오류라고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 같은 매니페스트에 `kubectl create`를 다시 하자 `Error from server (AlreadyExists): ... deployments.apps "ap" already exists`였다. `create`로 만든 오브젝트에 `kubectl apply`를 하면 `missing the kubectl.kubernetes.io/last-applied-configuration annotation` 경고가 나오고 어노테이션이 자동으로 붙어 적용되었다. 매니페스트가 replicas 2인데 live가 5이던 Deployment에 `kubectl diff`는 `-  replicas: 5`, `+  replicas: 2`를 보여 주고 종료 코드 1이었으며(차이가 없으면 0) apply 후 replicas가 2가 되었다. 레이블 `team`, `tier`를 매니페스트에 넣어 apply한 뒤 `manual=1` 레이블을 직접 붙이고 `tier`만 뺀 매니페스트를 apply하자 `tier`는 삭제되고 `manual`은 남았다. 한편 `labels` 항목 전체를 매니페스트에서 지운 채 apply한 뒤에는 `manual`까지 포함해 레이블이 모두 비었다(이유는 조사하지 않았고 관찰만 적는다). replicas가 처음부터 매니페스트에 없던 Deployment는 `kubectl scale` 값 7이 apply 뒤에도 유지되었지만, replicas가 있던 매니페스트로 apply한 뒤 그 줄을 지운 매니페스트로 다시 apply하면 live 값이 기본값 1로 돌아갔다(last-applied에 있던 필드가 파일에서 빠졌기 때문). `kubectl apply --server-side`는 `scale`로 바꿔 둔 replicas에 대해 `Apply failed with 1 conflict: conflict with "kubectl" with subresource "scale"` 오류를 냈다(서버 측 apply는 필드 관리자 방식으로 달라서 위 설명은 기본 apply 기준).
