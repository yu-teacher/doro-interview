**모범 답변 (30~60초)**
Deployment의 리비전은 파드 템플릿(`.spec.template`)이 바뀔 때만 만들어지므로, `rollout undo`는 파드 템플릿만 이전 리비전 값으로 되돌립니다. 그래서 중간에 `kubectl scale`로 바꾼 replicas 같은 다른 필드는 그대로 유지됩니다. 되돌린 결과도 새 리비전으로 기록되어 이전 리비전 번호가 최신 번호로 옮겨 갑니다. 이전 ReplicaSet이 `revisionHistoryLimit` 때문에 이미 정리됐다면 돌아갈 수 없고, 특정 리비전은 `--to-revision`으로 고릅니다. 또 `kubectl apply`로 관리 중이라면 undo는 매니페스트 파일을 바꾸지 않아 다음 apply가 다시 문제 버전을 덮어쓸 수 있으니 매니페스트도 함께 되돌려야 합니다.

(공식 문서) Deployment 페이지의 Rolling Back 절은 리비전이 파드 템플릿이 바뀔 때만 생기고 스케일 같은 다른 변경은 리비전을 만들지 않으며, 그래서 이전 리비전으로 롤백할 때 파드 템플릿 부분만 되돌려진다고 설명한다. `kubectl rollout undo`와 `--to-revision`, 롤백 시 `DeploymentRollback` 이벤트가 생성된다는 것, `.spec.revisionHistoryLimit`(기본 10)이 보존할 이전 ReplicaSet 수이고 0이면 롤백할 수 없다는 것, CHANGE-CAUSE가 `kubernetes.io/change-cause` 어노테이션에서 복사된다는 것도 설명한다. kubectl rollout undo 레퍼런스에 `--to-revision` 옵션이 있다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 replicas 4 Deployment에 나쁜 이미지를 배포한 뒤 `kubectl scale --replicas=6`을 하고 `kubectl rollout undo deploy/wd`를 실행하자 롤백이 끝난 뒤 replicas는 6으로 유지되고 이미지만 원래 태그로 돌아왔다. `scale`과 Deployment 자체(템플릿 밖)에 레이블을 붙이는 일은 리비전 이력을 늘리지 않았다. 리비전 이력은 1, 2번에서 `2`(나쁜 이미지), `3`(원래 이미지)으로 바뀌어 리비전 1이 3으로 옮겨 갔다(문서의 `Each rollback updates the revision of the Deployment`와 같은 결과). 이 Deployment는 `kubectl apply`로 만든 것이라 undo 시 `Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation ...` 경고가 출력되었고, undo 뒤 나쁜 이미지가 적힌 매니페스트를 다시 `kubectl apply`하자 이미지가 도로 나쁜 값이 되었다(이때 리비전은 3, 4로 이어졌다). `revisionHistoryLimit: 1`인 Deployment에서 템플릿을 세 번 바꾼 뒤 이력은 3, 4번만 남았고 `kubectl rollout undo --to-revision=1`은 `error: unable to find specified revision 1 in history`로 실패했다. 문서 본문 예시에는 롤백 때 `DeploymentRollback` 이벤트가 생긴다고 나오지만, 이 클러스터(v1.36.1)에서 `kubectl rollout undo` 뒤 `kubectl describe deploy`와 `kubectl get events`에는 그 이벤트가 없었고 `ScalingReplicaSet` 이벤트만 있었다.
