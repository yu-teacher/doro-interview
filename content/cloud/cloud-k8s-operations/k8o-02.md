**모범 답변 (30~60초)**
`Pending`은 파드가 클러스터에 접수됐지만 컨테이너 실행 준비가 끝나지 않았다는 단계입니다. 가장 흔한 경우는 스케줄러가 배치할 노드를 못 찾은 것으로, `kubectl describe pod`의 Events에 `FailedScheduling`과 이유가 나옵니다. 보통 `resources.requests`가 어느 노드의 남은 용량보다 크거나, 노드의 taint를 견디지 못하거나, `nodeSelector`에 맞는 노드가 없는 경우입니다. 컨테이너가 아직 만들어지지 않았으니 `logs`로는 아무것도 볼 수 없습니다. 요청량을 줄이거나 노드를 늘리거나 조건을 고쳐 해결하고, 노드에 배정된 뒤 이미지를 받는 시간도 문서상 Pending 단계에 포함됩니다.

```yaml
# 노드에 없는 만큼 요청해 Pending을 일부러 만든 파드
resources:
  requests: {cpu: "100", memory: 1Ti}
```

(공식 문서) Debug Pods 페이지는 Pending이 노드에 스케줄할 수 없다는 뜻이고 흔한 원인이 자원 부족과 `hostPort` 사용이라 하며 describe의 스케줄러 메시지를 보라고 한다. Debug Running Pods 페이지는 파드가 어느 노드에도 맞지 않는 경우(자원 요청 초과, 맞는 노드가 없는 레이블 선택자)를 이벤트로 알아낸다고 설명한다. Manage Resources 페이지의 Troubleshooting 절은 `FailedScheduling` 이벤트가 나오면 노드 추가, 불필요한 파드 정리, 파드가 모든 노드보다 큰지 확인, 노드 taint 확인을 해 보라고 한다. Pod Lifecycle 페이지는 Pending phase가 스케줄을 기다리는 시간과 이미지를 내려받는 시간을 포함한다고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 요청이 cpu 100, memory 1Ti인 파드는 `Pending`으로 남았고 이벤트가 `FailedScheduling`, 메시지 `0/1 nodes are available: 1 Insufficient cpu, 1 Insufficient memory.`(뒤에 선점 불가 안내가 붙음)였다. `nodeSelector`에 없는 레이블을 준 파드도 `Pending`이었고 이벤트가 `0/1 nodes are available: 1 node(s) didn't match Pod's node affinity/selector.`였다. 이 `Pending` 파드에 `kubectl logs`를 하면 오류 없이 빈 출력이었다. taint는 노드 설정을 바꿔야 해서 실험하지 않고 문서 근거로만 적었다.
