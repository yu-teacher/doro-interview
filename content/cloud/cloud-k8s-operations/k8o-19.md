**모범 답변 (30~60초)**
컨테이너 인식이 켜진 JVM은 cgroup 메모리 limit을 보고 기본 최대 힙을 그 일부로 잡습니다. 힙이 이 상한을 넘으면 JVM이 스스로 `OutOfMemoryError`를 던지고 프로세스가 종료 코드 1로 끝나는데, 이것은 컨테이너가 limit 때문에 죽은 `OOMKilled`가 아닙니다. 반대로 `-Xmx`를 limit보다 크게 주면 JVM은 자기 상한 안이라 판단해 계속 메모리를 쓰다가 컨테이너 limit에 먼저 닿아 커널이 프로세스를 죽여 `OOMKilled`(137)가 됩니다. 힙 말고도 메타스페이스, 스레드 스택, 네이티브 메모리가 limit을 쓰므로 힙을 limit 전체로 잡지 말고 `-XX:MaxRAMPercentage`처럼 비율로 여유를 남기는 것이 안전합니다.

```bash
java -XX:+PrintFlagsFinal -version | grep MaxHeapSize
java -XX:MaxRAMPercentage=75 -XX:+PrintFlagsFinal -version | grep MaxHeapSize
```

(공식 문서) Manage Resources 페이지는 메모리 limit이 커널의 OOM kill로 강제되고 limit을 넘으면 커널이 컨테이너를 종료할 수 있으며, 종료는 메모리 압박이 감지될 때만 일어나므로 limit 강제는 반응적이라고 설명한다. 같은 페이지의 OOMKilled 예시는 Last State에 `Reason: OOMKilled`, `Exit Code: 137`이 남는다고 보여 준다. JVM의 힙 계산 규칙에 대한 JDK 공식 문서는 이번 출처 범위가 아니어서 읽지 않았고, 아래 JVM 동작은 모두 실험 결과다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 `amazoncorretto:21`(OpenJDK 21.0.13), 메모리 request·limit이 같은 파드로 실험했다. (1) limit 256Mi에서 `java -XX:+PrintFlagsFinal -version`은 `UseContainerSupport = true`, `MaxRAMPercentage = 25.0`, `MinRAMPercentage = 50.0`, `MaxHeapSize = 132120576`(126MiB)을 출력했고, 512Mi는 128MiB, 1Gi는 256MiB였으며(limit에 비례, 256Mi만 25%보다 큰 이유는 확인하지 않았다 [미검증]), 256Mi에 `-XX:MaxRAMPercentage=75`를 주면 `MaxHeapSize = 201326592`(192MiB)였다. (2) 1MiB 배열을 400개 잡아 두는 프로그램을 기본 힙(256Mi limit)으로 실행하면 `allocated 100 MB`까지 출력한 뒤 `java.lang.OutOfMemoryError: Java heap space`가 났고 파드 STATUS `Error`, terminated reason `Error`, exit code 1이었다. (3) 같은 프로그램에 `-Xmx600m`을 주면 `allocated 150 MB`까지 출력한 뒤 STATUS `OOMKilled`, exit code 137이었다. (4) `-Xmx256m`(limit과 같은 값)도 `allocated 200 MB`까지 출력한 뒤 `OOMKilled`, 137이었고, `-XX:MaxRAMPercentage=75`(힙 192MiB)는 `allocated 150 MB` 뒤 `OutOfMemoryError`, exit code 1이었다. 스프링 부트 앱으로는 실험하지 않았다.
