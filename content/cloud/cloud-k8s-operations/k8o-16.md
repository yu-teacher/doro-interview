**모범 답변 (30~60초)**
액추에이터가 앱의 가용성 상태에서 liveness와 readiness 정보를 모아 헬스 그룹으로 `/actuator/health/liveness`, `/actuator/health/readiness`에 노출하고, 쿠버네티스 환경에서는 이 그룹이 자동으로 켜집니다. 매니페스트의 `livenessProbe`와 `readinessProbe`를 각각 이 경로의 `httpGet`으로 지정하면 됩니다. 시작 중에는 liveness가 `BROKEN`이고, 컨텍스트가 뜬 뒤 시작 작업이 끝나기 전까지는 readiness가 `REFUSING_TRAFFIC`이라 준비되지 않은 앱에 트래픽이 가지 않습니다. 관리 포트를 따로 쓰면 메인 서버가 망가져도 프로브만 통과할 수 있어서, `add-additional-paths` 설정으로 메인 포트의 `/livez`, `/readyz`를 쓰도록 권장합니다.

```yaml
livenessProbe:
  httpGet: {path: /actuator/health/liveness, port: 8080}
readinessProbe:
  httpGet: {path: /actuator/health/readiness, port: 8080}
# management.endpoint.health.probes.add-additional-paths=true 이면 /livez, /readyz 도 가능
```

(공식 문서) Spring Boot Actuator Endpoints 문서의 Kubernetes Probes 절은 쿠버네티스 환경에서 액추에이터가 ApplicationAvailability에서 liveness·readiness 정보를 모아 `LivenessStateHealthIndicator`, `ReadinessStateHealthIndicator`로 보여 주고 헬스 그룹 `/actuator/health/liveness`, `/actuator/health/readiness`로 노출하며 이 그룹이 자동으로 활성화되고 `management.endpoint.health.probes.enabled`로 끌 수 있다고 한다. 시작 단계 표에서 Starting은 LivenessState `BROKEN`, ReadinessState `REFUSING_TRAFFIC`, HTTP 서버 미시작이고, Started는 CORRECT와 `REFUSING_TRAFFIC`, Ready는 CORRECT와 `ACCEPTING_TRAFFIC`이라고 한다. 앱이 liveness 주기보다 오래 걸려 시작하면 쿠버네티스가 `startupProbe`를 해법으로 언급한다고 하며(readiness가 시작 작업이 끝날 때까지 실패하므로 꼭 필요하지는 않지만 오래 걸리면 liveness HTTP 프로브를 쓰는 `startupProbe`를 고려하라고 한다), 별도 관리 컨텍스트를 쓰면 프로브가 성공해도 메인 앱이 비정상일 수 있어 `management.endpoint.health.probes.add-additional-paths=true`로 메인 포트의 `/livez`, `/readyz`를 쓰는 것이 좋다고 한다. (2026-10-27 원문 확인)
스프링 부트 앱을 실제로 띄워 프로브를 호출해 보지는 않았다(문서 근거만). 쿠버네티스 쪽 프로브 동작은 앞의 질문들에서 실험했다. 프로브 필드 설정은 Configure Probes 페이지를 따른다.
