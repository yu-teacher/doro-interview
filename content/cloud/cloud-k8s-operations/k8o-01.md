**모범 답변 (30~60초)**
먼저 `kubectl get pods`로 STATUS와 RESTARTS를 보고 어느 단계에서 막혔는지 가늠합니다. 다음으로 `kubectl describe pod`에서 컨테이너 상태(Waiting, Running, Terminated)와 직전 종료 사유, 맨 아래 Events를 읽습니다. 스케줄러와 kubelet이 남기는 실패 메시지가 대부분 여기에 있습니다. 컨테이너가 한 번이라도 실행됐다면 `kubectl logs`로 앱 로그를 보고, 재시작됐다면 `--previous`로 이전 실행의 로그를 봅니다. 그래도 모르겠으면 `kubectl debug`로 임시 컨테이너를 붙여 안을 봅니다. 스케줄 전 단계(Pending)에서는 로그가 없으니 describe 이벤트가 사실상 유일한 단서입니다.

```bash
kubectl get pods -o wide
kubectl describe pod <파드>            # State, Last State, Events
kubectl logs <파드> [-c 컨테이너] [--previous]
kubectl get events --sort-by=.lastTimestamp
```

(공식 문서) Debug Pods 페이지는 파드 디버깅의 첫 단계로 `kubectl describe pods`로 현재 상태와 최근 이벤트를 보라고 하고, Pending(스케줄 불가)·Waiting(노드에는 배정됐지만 실행 못 함)·Terminating으로 나눠 다음 확인 사항을 안내한다. Debug Running Pods 페이지는 컨테이너 상태가 Waiting, Running, Terminated 중 하나이며 상태에 따라 사유가 붙는다고 설명하고, 이벤트가 etcd에 저장되어 `kubectl get events`로 볼 수 있으며(네임스페이스별), 죽은 적 있는 컨테이너는 `--previous`로 직전 로그를 본다고 한다. 셸이 없는 이미지에는 `kubectl debug`의 임시 컨테이너를 쓴다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 존재하지 않는 이미지, 잘못된 실행 파일, 종료 코드 3으로 끝나는 명령, 메모리 초과, 없는 ConfigMap 참조 등 고장 파드를 일부러 만들자, 각 원인이 `kubectl get`의 STATUS와 `describe`의 Events에 그대로 나타났다. 스케줄 전 `Pending` 파드에 `kubectl logs`를 하면 오류 없이 빈 출력이었고, `kubectl get events --sort-by=.lastTimestamp`는 이벤트를 시간순으로 보여 주었다. 각 항목은 이후 질문에서 자세히 다룬다.
