**모범 답변 (30~60초)**
이미지를 가져오지 못하면 컨테이너는 `Waiting` 상태에 머뭅니다. pull 시도가 실패한 직후에는 reason이 `ErrImagePull`이고, 쿠버네티스가 늘어나는 간격으로 재시도를 기다리는 동안은 `ImagePullBackOff`여서 `kubectl get`의 STATUS에는 둘이 번갈아 보입니다. 같은 문제의 즉시 실패 표시와 재시도 대기 표시인 셈입니다. 원인은 `kubectl describe pod` 이벤트의 `Failed` 메시지에 나오므로, 이미지 이름과 태그 오타, 레지스트리에 이미지가 있는지, 비공개 저장소라면 `imagePullSecrets`를 붙였는지 순서로 확인합니다. 이미지를 바로잡으면 다음 시도에서 정상적으로 시작됩니다.

(공식 문서) Images 페이지는 컨테이너가 이미지를 못 받는 이유(잘못된 이미지 이름, `imagePullSecret` 없는 비공개 레지스트리)로 `ImagePullBackOff` 상태가 되고, BackOff는 쿠버네티스가 증가하는 지연으로 계속 시도한다는 뜻이며 지연은 컴파일된 한도인 300초(5분)까지 늘어난다고 설명한다. Debug Pods 페이지는 Waiting 파드의 가장 흔한 원인이 이미지 pull 실패이며 이미지 이름, 레지스트리에 올렸는지, 수동 pull 가능 여부를 확인하라고 한다. `ErrImagePull`이라는 이름은 영문 쿠버네티스 문서 `/docs/` 아래 1,057페이지(2026-10-27 사이트맵 기준)를 내려받아 검색했으나 어디에도 없었다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 존재하지 않는 이미지 이름(`exp-opsv-no-such/app:9.9`)으로 만든 파드는 이벤트가 Pulling, `Failed to pull image ... pull access denied for ..., repository does not exist or may require 'docker login'`, `Error: ErrImagePull`, `Back-off pulling image`, `Error: ImagePullBackOff` 순서로 쌓였고 파드 phase는 `Pending`, 컨테이너 상태는 `Waiting`이었다. 12초 간격으로 `kubectl get`의 STATUS를 보자 `ImagePullBackOff`, `ErrImagePull`, `ImagePullBackOff`가 번갈아 나타났다. `ErrImagePull`은 문서에는 없고 실험에서만 확인했다. 파드의 `image` 필드는 수정할 수 있어서 `kubectl set image pod/<파드> c=busybox:1.36`으로 고치자 약 15초 안에 컨테이너가 새 이미지로 시작되었다. `imagePullSecrets` 경우는 실험하지 않고 문서 근거로만 적었다.
