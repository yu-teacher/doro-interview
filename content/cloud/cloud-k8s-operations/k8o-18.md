**모범 답변 (30~60초)**
파드가 삭제되면 kubelet이 컨테이너 주 프로세스에 SIGTERM을 보내고, `terminationGracePeriodSeconds`(기본 30초) 안에 끝나지 않으면 SIGKILL로 강제 종료합니다. 스프링 부트는 SIGTERM을 받으면 graceful shutdown으로 새 요청을 거부하고 진행 중인 요청을 `spring.lifecycle.timeout-per-shutdown-phase`만큼 기다립니다. 이 대기 시간이 유예 시간보다 길면 정리가 끝나기 전에 SIGKILL이 도착해 진행 중이던 요청이 끊깁니다. 그러니 앱의 종료 대기와 `preStop` 같은 추가 대기를 합한 값이 유예 시간보다 짧아야 합니다. 또 PID 1 프로세스가 SIGTERM을 처리하지 않으면(셸 스크립트로 시작하는 경우 등) 신호가 앱에 전달되지 않거나 무시되어 유예 시간을 끝까지 채우고 강제 종료됩니다.

(공식 문서) Pod Lifecycle 페이지의 Termination of Pods 절은 삭제 요청 시 유예 시간(기본 30초)을 기록하고 kubelet이 컨테이너 런타임에 각 컨테이너의 주 프로세스로 TERM 신호를 보내게 하며, 유예 시간이 지나면 남은 프로세스에 KILL 신호를 보내고 파드를 API 서버에서 지운다고 설명한다. 같은 페이지는 `preStop` 훅이 유예 시간이 끝난 뒤에도 돌고 있으면 kubelet이 2초의 일회성 연장을 요청한다고도 한다. Spring Boot Graceful Shutdown 문서는 graceful shutdown이 기본 활성이고, 타임아웃 동안 기존 요청은 완료되게 하고 새 요청은 받지 않으며 `spring.lifecycle.timeout-per-shutdown-phase`로 기간을 조정한다고 한다. Pods and Endpoints Termination Flow 튜토리얼은 `preStop`이 `terminationGracePeriodSeconds`보다 오래 걸리면 유예 시간이 끝나는 시점에 컨테이너가 강제 종료되는 예를 보여 준다. 이 답변이 합산해서 맞추라고 한 것은 이 문서들을 연결한 추론이며 위 (4)로 확인했다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 `terminationGracePeriodSeconds: 8`인 파드를 지우고 삭제 완료까지 걸린 시간과 컨테이너 로그를 쟀다. (1) `sh -c "sleep 3600"`로 시작한 파드(PID 1에 SIGTERM 처리기가 없음)는 10초가 걸렸다. (2) SIGTERM에 `trap`으로 로그를 찍고 20초 정리를 하는 컨테이너는 `got-TERM`만 출력되고 `drained`는 끝내 출력되지 않은 채 10초 만에 사라졌다. (3) SIGTERM에 2초 정리 후 `exit 0` 하는 컨테이너는 `got-TERM`, `drained`를 모두 출력하고 4초 만에 삭제되었다. (4) `preStop`으로 `sleep 6`을 하고 SIGTERM 정리에 4초가 드는 컨테이너는 합계 10초가 유예 8초를 넘어 `got-TERM`만 나오고 `drained`는 없었고, `preStop` 3초에 정리 4초(합계 7초)는 둘 다 출력되고 9초 만에 삭제되었다. (5) `preStop`이 `sleep 20`이어서 유예 8초를 넘기면 유예가 끝난 뒤에야 `got-TERM`이 찍히고 10초 만에 삭제되었다(문서의 2초 연장과 같은 결과). (6) 앱이 자식 프로세스인 `sh -c 'sh -c "trap ...; 반복" & wait'` 형태에서는 자식에게 SIGTERM이 전달되지 않아 `got-TERM` 없이 10초 만에 삭제되었고, `exec`로 앱이 PID 1이 되게 하면 `got-TERM`이 찍히고 1초 만에 삭제되었다. 삭제 시간이 유예보다 2초쯤 긴 것은 삭제 처리 시간으로 보이며(2초 정리가 4초 걸린 (3)과 같은 차이) 정확한 분해는 확인하지 않았다. 스프링 앱의 실제 종료 시간은 측정하지 않았다.
