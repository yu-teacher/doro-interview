**모범 답변 (30~60초)**
liveness가 실패하면 쿠버네티스는 앱 인스턴스를 재시작해서 문제를 풀려고 합니다. 그런데 DB나 외부 API, 캐시 같은 외부 시스템이 장애인 경우에는 재시작해도 나아지지 않고, 모든 인스턴스의 liveness가 동시에 실패해 전부 재시작되는 연쇄 장애로 번질 수 있습니다. 그래서 스프링 부트 문서는 liveness가 외부 시스템 헬스 체크에 의존하면 안 된다고 하고, 기본적으로 이 그룹에 다른 헬스 인디케이터를 더하지 않습니다. readiness에 포함할지는 신중하게 판단해야 합니다. 포함하면 외부 시스템이 죽을 때 파드가 서비스에서 빠지는데, 모든 인스턴스가 공유하는 의존성이면 전체가 트래픽을 못 받기 때문입니다. 서킷 브레이커로 호출하는 쪽에서 다루는 선택지도 있습니다.

(공식 문서) Spring Boot Actuator Endpoints 문서의 Checking External State With Kubernetes Probes 절은 liveness 프로브가 외부 시스템 헬스 체크에 의존하면 안 되며, liveness 상태가 깨지면 쿠버네티스가 앱 인스턴스를 재시작하므로 DB·웹 API·외부 캐시 같은 외부 시스템이 장애일 때 모든 인스턴스를 재시작해 연쇄 장애를 일으킬 수 있다고 설명한다. 스프링 부트는 기본적으로 두 그룹에 다른 헬스 인디케이터를 추가하지 않으며, readiness는 외부 시스템 확인 여부를 개발자가 신중히 정해야 하고, 모든 인스턴스가 공유하는 외부 시스템은 readiness에 넣어 서비스에서 빠지게 둘지, 빼고 상위에서 서킷 브레이커로 다룰지 판단이 필요하다고 한다. 모든 인스턴스가 unready이면 ClusterIP·NodePort Service는 연결 자체를 받지 않고 HTTP 오류 응답도 없다고 한다. Pod Lifecycle 페이지는 liveness 실패 횟수가 임계를 넘으면 kubelet이 컨테이너를 재시작한다고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 레디니스 프로브가 계속 실패하는 파드 하나만 고르는 ClusterIP Service에 클러스터 안 파드에서 `wget`·`nc`를 하자 `Connection refused`로 즉시 실패했다(HTTP 오류 응답이 아니라 연결 거부). 이것은 쿠버네티스 쪽 동작만 확인한 것이고, 스프링 앱과 DB 장애 시나리오나 liveness 연쇄 재시작은 실행해 보지 않았다(문서 근거만).
