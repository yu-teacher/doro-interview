**모범 답변 (30~60초)**
Kustomize는 평범한 YAML 매니페스트를 그대로 두고 그 위에 변경을 얹는 도구입니다. `kustomization.yaml`이 있는 디렉터리가 base이고, 다른 kustomization 디렉터리를 base로 참조해 패치, 이름 접두사, 공통 레이블, ConfigMap·Secret 생성 같은 변경을 더한 디렉터리가 overlay입니다. dev와 prod overlay가 같은 base를 공유하며 레플리카나 이미지 같은 차이만 담고, `kubectl apply -k`나 `kubectl kustomize`로 쓰며 kubectl에 내장되어 있습니다. Helm은 값을 템플릿에 넣어 렌더링하는 차트 패키지 방식이고 릴리스와 리비전으로 설치 이력을 관리한다는 점이 다릅니다.

```yaml
# overlays/prod/kustomization.yaml
resources: [../../base]
namePrefix: prod-
labels:
- pairs: {env: prod}
patches:
- patch: |-
    - op: replace
      path: /spec/replicas
      value: 3
  target: {kind: Deployment, name: app}
```

(공식 문서) Declarative Management of Kubernetes Objects Using Kustomize 페이지는 Kustomize를 설정 파일을 사용자 지정하는 도구로 소개하며 다른 소스에서 리소스 생성(configMapGenerator, secretGenerator), 리소스 전체에 공통 필드 설정, 리소스 모음의 구성과 사용자 지정(패치 등) 기능을 든다. base는 `kustomization.yaml`이 든 디렉터리이고 overlay는 다른 kustomization 디렉터리를 base로 참조하는 `kustomization.yaml`이 든 디렉터리이며, base는 overlay를 모르고 여러 overlay에서 쓸 수 있다고 한다. 적용은 `kubectl apply -k`이고 `kubectl kustomize`로 결과를 본다고 한다. Using Helm·Charts 페이지는 Helm 차트가 값과 `templates/`를 결합해 매니페스트를 만들고 릴리스가 리비전으로 관리된다고 설명한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)의 kubectl(v1.36.1, 내장 Kustomize v5.8.1)로 replicas 1인 Deployment base와, `namePrefix: prod-`, 레이블 `env: prod`, replicas를 3으로 바꾸는 JSON 패치를 가진 prod overlay, `namePrefix: dev-`만 가진 dev overlay를 만들었다. `kubectl kustomize`는 prod에서 이름 `prod-app`, 메타데이터 레이블 `env: prod`(선택자에는 들어가지 않았다), replicas 3의 완성된 매니페스트를, dev에서 `dev-app`, replicas 1을 출력했고 base 디렉터리는 접두사 없는 `app`이었다. `kubectl apply -k`로 `deployment.apps/prod-app`이 만들어졌고(READY 0/3으로 레플리카 3 요청) `kubectl delete -k`로 지웠다. Helm은 이 환경에 없어 비교는 문서 근거로만 했다.
