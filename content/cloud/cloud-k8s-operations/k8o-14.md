**모범 답변 (30~60초)**
컨테이너는 실행 중이지만 레디니스 프로브가 실패해서 파드가 준비되지 않은 상태입니다. liveness와 달리 readiness 실패는 컨테이너를 재시작하지 않기 때문에 RESTARTS가 0으로 유지되고, 대신 그 파드는 Service의 트래픽 대상에서 빠져 요청을 받지 못합니다. `kubectl describe pod`의 Events에 `Readiness probe failed`와 이유가 찍히고 Conditions의 `Ready`가 False입니다. 모든 파드가 이 상태면 Service에 보낼 곳이 없어 연결이 실패합니다. 앱이 준비 중이거나, 프로브 경로·포트·명령이 틀렸거나, 의존 대상이 불가한 경우라 로그와 프로브 설정을 같이 봅니다. 시작 프로브가 아직 성공 전일 때도 같은 모습입니다.

(공식 문서) Configure Probes 페이지는 readiness 프로브가 실패하면 파드가 준비 안 됨으로 표시되어 어떤 서비스로부터도 트래픽을 받지 않고, readiness 프로브가 컨테이너 전체 수명 동안 실행된다고 설명한다. Pod Lifecycle 페이지는 readiness 프로브가 실패 상태를 반환하면 EndpointSlice 컨트롤러가 일치하는 모든 Service의 EndpointSlice에서 파드 IP 주소를 제거한다고 하고, liveness는 실패 횟수가 임계를 넘으면 컨테이너를 재시작한다고 한다. Debug Running Pods 페이지는 파드의 Ready 조건이 서비스 요청을 처리할 수 있어 매칭되는 서비스의 로드밸런싱 풀에 추가돼야 함을 뜻한다고 한다. (2026-10-27 원문 확인)
(실험 확인) Docker Desktop 단일 노드 클러스터(Kubernetes v1.36.1, 런타임 docker 29.6.1)에서 없는 파일을 `cat`하는 exec 레디니스 프로브를 둔 파드는 `READY 0/1`, `Running`, `RESTARTS 0`을 2분 넘게 유지했고 이벤트에 `Readiness probe failed: cat: can't open '/tmp/ready': No such file or directory`가 반복되었으며 Conditions는 `Ready False`, `ContainersReady False`였다. 이 파드를 selector로 가리키는 Service의 `kubectl get endpoints` ENDPOINTS 열은 비어 있었고(준비된 파드가 하나 더 있는 Service에서는 그 파드 IP만 나왔다), EndpointSlice에는 그 파드가 `ready: false`로 남아 있었다(문서의 표현은 IP 제거이고 실험에서는 `ready: false`로 남은 차이가 있으나 정확한 구현은 확인하지 않았다). 준비되지 않은 파드만 고르는 ClusterIP Service에 클러스터 안 파드에서 `wget`·`nc`를 하자 `Connection refused`로 실패했다. 시작 프로브가 끝내 성공하지 못하는 파드(`failureThreshold: 3`)도 시작 30초 시점에 `READY 0/1`, `Running`, `RESTARTS 0`이었다(이후 임계를 넘어 재시작).
