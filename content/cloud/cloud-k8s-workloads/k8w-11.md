**모범 답변 (30~60초)**
LimitRange는 Pod가 만들어지는 admission 단계에서 동작합니다. 먼저 requests와 limits가 없는 컨테이너에 `defaultRequest`와 `default` 값을 채우고, 그다음 최소·최대·비율 제약을 어기지 않는지 검사해서 어기면 403으로 거부합니다. 검사는 이 시점에만 이뤄져서 LimitRange를 새로 만들거나 바꿔도 이미 실행 중인 Pod는 그대로입니다. 또 기본값끼리의 일관성은 따지지 않아서, 기본 limit이 사용자가 쓴 request보다 작아지면 Pod가 invalid로 거부됩니다. 같은 네임스페이스에 LimitRange가 둘 이상이면 어떤 기본값이 쓰일지 정해져 있지 않습니다.

(공식 문서) Limit Ranges 페이지는 LimitRange 어드미션 컨트롤러가 먼저 자원 값이 없는 Pod와 컨테이너에 기본 request·limit를 적용하고, 그다음 최소·최대·비율을 넘지 않는지 추적하며, 위반하면 403으로 거부된다고 설명한다. 검증은 Pod 어드미션 단계에서만 일어나고 기존 Pod는 바뀌지 않으며, 기본값의 일관성은 검사하지 않아 기본 limit이 컨테이너의 request보다 작으면 Pod를 스케줄할 수 없다고 한다. LimitRange가 둘 이상이면 적용되는 기본값이 정해져 있지 않다고도 한다.
(실험 확인) Kubernetes v1.36.1에서 `default` cpu 300m·memory 128Mi, `defaultRequest` cpu 100m·memory 64Mi, 컨테이너 memory `max` 256Mi인 LimitRange가 있을 때, 값 없는 Pod는 위 기본값이 들어갔고 requests와 limits가 달라 QoS가 Burstable이었다. limit 300Mi Pod는 최대값 때문에 거부됐고, `requests.cpu: 350m`만 쓴 Pod는 기본 limit 300m이 적용돼 `must be less than or equal to cpu limit of 300m`(invalid)로 거부됐다. 순서 확인으로, 컨테이너 기본 limit 128Mi에 Pod 타입 `max` memory 100Mi인 LimitRange에서 자원 값 없는 Pod는 `maximum memory usage per Pod is 100Mi, but limit is 128Mi`로 거부됐다(기본값이 먼저 들어간 뒤 최대값 검사). 이미 실행 중인 Pod는 LimitRange를 더 엄격하게(Pod `max` 10Mi) 패치한 뒤에도 Running이었다. 같은 네임스페이스에 기본 limit이 다른 LimitRange 둘(100Mi, 200Mi)을 두고 Pod 6개를 만들자 5개는 100Mi, 1개는 200Mi가 들어가 어느 쪽이 적용될지 일정하지 않았다. 컨테이너 `max`보다 큰 `default`를 가진 LimitRange는 만들 때 `default value 128Mi is greater than max value 64Mi`로 거부됐다.
