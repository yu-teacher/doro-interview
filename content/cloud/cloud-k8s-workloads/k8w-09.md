**모범 답변 (30~60초)**
스케줄러는 노드의 실제 사용량이 아니라, 이미 배치된 Pod들의 requests 합계가 노드의 할당 가능 용량을 넘지 않는지로 판단하기 때문입니다. 한 Pod가 CPU 9코어를 requests로 잡아 두면 실제로는 놀고 있어도 그만큼은 예약된 것으로 계산됩니다. 그래서 다른 Pod의 requests가 남은 몫보다 크면 `Insufficient cpu`로 Pending이 됩니다. 문서도 실제 사용량이 매우 낮아도 용량 검사에 실패하면 배치하지 않는다고 하는데, 나중에 사용량이 늘 때의 부족을 막기 위해서입니다. 비교 기준은 노드의 `status.allocatable`이라, 시스템 데몬 몫을 뺀 이 값에서 requests가 얼마나 예약됐는지가 관건입니다.

(공식 문서) Resource Management 페이지는 스케줄러가 자원 종류마다 스케줄된 컨테이너들의 requests 합이 노드 용량보다 작도록 보장하며, 실제 CPU·메모리 사용량이 매우 낮더라도 용량 검사에 실패하면 Pod를 배치하지 않는다고 설명한다. 이유는 나중에 사용량이 늘 때(예: 일일 피크)의 자원 부족을 막기 위해서이다. 같은 페이지는 `status.allocatable`이 시스템 데몬 몫을 뺀 Pod용 가용량이고 스케줄러가 Pod 적합성을 판단할 때 이 값을 쓴다고 한다.
(실험 확인) Kubernetes v1.36.1 단일 노드의 CPU allocatable은 15였고 다른 Pod들의 requests 합은 약 850~960m였다. `sleep`만 실행하는 Pod에 `requests.cpu: 9`와 `requests.cpu: 5`를 주자 모두 Running이 됐고(노드 Allocated cpu requests 14960m, 99%), 같은 9와 6을 요청한 Pod 두 개는 `0/1 nodes are available: 1 Insufficient cpu.`로 Pending이 됐다. 이어서 9코어 Pod를 지우자 대기 중이던 Pod 하나가 바로 스케줄됐다. 이 노드에는 metrics API가 없어(`kubectl top`: `Metrics API not available`) 실제 사용률 수치를 재지는 못했고, 실험 Pod가 `sleep`만 돌리는 것을 근거로 했다.
