**모범 답변 (30~60초)**
StatefulSet의 Pod는 `web-0`, `web-1`처럼 StatefulSet 이름과 서수로 이뤄진 고정된 이름을 갖고, Pod가 지워져 다시 만들어져도 같은 이름과 같은 PVC를 이어받습니다. 이 이름이 호스트명이 되고, `serviceName`으로 지정한 헤드리스 Service(`clusterIP: None`)가 `web-0.web.<네임스페이스>.svc.cluster.local` 같은 Pod별 DNS 이름을 만들어 줍니다. 이 Service는 직접 만들어야 합니다. 기본 `OrderedReady` 정책에서는 0번부터 차례로, 앞 번호가 Running이고 Ready가 된 뒤에 다음을 만들며, 줄일 때는 큰 번호부터 역순으로 종료합니다. 순서가 필요 없으면 `Parallel`로 풀 수 있습니다.

(공식 문서) StatefulSet 페이지는 Pod가 서수, 안정적인 네트워크 ID, 안정적인 저장소로 이뤄진 정체성을 가지며 노드가 바뀌어도 유지된다고 한다. 호스트명은 `$(statefulset 이름)-$(서수)`이고 헤드리스 Service가 Pod별 DNS(`$(pod 이름).$(서비스 도메인)`)를 관리하며 이 Service는 사용자가 만들어야 한다. Pod가 다시 스케줄되면 그 Pod의 PVC에 묶인 볼륨이 다시 마운트된다. 기본 `OrderedReady`에서는 {0..N-1} 순서로 만들고 이전 Pod가 Running·Ready여야 다음으로 가며, 삭제는 {N-1..0} 역순으로 하고 후속 Pod가 완전히 종료돼야 진행한다. `Parallel`은 기다리지 않고 동시에 만들거나 종료한다.
(실험 확인) Kubernetes v1.36.1(Docker Desktop 단일 노드)에서 readiness 지연(4초)을 둔 replicas 3 StatefulSet과 헤드리스 Service를 만들자 `web-0`이 Ready가 된 뒤에 `web-1`이, `web-1`이 Ready가 된 뒤에 `web-2`가 만들어졌다(생성 시각 6초·5초 간격). Pod의 hostname은 `web-0`, subdomain은 `web`이었다. `web-1`을 삭제하면 UID와 IP는 바뀌었지만 같은 이름으로 다시 만들어졌고, 시작 로그가 `web-1 previous-count=1`이라 같은 PVC의 데이터를 이어받은 것을 확인했다. busybox `nslookup`에서 `web-2.web.exp-workloadv.svc.cluster.local`은 해당 Pod IP 하나로, `web.exp-workloadv.svc.cluster.local`은 Pod 3개의 IP로 풀렸고, 존재하지 않는 서비스 이름을 쓴 이름은 NXDOMAIN이었다. replicas를 3에서 1로 줄이자 `web-2`의 삭제 이벤트가 `web-1`보다 먼저였고 3초 뒤 `web-1`이 삭제됐다. `podManagementPolicy: Parallel` StatefulSet은 Pod 3개가 같은 초에 만들어졌다. `serviceName`이 가리키는 Service 없이도 StatefulSet 자체는 만들어졌다(Service는 직접 만들어야 함).
