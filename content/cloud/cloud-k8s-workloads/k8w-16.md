**모범 답변 (30~60초)**
required 안티어피니티는 같은 라벨의 Pod가 이미 있는 노드에는 배치하지 않는 하드 규칙입니다. 그런데 롤링 업데이트의 기본값은 `maxSurge` 25%(올림)와 `maxUnavailable` 25%(내림)라서, replicas가 1이면 이전 Pod를 지우기 전에 새 Pod를 하나 더 띄우려 합니다. 새 Pod는 이전 Pod와 라벨이 같아 같은 노드에 놓일 수 없고, 다른 노드가 없거나 부족하면 Pending이 됩니다. `maxUnavailable`이 0이라 이전 Pod를 먼저 내릴 수도 없어서 롤아웃이 멈춥니다. 노드를 늘리거나 `maxSurge: 0`에 `maxUnavailable: 1`로 바꾸거나 규칙을 `preferred`로 완화해서 풉니다.

(공식 문서) Assigning Pods to Nodes 페이지는 `required` 파드 안티어피니티가 노드 필터링 단계의 하드 제약이라 기존 Pod 기준의 규칙을 만족하는 노드에만 배치하고, `preferred`는 점수에만 반영된다고 설명한다. `topologyKey`는 규칙을 적용하는 토폴로지 도메인(노드 등)을 정한다. Deployments 페이지는 `maxSurge`가 올림, `maxUnavailable`이 내림으로 계산되며 기본값이 각각 25%이고 둘 다 0일 수는 없다고 한다. "노드를 늘린다"는 해결책은 Resource Management 페이지의 Pending 문제 해결 절(노드 추가)에서 가져온 일반 조치다.
(실험 확인) Kubernetes v1.36.1 단일 노드에서 replicas 1, `kubernetes.io/hostname` 기준 `required` 안티어피니티 Deployment의 전략은 기본 25%/25%였고, 환경 변수를 바꾸자 새 Pod가 `Pending`이 되고 이전 Pod는 Running으로 남았으며 `rollout status`가 시간 초과됐다. `maxSurge: 0`, `maxUnavailable: 1`로 패치하자 이전 Pod가 내려가고 새 Pod가 Running이 되어 롤아웃이 끝났다. 두 값을 모두 0으로 패치하면 API가 `may not be 0 when maxSurge is 0`으로 거부했다. 별도로 replicas 2에 같은 규칙을 주면 Pod 하나는 Running, 하나는 Pending이었고, `preferred`로 바꾸면 둘 다 Running이었으며 replicas 1 `preferred` Deployment의 이미지 롤아웃도 정상 완료됐다.
