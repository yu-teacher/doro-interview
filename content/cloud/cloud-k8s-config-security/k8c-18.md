**모범 답변 (30~60초)**
네임스페이스는 이름과 RBAC, 쿼터 같은 API 리소스의 범위를 나누는 장치이지 네트워크를 막아 주지 않습니다. 기본적으로 클러스터의 모든 Pod는 네임스페이스와 상관없이 서로 통신할 수 있어서, 다른 네임스페이스의 Service도 `서비스.네임스페이스.svc.cluster.local` 이름으로 호출됩니다. 막으려면 NetworkPolicy를 쓰는데, 이것은 API 객체일 뿐 실제 차단은 네트워크 플러그인(CNI)이 구현합니다. 지원하는 플러그인이 없으면 정책을 만들어도 효과가 없고 오류도 나지 않으므로, 만든 뒤에 실제로 막히는지 확인해야 합니다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: deny-all-ingress, namespace: exp-configv-b}
spec:
  podSelector: {}
  policyTypes: [Ingress]
```

(공식 문서) Network Policies 페이지는 NetworkPolicy가 네트워크 플러그인에 의해 구현되며 지원하는 네트워킹 솔루션이 필요하고, 이를 구현하는 컨트롤러 없이 리소스를 만들면 아무 효과가 없다고 한다. 기본적으로 Pod는 인그레스와 이그레스 모두 격리되지 않아 모든 연결이 허용되고, 정책이 Pod를 선택해 해당 방향의 `policyTypes`에 있어야 그 방향이 격리된다. Multi-tenancy 페이지는 기본적으로 클러스터의 모든 Pod가 서로 통신할 수 있고, 네임스페이스 격리 모델은 다른 리소스와 네트워크 플러그인 설정이 함께 필요하며, NetworkPolicy는 이를 지원하는 CNI 플러그인이 없으면 무시된다고 경고한다. Namespaces 페이지는 네임스페이스를 이름의 범위로 설명하고 Service마다 `<service-name>.<namespace-name>.svc.cluster.local` 형태의 DNS 항목이 생긴다고 하며, Multi-tenancy 페이지는 기본적으로 DNS 조회가 모든 네임스페이스에 걸쳐 허용된다고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `exp-configv-b`에 nginx Pod와 Service를 만들고 다른 네임스페이스 `exp-configv`의 curl Pod에서 `web.exp-configv-b.svc.cluster.local`을 호출하자 HTTP 200이었다. 위 `deny-all-ingress` 정책을 `exp-configv-b`에 만들어 `kubectl get netpol`에서 보이는 것을 확인한 뒤 같은 호출을 다시 하자 여전히 200이었고 같은 네임스페이스의 Pod에서 호출해도 200이었다. 호출하는 쪽 네임스페이스에 `policyTypes: [Egress]` 전부 거부 정책을 만들고 다시 호출해도 200이었다. 이 클러스터의 `kube-system` Pod 목록은 CoreDNS, etcd, kube-apiserver, kube-controller-manager, kube-proxy, kube-scheduler, storage-provisioner, vpnkit-controller뿐이었고 정책 구현으로 보이는 별도 데몬은 없었다(원인은 확인하지 않았다). 이 클러스터에서는 NetworkPolicy가 강제되지 않는다는 결과만 확인했고, 다른 CNI에서의 동작은 문서 근거만 있다.
