**모범 답변 (30~60초)**
`runAsNonRoot: true`는 컨테이너를 비루트로 바꿔 주는 설정이 아니라 root로 실행되려 하면 시작을 거부하는 검증입니다. kubelet이 런타임에 이미지가 UID 0으로 실행되는지 검증하고, 그렇다면 컨테이너를 시작하지 않고 `CreateContainerConfigError`를 냅니다. 이미지에 `USER`가 없거나 root이거나 이름으로만 적혀 UID를 확인할 수 없는데 `runAsUser`도 주지 않았다면 이 오류가 나므로, `runAsUser`를 0이 아닌 숫자로 지정하거나 이미지를 숫자 UID의 비루트 사용자로 만들어야 합니다. 또 Pod Security Admission의 통과와는 다른 층의 검사라서, 이 실험에서 필드가 모두 설정된 Pod는 admission을 통과했지만 kubelet에서 막혔습니다.

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001      # 이것이 없으면 root 이미지는 시작하지 못한다
```

(공식 문서) Pod API 참조는 `runAsNonRoot`를 컨테이너가 비루트로 실행되어야 한다는 표시로, true면 kubelet이 런타임에 이미지가 UID 0으로 실행되지 않는지 검증하고 root면 컨테이너 시작에 실패하며 설정하지 않거나 false면 검증하지 않는다고 설명한다. `runAsUser`는 컨테이너 프로세스의 UID이고 지정하지 않으면 이미지 메타데이터의 사용자를 쓴다고 한다. Pod Security Standards의 restricted는 `runAsNonRoot`가 true일 것과 `runAsUser`가 0이 아닐 것을 요구한다. 이미지의 USER가 이름으로만 지정된 경우는 문서에서 설명을 찾지 못했다(Pod API 참조, Pod Security Standards, Configure a Security Context, Linux Kernel Security Constraints 페이지를 확인했다).
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `enforce=restricted` 네임스페이스에서 설정 없는 Pod는 `runAsNonRoot != true` 등 네 가지 위반으로 `Forbidden`이었다. `runAsNonRoot: true`, `seccompProfile: RuntimeDefault`, `allowPrivilegeEscalation: false`, capability drop ALL을 모두 설정하되 `runAsUser`를 주지 않은 busybox Pod는 admission을 통과했지만 `CreateContainerConfigError`가 됐고 이벤트는 `container has runAsNonRoot and image will run as root`였다. `runAsUser: 10001`을 더하자 `Running`이 됐고 `id`는 `uid=10001`을 보였다. 이미지가 `USER curl_user`처럼 이름으로만 지정된 `curlimages/curl:8.10.1`에 `runAsUser`를 주지 않으면 비루트 사용자인데도 `image has non-numeric user (curl_user), cannot verify user is non-root`로 같은 오류가 났고, `runAsUser: 100`을 주자 `Running`이었다. `runAsNonRoot: true`와 `runAsUser: 0`을 함께 준 Pod는 `restricted` 네임스페이스의 admission에서 `runAsUser=0 (pod must not set runAsUser=0)`으로 거부됐다.
