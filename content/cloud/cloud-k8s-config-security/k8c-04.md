**모범 답변 (30~60초)**
Role은 어떤 API 그룹의 어떤 리소스에 어떤 동사, 예를 들어 `get`과 `list`를 허용할지 적은 권한 규칙의 묶음이고, RoleBinding은 그 Role을 사용자나 그룹, ServiceAccount 같은 주체에 연결합니다. Role은 만들 때 지정한 네임스페이스 안에서만 유효합니다. RBAC의 권한은 순수하게 더해지는 방식이라 거부 규칙이 없고, 바인딩으로 허용된 것 말고는 열리지 않습니다. 그래서 무언가를 막으려면 그 권한을 주지 않아야 합니다. 설정이 의도대로인지는 `kubectl auth can-i`에 `--as`로 주체를 바꿔 확인할 수 있습니다.

```bash
kubectl -n exp-configv create role pod-reader --verb=get,list --resource=pods
kubectl -n exp-configv create rolebinding read-pods --role=pod-reader --serviceaccount=exp-configv:reader
kubectl auth can-i list pods -n exp-configv --as=system:serviceaccount:exp-configv:reader   # yes
```

(공식 문서) RBAC 페이지는 Role이나 ClusterRole이 권한 규칙의 집합이고 권한은 순수하게 추가되며 거부 규칙은 없다고 명시한다. Role은 항상 특정 네임스페이스 안의 권한을 정하며 만들 때 네임스페이스를 지정해야 하고, 바인딩은 사용자·그룹·ServiceAccount 목록과 역할 참조를 가지며 RoleBinding은 특정 네임스페이스에서 권한을 부여한다고 설명한다. Authorization 페이지는 API 요청의 모든 부분이 어떤 인가 방식에 의해 허용되어야 하며 기본적으로 접근이 거부된다고 하고, `kubectl auth can-i` 레퍼런스는 이 명령이 임퍼스네이션(`--as`)과 잘 맞는다고 하며 `--as=system:serviceaccount:...` 예시를 든다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. ServiceAccount `reader`는 바인딩 전에 `list pods`가 `no`였다. `pod-reader` Role과 RoleBinding을 만든 뒤 같은 네임스페이스의 `list pods`와 `get pods`는 `yes`, `delete pods`와 허용하지 않은 동사 `watch pods`는 `no`였고, 다른 네임스페이스(`default`)의 `list pods`, 모든 네임스페이스의 `list pods`, `list secrets`, `list nodes`도 `no`였다. 바인딩이 없는 임의의 사용자 `jane`도 `no`였다. 실제 호출에서도 `reader` 권한으로 Pod 목록은 조회됐고 Secret 목록은 `Forbidden`이었다.
