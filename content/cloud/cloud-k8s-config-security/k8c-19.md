**모범 답변 (30~60초)**
네, 알아낼 수 있습니다. Secret을 직접 읽는 `get`이나 `list` 권한이 없어도 같은 네임스페이스에서 Pod를 만들 수 있으면, 그 Secret을 환경 변수나 볼륨으로 쓰는 Pod를 만들어 값을 출력하게 할 수 있습니다. 문서도 Pod를 만들 수 있으면 Deployment 같은 간접 경로를 포함해 그 네임스페이스의 모든 Secret을 읽을 수 있다고 경고합니다. 또 `list`나 `watch` 권한만으로도 Secret 내용이 보입니다. 그러므로 Pod 생성 권한도 Secret의 신뢰 경계로 보고, 네임스페이스를 나눠 Secret 접근을 격리하며 읽기 이벤트를 감사하는 식으로 설계해야 합니다.

```bash
kubectl --as=system:serviceaccount:exp-configv:creator -n exp-configv get secret dbpw
# Forbidden: cannot get resource "secrets"
# 같은 계정으로 secretKeyRef Pod를 만들고 logs 를 보면 값이 출력된다
```

(공식 문서) Secrets 페이지의 경고는 네임스페이스에서 Pod를 만들 권한이 있으면 직접·간접(Deployment 생성 포함) 접근으로 그 네임스페이스의 모든 Secret을 읽을 수 있다고 한다. Good practices for Kubernetes Secrets 페이지는 Secret `list` 접근이 내용 조회를 함의하고, Pod를 만들 수 있는 사용자는 그 Pod가 Secret을 노출하게 해 값을 볼 수 있으며, 완화책으로 수명이 짧은 Secret, 여러 Secret의 동시 읽기 같은 이벤트에 대한 감사 규칙, 별도 네임스페이스로 마운트된 Secret의 접근 격리를 든다. RBAC Good Practices 페이지는 `get`뿐 아니라 `list`와 `watch` 접근도 Secret 내용을 드러내고, 워크로드 생성 권한이 그 네임스페이스의 Secret 같은 다른 리소스에 대한 접근을 함의한다고 설명한다. `watch` 권한만으로 읽히는 것은 실험하지 않았다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. ServiceAccount `creator`에게 `pods`와 `pods/log`에 대한 `create`, `get`만 허용하자 `get secret dbpw`와 `get secrets`는 `Forbidden`이었다. 같은 계정으로 `secretKeyRef` 환경 변수를 출력하는 Pod를 만들고 로그를 읽자 Secret 값이 그대로 출력됐다. `deployments`의 `create`와 Pod·로그 `get`, `list`만 있고 `pods` `create`는 없는 계정(`can-i create pods`는 `no`)이 Secret을 참조하는 Deployment를 만들자 컨트롤러가 만든 Pod의 로그에 Secret 값이 출력됐다. `secrets`의 `list`만 허용한 계정은 `get secret`이 `Forbidden`인데 `kubectl get secrets -o jsonpath`의 `.data`로 값(base64)을 얻었다. 다른 네임스페이스의 Secret을 참조한 Pod는 `not found`로 시작하지 못했다.
