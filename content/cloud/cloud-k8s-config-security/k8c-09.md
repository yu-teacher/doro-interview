**모범 답변 (30~60초)**
동적으로 만든 PV는 StorageClass의 reclaimPolicy를 물려받고 기본은 `Delete`입니다. `Delete`는 PVC를 지우면 PV 객체와 실제 스토리지를 함께 지워 데이터가 사라집니다. `Retain`은 PV와 데이터를 남기고 상태를 `Released`로 바꾸는데, 이전 사용자의 데이터가 남아 있으므로 다른 PVC에 자동으로 다시 붙지 않습니다. 관리자가 데이터를 정리한 뒤 PV를 지우거나 새로 만들어야 합니다. Pod가 쓰는 중인 PVC를 지우면 `pvc-protection` 파이널라이저 때문에 삭제가 미뤄지고 Pod가 사라진 뒤에야 처리됩니다.

```bash
kubectl get pv -o custom-columns=NAME:.metadata.name,RECLAIM:.spec.persistentVolumeReclaimPolicy,STATUS:.status.phase
# pvc-2498...   Retain   Released     (PVC 삭제 뒤)
```

(공식 문서) Persistent Volumes 페이지는 reclaim 정책이 Retain, Recycle, Delete이고 Recycle은 deprecated라고 한다. Retain은 PVC 삭제 후에도 PV가 남아 released 상태가 되지만 이전 사용자의 데이터가 남아 있어 다른 claim에 쓸 수 없고, 관리자가 PV를 지우고 데이터를 정리하는 등 수동으로 회수한다고 한다. Delete는 PV 객체와 외부 스토리지를 함께 지우고(이 정책을 지원하는 볼륨 플러그인의 경우), 동적 프로비저닝 볼륨은 StorageClass의 정책을 상속하며 기본값은 Delete라고 한다. 사용 중인 PVC는 삭제가 미뤄지는 Storage Object in Use Protection이 있고 `kubernetes.io/pvc-protection` 파이널라이저로 확인한다고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. 기본 StorageClass(Delete)의 PVC를 Pod가 쓰는 동안 `kubectl delete pvc --wait=false`를 하자 PVC에 `["kubernetes.io/pvc-protection"]` 파이널라이저와 삭제 시각이 남은 채 유지됐고, Pod를 지운 뒤 PVC와 PV가 모두 사라졌다. `reclaimPolicy: Retain`인 StorageClass의 PVC를 지우자 PV가 `Released`로 남고 `claimRef`가 이전 PVC를 가리키는 채였다. 같은 클래스·같은 `volumeName`으로 새 PVC를 만들어도 `Pending`이었고 PV는 `Released` 그대로였다. 그 PV의 `claimRef`를 `kubectl patch`로 지우자 `Available`이 되었고 같은 `volumeName`의 PVC와 다시 연결됐다(그 PVC를 지우자 PV는 다시 `Released`, `claimRef`는 새 PVC). 이 절차는 문서의 PVC 축소 방법에 나온 단계이고, 회수 절차로 문서가 설명하는 것은 PV 삭제와 데이터 정리다. 실험이 끝난 뒤 PV 객체는 지웠다.
