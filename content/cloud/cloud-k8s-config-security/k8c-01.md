**모범 답변 (30~60초)**
ConfigMap은 비밀이 아닌 설정을 키와 값으로 담는 객체이고, 컨테이너에는 명령과 인자, 환경 변수, 읽기 전용 볼륨의 파일, 그리고 앱이 쿠버네티스 API로 직접 읽는 방법으로 쓸 수 있습니다. 앞의 세 가지는 kubelet이 컨테이너를 띄울 때 값을 넣어 줍니다. `LOG_LEVEL`처럼 값 하나씩 필요한 단순 설정은 환경 변수가, 설정 파일 통째로 필요하면 볼륨 마운트가 어울립니다. 볼륨은 키가 파일 이름이 되고, 환경 변수는 바뀌어도 재시작해야 반영됩니다. Pod와 같은 네임스페이스에 있어야 하고 데이터는 1MiB를 넘을 수 없으며, 기밀 값은 Secret에 둬야 합니다.

```yaml
env:
- name: LOG_LEVEL
  valueFrom: {configMapKeyRef: {name: app-cfg, key: LOG_LEVEL}}
volumeMounts:
- {name: cfg, mountPath: /etc/cfg, readOnly: true}
volumes:
- name: cfg
  configMap: {name: app-cfg}
```

(공식 문서) ConfigMaps 페이지는 ConfigMap을 비기밀 데이터를 키-값으로 담는 API 객체라 하고, 컨테이너 command와 args, 환경 변수, 읽기 전용 볼륨의 파일, 앱이 API로 직접 읽는 네 가지 사용법을 든다. 앞의 세 방법은 kubelet이 컨테이너를 시작할 때 ConfigMap 데이터를 쓰고, 네 번째는 코드를 짜야 하는 대신 변경을 구독하거나 다른 네임스페이스의 ConfigMap도 읽을 수 있다고 한다. Pod와 ConfigMap은 같은 네임스페이스여야 하고, 데이터는 1MiB를 넘을 수 없으며, 비밀이 아니므로 기밀 데이터는 Secret을 쓰라고 경고한다. 환경 변수로 쓴 ConfigMap은 자동 갱신되지 않고 Pod 재시작이 필요하며, 볼륨에서 `items`를 생략하면 모든 키가 같은 이름의 파일이 되고, 정적 Pod는 ConfigMap을 참조할 수 없다고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. 1.1MB짜리 파일로 `kubectl create configmap`을 하면 `Too long: may not be more than 1048576 bytes`로 거부됐고 같은 파일의 Secret도 같은 한도로 거부됐다. 값이 정확히 1048576바이트인 ConfigMap은 만들어졌다. 위 매니페스트의 Pod는 환경 변수와 볼륨 파일 값을 모두 읽었다. 명령 인자로 쓰는 방식은 실행하지 않았고 문서 근거만 있다. 이 환경에서는 `kubectl exec`가 `server gave HTTP response to HTTPS client` 오류로 동작하지 않아 값을 3초마다 로그로 찍게 했다. ConfigMap의 `LOG_LEVEL`을 `debug`에서 `info`로 패치하자 90초 뒤 로그에서 볼륨 파일은 `info`로 바뀌었지만 환경 변수는 `debug`로 남았고, Pod를 다시 만들자 `info`가 읽혔다. 다른 네임스페이스에 있는 ConfigMap을 `configMapKeyRef`로 참조한 Pod는 `CreateContainerConfigError`와 `configmap "only-b" not found`였다.
