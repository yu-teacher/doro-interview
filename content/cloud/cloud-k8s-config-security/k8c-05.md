**모범 답변 (30~60초)**
ServiceAccount는 사람이 아니라 Pod 같은 워크로드와 자동화에 신원을 주는 쿠버네티스 API 객체이고 네임스페이스에 속합니다. 사용자 계정은 API 서버에 객체로 존재하지 않고 클러스터 밖의 인증 수단이 다루지만, ServiceAccount는 `kubectl create serviceaccount`로 만듭니다. 네임스페이스마다 `default`가 자동으로 생기고, Pod에 `serviceAccountName`을 쓰지 않으면 그것이 붙습니다. 이 계정은 기본 API 조회 권한 외에는 권한이 없으므로, API를 호출해야 하는 앱은 전용 ServiceAccount를 만들어 RoleBinding으로 필요한 권한만 줍니다.

```yaml
spec:
  serviceAccountName: reader
```

(공식 문서) Service Accounts 페이지는 ServiceAccount를 워크로드와 시스템 구성요소를 위한 비인간 계정이고 네임스페이스에 속하며 API의 ServiceAccount 객체로 존재한다고 하고, 사용자 계정은 기본적으로 API 서버에 존재하지 않는 외부 신원이라 비교한다. 모든 네임스페이스는 `default` ServiceAccount를 받고, 이 계정은 RBAC이 켜진 경우 모든 인증된 주체가 갖는 API 발견 권한 외에는 권한이 없으며, Pod에 지정하지 않으면 `default`가 배정된다고 한다. Configure Service Accounts 페이지는 Pod의 `spec.serviceAccountName`으로 지정한다고 하고, RBAC 페이지는 ServiceAccount를 API나 매니페스트, `kubectl create serviceaccount` 등으로 만들고 권한은 RBAC으로 따로 부여한다고 설명한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `default` ServiceAccount를 쓰는 Pod가 마운트된 토큰으로 API 서버에 같은 네임스페이스의 Pod 목록을 요청하자 HTTP 403이었고 `/version`은 200이었다. Role을 바인딩한 `reader`를 `serviceAccountName`으로 지정한 Pod는 Pod 목록 요청에서 200, Secret 목록 요청에서는 403이었다. `default` ServiceAccount를 지우자 3초 안에 다시 만들어졌다. 존재하지 않는 ServiceAccount나 다른 네임스페이스에만 있는 ServiceAccount를 `serviceAccountName`으로 주면 Pod 생성이 `serviceaccount "..." not found`로 거부됐다.
