**모범 답변 (30~60초)**
`data`의 값은 base64로 인코딩한 문자열이어야 하고, `stringData`는 인코딩 없이 평문 문자열을 적게 해 주는 편의 필드입니다. `stringData`는 서버에서 `data`로 합쳐져 저장되므로 읽어 오면 base64 값만 보이고, 같은 키가 둘 다 있으면 `stringData`가 우선합니다. `type`은 Secret의 용도를 나타내며 내장 타입은 필수 키를 API 서버가 검증합니다. 기본은 `Opaque`이고, 이미지 레지스트리 인증은 `kubernetes.io/dockerconfigjson`, TLS 인증서는 `kubernetes.io/tls` 같은 타입을 씁니다. 어느 쪽이든 base64는 암호화가 아니므로 값의 보호는 따로 생각해야 합니다.

```bash
kubectl -n exp-configv apply -f - <<'EOF'
apiVersion: v1
kind: Secret
metadata: {name: sd}
stringData: {user: admin}
EOF
kubectl -n exp-configv get secret sd -o jsonpath='stringData={.stringData} data={.data}'
# stringData= data={"user":"YWRtaW4="}
```

(공식 문서) Managing Secrets using Configuration File 페이지는 `data`가 임의의 데이터를 base64로 인코딩해 담는 필드이고, `stringData`는 편의를 위해 base64가 아닌 문자열을 바로 넣게 해 주며 Secret을 만들거나 갱신할 때 인코딩된다고 설명한다. 같은 키를 둘 다에 쓰면 `stringData`의 값이 쓰이고, `stringData`가 서버 측 적용(server-side apply)과 잘 맞지 않는다는 주의도 이 페이지와 Secrets 페이지에 있다. Secrets 페이지는 `type`이 Secret 데이터의 프로그램적 처리를 돕는 값이고 내장 타입(`Opaque`, `kubernetes.io/service-account-token`, `kubernetes.io/dockerconfigjson`, `kubernetes.io/basic-auth`, `kubernetes.io/ssh-auth`, `kubernetes.io/tls` 등)마다 검증과 제약이 다르며, 타입을 쓰지 않으면 `Opaque`이고 내장 타입을 쓰려면 그 요구사항을 모두 맞춰야 한다고 한다. 또 Secret이 기본적으로 API 서버의 데이터 저장소에 암호화되지 않은 채 저장된다고 적는다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. 위 매니페스트를 적용한 뒤 `.stringData`는 비어 있었고 `.data`에는 `user: YWRtaW4=`만 남았다. `data.username`과 `stringData.username`을 모두 준 Secret은 `stringData`의 값(`administrator`의 base64)으로 저장됐다. `data`에 base64가 아닌 `admin`을 쓰면 `illegal base64 data`로 거부됐다. `type: kubernetes.io/tls`에 `tls.crt`와 `tls.key` 없이 `stringData: {foo: bar}`만 주면 `data[tls.crt]: Required value`와 `data[tls.key]: Required value`로 거부됐고, 임의 타입 `example.com/mytype`은 만들어졌다. `kubectl create secret generic`의 타입은 `Opaque`, `docker-registry`는 `kubernetes.io/dockerconfigjson`이었다.
