**모범 답변 (30~60초)**
immutable로 표시하면 `data` 변경 요청이 거부되고, 한 번 켜면 되돌릴 수 없어서 값을 바꾸려면 지우고 새로 만들어야 합니다. 의도하지 않은 수정이 앱 장애로 번지는 것을 막아 주고, Secret을 수만 개 규모로 쓰는 클러스터에서는 kubelet이 immutable 객체를 watch하지 않아도 되어 API 서버 부하가 줄어듭니다. 다시 만들어도 이미 실행 중인 Pod는 이전 마운트를 유지하므로 Pod를 새로 만들어야 합니다. 그래서 쓰는 쪽에서는 값을 바꿀 때마다 반영 방법까지 함께 계획해야 합니다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata: {name: imm}
data: {a: "1"}
immutable: true
```

(공식 문서) Secrets 페이지는 Secret과 ConfigMap을 immutable로 표시할 수 있고(1.21 stable) 의도치 않은 업데이트로 인한 장애를 막고, 수만 개 이상의 고유한 Secret-Pod 마운트를 쓰는 클러스터에서는 kubelet이 immutable Secret을 watch하지 않아 kube-apiserver 부하가 크게 줄어든다고 설명한다. 한 번 immutable로 하면 되돌리거나 `data`를 바꿀 수 없고 삭제 후 재생성만 가능하며, 기존 Pod는 삭제된 Secret의 마운트를 유지하므로 Pod 재생성을 권한다고 한다. ConfigMaps 페이지도 immutable ConfigMap(1.19부터 필드 추가, 1.21 stable)을 같은 방식으로 설명한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `immutable: true`인 ConfigMap과 Secret의 `data`를 패치하자 둘 다 `field is immutable when `immutable` is set`으로 거부됐다. ConfigMap의 `immutable`을 `false`로 되돌리려는 패치와 키를 추가하는 패치도 거부됐고, 레이블 추가는 허용됐다. 두 객체를 지우고 값을 바꿔 다시 만든 뒤 70초 뒤에도 그 값을 마운트하던 기존 Pod의 볼륨 파일은 이전 값 그대로였다. kubelet의 watch 감소로 인한 API 서버 부하 감소는 측정하지 않았고 문서 근거만 있다.
