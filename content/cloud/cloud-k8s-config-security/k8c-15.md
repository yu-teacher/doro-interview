**모범 답변 (30~60초)**
레지스트리 인증 정보를 `kubernetes.io/dockerconfigjson` 타입 Secret으로 만들고(`kubectl create secret docker-registry`), Pod의 `imagePullSecrets`에 그 이름을 적습니다. Secret은 Pod와 같은 네임스페이스에 있어야 합니다. 매번 적기 번거로우면 ServiceAccount의 `imagePullSecrets`에 넣어 두면 그 ServiceAccount를 쓰는 새 Pod에 자동으로 채워집니다. 문서가 권장하는 이 방식은 키를 가진 Pod만 레지스트리에 접근하게 하며, Pod마다 키를 주지 않으려면 노드에 인증을 설정하거나 kubelet 자격 증명 제공자 플러그인을 쓰는 방법도 있습니다. Secret 안의 `auth` 값도 base64일 뿐이라 읽을 수 있는 사람은 토큰을 알 수 있습니다.

```bash
kubectl -n exp-configv create secret docker-registry regkey \
  --docker-server=registry.example.invalid:5000 --docker-username=tiger \
  --docker-password=dummy-pass --docker-email=t@example.invalid
kubectl -n exp-configv patch sa reader -p '{"imagePullSecrets":[{"name":"regkey"}]}'
```

(공식 문서) Images 페이지는 프라이빗 레지스트리 인증 방법으로 Pod의 `imagePullSecrets`(자기 키를 가진 Pod만 접근, 권장), 노드 인증 설정(모든 Pod가 읽음, 클러스터 관리자의 노드 설정 필요), kubelet 자격 증명 제공자 플러그인(kubelet 수준 설정 필요), 미리 받아 둔 이미지를 든다. `imagePullSecrets`는 Pod와 같은 네임스페이스의 `kubernetes.io/dockercfg` 또는 `kubernetes.io/dockerconfigjson` 타입 Secret이어야 한다고 한다. Secrets 페이지는 ServiceAccount가 imagePullSecrets를 참조하게 하면 그 ServiceAccount로 만든 Pod의 필드가 채워진다고 하고, docker config Secret의 `auth` 값이 base64로 가려졌을 뿐 비밀이 아니라고 경고한다. Configure Service Accounts 페이지도 ServiceAccount에 `imagePullSecrets`를 패치하면 새 Pod의 `spec.imagePullSecrets`가 자동으로 채워진다고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `docker-registry` Secret의 타입은 `kubernetes.io/dockerconfigjson`이었고 `.dockerconfigjson`을 디코딩하자 사용자 이름과 비밀번호가 평문 JSON으로 나왔다(예시 값만 사용). ServiceAccount에 `imagePullSecrets`를 패치하기 전에 만든 Pod의 `.spec.imagePullSecrets`는 비어 있었고, 패치 뒤 그 ServiceAccount로 새로 만든 Pod는 `[{"name":"regkey"}]`로 자동 채워졌다. 존재하지 않는 레지스트리 주소(`registry.example.invalid`)의 이미지를 쓴 Pod는 `ErrImagePull`이 되었고 사유는 이름 해석 실패였다. 실제 프라이빗 레지스트리 인증 성공은 확인하지 않았다.
