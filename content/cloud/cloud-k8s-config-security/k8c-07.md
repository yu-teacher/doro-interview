**모범 답변 (30~60초)**
`runAsNonRoot: true`는 UID 0으로 실행되는 컨테이너를 시작하지 못하게 하고, `runAsUser`는 실행할 UID를 정합니다. `allowPrivilegeEscalation: false`는 프로세스가 부모보다 더 많은 권한을 얻지 못하게 하는데 지정하지 않으면 기본값이 true입니다. `readOnlyRootFilesystem: true`는 루트 파일시스템을 읽기 전용으로 마운트하므로 쓰기가 필요한 경로는 `emptyDir` 같은 볼륨으로 따로 줘야 합니다. `capabilities.drop: [ALL]`로 리눅스 capability를 모두 버리는 것도 흔하며, 앞의 비루트와 권한 상승 금지, capability 항목은 restricted 수준의 요구사항과 겹칩니다.

```yaml
securityContext:   # 컨테이너 수준(runAsNonRoot와 runAsUser는 Pod 수준에도 둘 수 있다)
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: {drop: [ALL]}
```

(공식 문서) Configure a Security Context 페이지는 `allowPrivilegeEscalation`이 프로세스가 부모보다 많은 권한을 얻을 수 있는지 정하며 컨테이너의 `securityContext`에 정의하지 않으면 기본값이 true라고 하고, `readOnlyRootFilesystem`은 컨테이너의 루트 파일시스템을 읽기 전용으로 마운트한다고 설명한다. Pod API 참조는 `runAsNonRoot: true`일 때 kubelet이 런타임에 이미지가 UID 0으로 실행되지 않는지 검증하고 root면 컨테이너 시작에 실패하며, 설정하지 않거나 false면 검증하지 않는다고 하고, `runAsUser`는 지정하지 않으면 이미지 메타데이터의 사용자를 쓰며 컨테이너 수준 값이 Pod 수준 값보다 우선한다고 한다. Pod Security Standards의 restricted 표는 `allowPrivilegeEscalation: false`, 비루트 실행, 모든 capability drop(`NET_BIND_SERVICE`만 추가 허용)을 요구하고, 이 페이지에서 `readOnlyRootFilesystem`은 요구 항목으로 나오지 않는다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. Pod 수준에 `runAsNonRoot`와 `runAsUser: 10001`, 컨테이너 수준에 `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, capability 전부 drop, `/tmp`에 `emptyDir`를 준 busybox Pod는 `enforce=restricted` 네임스페이스에서 실행됐다. 컨테이너 안에서 `id`는 `uid=10001`, `touch /w`는 `Read-only file system`으로 실패, `/tmp`에는 파일 생성이 됐고, `/proc/self/status`는 `NoNewPrivs: 1`, `CapEff: 0000000000000000`이었다. 아무것도 지정하지 않은 같은 이미지의 Pod는 `uid=0`, 루트 파일시스템 쓰기 가능, `NoNewPrivs: 0`(기본이 true라는 문서와 같은 방향), `CapEff: 00000000a80425fb`였다.
