**모범 답변 (30~60초)**
Role은 한 네임스페이스 안의 권한이고, ClusterRole은 네임스페이스가 없는 객체라서 노드 같은 클러스터 범위 리소스, `/healthz` 같은 비리소스 URL, 모든 네임스페이스의 리소스에 대한 권한을 정의할 수 있습니다. 권한이 미치는 범위는 바인딩이 정해서, RoleBinding은 한 네임스페이스에, ClusterRoleBinding은 클러스터 전체에 권한을 줍니다. RoleBinding이 ClusterRole을 참조하면 그 권한이 RoleBinding의 네임스페이스 안으로만 한정되므로 공통 역할을 하나 정의해 네임스페이스마다 재사용할 수 있습니다. 바인딩의 `roleRef`는 만든 뒤 바꿀 수 없어서 바꾸려면 지우고 다시 만들어야 합니다.

```bash
kubectl -n exp-configv create rolebinding view-rb --clusterrole=view --serviceaccount=exp-configv:reader
kubectl auth can-i list deployments -n default --as=system:serviceaccount:exp-configv:reader   # no
```

(공식 문서) RBAC 페이지는 ClusterRole이 네임스페이스에 속하지 않으며 네임스페이스 리소스의 권한을 특정 네임스페이스 또는 모든 네임스페이스에 주거나, 클러스터 범위 리소스나 비리소스 엔드포인트(`/healthz`)에 대한 권한을 정의하는 데 쓰인다고 설명한다. RoleBinding은 같은 네임스페이스의 Role을 참조하거나 ClusterRole을 참조해 그 권한을 RoleBinding의 네임스페이스에 한정해 주며, 이렇게 공통 역할을 정의해 여러 네임스페이스에서 재사용할 수 있다고 한다. 클러스터 전체에는 ClusterRoleBinding을 쓴다. 바인딩 생성 후에는 roleRef를 바꿀 수 없고 검증 오류가 나며 삭제 후 다시 만들어야 하는데, 이유는 주체 목록을 관리하는 권한과 부여되는 역할을 바꾸는 권한을 분리하고 다른 역할로의 바인딩은 근본적으로 다른 바인딩이기 때문이라고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. 내장 ClusterRole `view`를 RoleBinding으로 ServiceAccount에 묶자 해당 네임스페이스의 `list deployments`는 `yes`, `default` 네임스페이스는 `no`, `list secrets`와 `create deployments`는 `no`였다. 노드와 Pod 조회를 담은 ClusterRole(`exp-configv-nodes`)을 RoleBinding으로 묶으면 해당 네임스페이스의 `list pods`만 `yes`이고 `list nodes`는 `no`였고, ClusterRoleBinding으로 묶자 `list nodes`와 모든 네임스페이스의 `list pods`가 `yes`가 됐다. 이미 만든 RoleBinding의 `roleRef`를 패치하자 `cannot change roleRef` 오류로 거부됐고 `roleRef`는 `view` 그대로였다. 실험용 ClusterRole과 ClusterRoleBinding은 지웠다.
