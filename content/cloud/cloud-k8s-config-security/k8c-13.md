**모범 답변 (30~60초)**
1.22 이후에는 kubelet이 TokenRequest API로 수명이 제한된 토큰을 받아 projected 볼륨으로 Pod의 `/var/run/secrets/kubernetes.io/serviceaccount`에 마운트하고, 만료 전에 갱신합니다. 이 토큰은 Pod에 묶여 있어서 Pod가 삭제되면 무효가 됩니다. 예전에는 ServiceAccount마다 만료 없는 토큰이 Secret으로 만들어졌고 문서는 장기 자격 증명의 위험 때문에 이를 권하지 않습니다. API 접근이 필요 없는 Pod는 `automountServiceAccountToken: false`로 주입 자체를 막을 수 있고, Pod 설정이 ServiceAccount 설정보다 우선합니다.

```yaml
spec:
  automountServiceAccountToken: false
```

(공식 문서) Service Accounts 페이지는 1.22 이상에서 Pod에 지정한 ServiceAccount의 토큰을 TokenRequest API로 짧은 수명의 자동 갱신 토큰으로 받아 projected 볼륨으로 마운트하고, `automountServiceAccountToken: false`로 자동 주입을 막을 수 있으며, 1.22 이전에는 Secret의 장기 토큰이었다고 설명한다. 만료 없고 갱신되지 않는 토큰 Secret은 더 이상 권장하지 않으며, 1.24 이전에는 ServiceAccount마다 영구 토큰이 자동으로 만들어졌다고 한다. Service Account Administration 페이지는 Pod에 묶인 토큰이 Pod 삭제 시 무효가 되고, 토큰에 묶인 객체의 이름과 uid가 JWT 클레임에 들어가며, kubelet이 가져오는 시간 제한 토큰의 기본 수명이 1시간이고 만료 전에 갱신한다고 설명한다. Configure Service Accounts 페이지는 ServiceAccount와 Pod 둘 다 `automountServiceAccountToken`을 지정하면 Pod 값이 우선한다고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. 기본 ServiceAccount의 Pod에는 `ca.crt`, `namespace`, `token` 세 파일이 `tmpfs`로 마운트됐고 토큰 JWT의 클레임에 `namespace`, 이 Pod의 이름과 uid, 노드 이름, ServiceAccount 이름이 들어 있었다. `automountServiceAccountToken: false` Pod에서는 그 디렉터리가 없었다(`No such file or directory`). ServiceAccount에 `false`를 두고 Pod에 `true`를 쓰면 토큰이 마운트됐고 Pod에 값이 없으면 마운트되지 않았다. `kubectl create token reader`로 받은 토큰은 `exp`와 `iat`의 차이가 3600초였고 ServiceAccount의 `secrets` 목록은 비어 있었으며 네임스페이스에 토큰 Secret이 자동 생성되지 않았다. Pod에서 꺼낸 토큰으로 API 서버를 호출하면 200이었다가 Pod를 지운 뒤에는 401이었고 `create token`으로 받은 토큰은 200이었다. Pod에 마운트된 토큰의 `exp`는 발급 시각에서 1년 뒤로 찍혀 있었는데 이유는 확인하지 않았다(문서에서 확인한 1시간 기본 수명과 다르다).
