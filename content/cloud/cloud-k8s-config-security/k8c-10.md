**모범 답변 (30~60초)**
접근 모드는 PVC와 PV를 맞추는 기준이면서 볼륨을 어디에 마운트할 수 있는지를 나타냅니다. `ReadWriteOnce`는 하나의 노드에서 읽기·쓰기로 마운트된다는 뜻이라 같은 노드에 있는 여러 Pod는 함께 쓸 수 있습니다. 클러스터 전체에서 Pod 하나만 쓰게 하려면 `ReadWriteOncePod`를 써야 하고 1.29부터 stable이며 CSI 볼륨 대상입니다. `ReadOnlyMany`는 여러 노드에서 읽기 전용, `ReadWriteMany`는 여러 노드에서 읽기·쓰기 마운트입니다. 접근 모드가 마운트 후의 쓰기를 막아 주지는 않으므로 읽기 전용이 필요하면 별도로 보장해야 합니다.

```yaml
spec:
  accessModes: [ReadWriteOncePod]   # 한 번에 Pod 하나만
```

(공식 문서) Persistent Volumes 페이지는 `ReadWriteOnce`가 단일 노드에서 읽기·쓰기 마운트이고 같은 노드에서 실행되는 여러 Pod는 접근할 수 있다고 하며, 단일 Pod 접근에는 `ReadWriteOncePod`(1.29 stable)를 쓰라고 한다. `ReadOnlyMany`와 `ReadWriteMany`는 여러 노드에서 읽기 전용, 읽기·쓰기 마운트다. 접근 모드는 PVC와 PV를 맞추는 데 쓰이고 일부 경우에 마운트 위치를 제약할 뿐 마운트 후 쓰기 보호를 강제하지 않으며, `ReadWriteOncePod`만 하나의 Pod로 제약한다고 한다. `ReadWriteOncePod`는 CSI 볼륨과 1.22+에서만 지원된다고 적혀 있다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. 노드가 하나인 이 클러스터에서 `ReadWriteOnce` PVC 하나를 Pod 두 개가 마운트하자 둘 다 `Running`이었다. `ReadWriteOncePod` PVC는 `RWOP`로 바인딩되고 먼저 만든 Pod만 `Running`, 두 번째 Pod는 `Pending`이었으며 이벤트는 `PersistentVolumeClaim with ReadWriteOncePod access mode already in-use by another pod`였고, 첫 Pod를 지우자 두 번째 Pod가 `Running`이 됐다. 이 클러스터에는 `kubectl get csidrivers` 결과가 없고(`No resources found`) provisioner는 `docker.io/hostpath`인데도 RWOP 제약은 적용됐다. 문서의 CSI 한정 조건은 이 결과로 검증되지 않았으므로 문서 근거로만 둔다. 이 단일 노드에서는 RWO가 다른 노드의 Pod 마운트를 막는 동작은 확인할 수 없었다.
