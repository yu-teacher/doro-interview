**모범 답변 (30~60초)**
`default` ServiceAccount는 `serviceAccountName`을 지정하지 않은 같은 네임스페이스의 모든 Pod가 쓰기 때문에, 여기에 준 권한은 그런 Pod 전부가 갖게 됩니다. 앱 하나를 위해 준 권한이 관계없는 Pod에도 퍼지고, 그중 하나가 침해되면 마운트된 토큰으로 그 권한을 쓸 수 있습니다. 문서가 가장 안전한 방법으로 꼽는 것은 애플리케이션 전용 ServiceAccount를 만들고 Pod에 `serviceAccountName`으로 지정해 거기에만 권한을 주는 것입니다. API가 필요 없는 Pod는 `automountServiceAccountToken: false`로 토큰 주입도 끌 수 있습니다.

```bash
kubectl -n exp-configv create rolebinding default-read --role=pod-reader --serviceaccount=exp-configv:default
```

(공식 문서) RBAC 페이지의 ServiceAccount permissions 절은 가장 안전한 것부터 애플리케이션 전용 ServiceAccount에 역할 부여(모범 사례), 네임스페이스의 `default` ServiceAccount에 부여, 네임스페이스의 모든 ServiceAccount에 부여 순으로 설명하고, `default`에 준 권한은 `serviceAccountName`을 지정하지 않은 네임스페이스의 모든 Pod가 쓸 수 있다고 한다. RBAC Good Practices 페이지는 강력한 권한의 ServiceAccount를 Pod에 주지 말고 권한 있는 토큰의 배포를 최소화하라고 하며, 기본 자동 마운트를 `automountServiceAccountToken: false`로 피하고 Pod에 설정하면 ServiceAccount 설정을 덮어쓴다고 한다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `default` ServiceAccount 기반 Pod는 권한을 주기 전에 API 서버에 Pod 목록을 요청하면 403이었다. `pod-reader` Role을 `default`에 바인딩한 뒤 `serviceAccountName` 없이 새로 만든 Pod는 같은 요청에서 200이었고, 다른 ServiceAccount(`pull-sa`)를 쓰는 Pod는 같은 요청에서 403이었다. `can-i`로 보면 다른 네임스페이스(`exp-configv-b`)의 Pod 조회와 같은 네임스페이스의 Secret 조회는 `no`였다.
