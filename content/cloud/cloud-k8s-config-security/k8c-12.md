**모범 답변 (30~60초)**
볼륨으로 마운트하면 키가 파일이 되고 항상 읽기 전용이며, kubelet은 이 사본을 디스크가 아니라 tmpfs에 둬서 비휘발성 저장소에 쓰이지 않게 합니다. Secret이 바뀌면 볼륨 파일은 시간이 지나 갱신되지만 `subPath` 마운트는 갱신되지 않고, 환경 변수로 쓰는 값은 컨테이너를 재시작해야 바뀝니다. Secret은 그것을 쓰는 Pod가 있는 노드에만 전달되고 Pod가 지워지면 노드의 사본도 지워집니다. 참조한 Secret이 없으면 `optional`로 표시하지 않은 한 컨테이너가 시작하지 않습니다.

```yaml
volumes:
- name: s
  secret: {secretName: db}     # optional: true 를 주면 없어도 시작
```

(공식 문서) Secrets 페이지는 Secret이 그것을 필요로 하는 Pod가 있는 노드에만 전송되고, 볼륨 마운트 시 kubelet이 데이터 사본을 tmpfs에 두어 내구성 있는 저장소에 쓰이지 않으며 Pod가 삭제되면 노드의 사본도 지운다고 설명한다. Volumes 페이지는 secret 볼륨이 tmpfs로 백업되어 비휘발성 저장소에 쓰이지 않고 항상 읽기 전용으로 마운트되며 `subPath` 사용 컨테이너는 갱신을 받지 못한다고 한다. Secrets 페이지는 볼륨의 Secret이 갱신되면 결국 일관성(eventually-consistent) 방식으로 볼륨 데이터를 갱신한다고 하고, Distribute Credentials Securely 페이지는 환경 변수로 쓰는 값은 컨테이너를 재시작해야 갱신이 보인다고 적는다. 기본적으로 Secret은 필수이고 없거나 키가 없으면 시작이 안 되며 `optional: true`면 무시된다고 한다. 노드에만 전달되는 동작은 단일 노드라 실험하지 않았고 문서 근거만 있다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. Secret을 볼륨으로 마운트한 Pod의 `/proc/mounts`에는 `tmpfs /etc/sec tmpfs ro,relatime,...`가 보였고, 그 안에 `touch`를 하면 `Read-only file system`이었다(볼륨 마운트에 `readOnly`를 따로 주지 않았다). Secret 값을 `v1`에서 `v2`로 패치하고 약 60초 뒤에 볼륨 파일은 `v2`로 바뀌었지만 같은 Secret의 `subPath` 마운트 파일과 `secretKeyRef` 환경 변수는 `v1` 그대로였다. 존재하지 않는 Secret을 `envFrom`으로 참조한 Pod는 `CreateContainerConfigError`와 `secret "nosuch" not found`였고, 있는 Secret의 없는 키를 `secretKeyRef`로 참조하면 `couldn't find key nokey in Secret ...`였다. 없는 Secret을 볼륨에서 `optional: true`로 참조한 Pod는 `Running`이었다. 다른 네임스페이스에만 있는 Secret을 참조해도 `not found`였다.
