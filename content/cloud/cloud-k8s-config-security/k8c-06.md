**모범 답변 (30~60초)**
Pod Security Standards는 privileged, baseline, restricted 세 단계로 누적되는 정책을 정의합니다. privileged는 제한이 없고, baseline은 호스트 네임스페이스 공유나 특권 컨테이너처럼 알려진 권한 상승을 막으면서 기본 설정의 Pod는 허용하며, restricted는 비루트 실행과 권한 상승 금지 같은 모범 사례까지 요구합니다. 이를 적용하는 내장 Pod Security Admission은 네임스페이스에 `pod-security.kubernetes.io/enforce`, `audit`, `warn` 레이블을 달아 씁니다. enforce는 위반한 Pod를 거부하고, warn은 사용자에게 경고만 보여 주며, audit은 감사 로그에 주석을 남깁니다.

```bash
kubectl label ns exp-configv pod-security.kubernetes.io/enforce=baseline
```

(공식 문서) Pod Security Standards 페이지는 세 정책이 누적적이고 privileged는 제한 없음, baseline은 알려진 권한 상승을 막으면서 기본 Pod 설정을 허용, restricted는 현재의 Pod 강화 모범 사례를 따른다고 설명한다. Pod Security Admission 페이지는 Stable(1.25부터)이며 네임스페이스 레이블 `pod-security.kubernetes.io/<MODE>: <LEVEL>`로 enforce(위반 시 Pod 거부), audit(감사 로그에 주석 추가, 허용), warn(사용자 경고, 허용) 모드를 설정하고 한 네임스페이스에 여러 모드를 서로 다른 수준으로 쓸 수 있다고 한다. 이 페이지는 확인 시점에 v1.37 문서로 표시됐다.
(실험 확인) Kubernetes v1.36.1 Docker Desktop 단일 노드 클러스터(kubeadm, 컨텍스트 docker-desktop)에서 재실행했다. `warn=restricted`만 단 네임스페이스에서 설정 없는 busybox Pod는 `Warning: would violate PodSecurity "restricted:latest"` 경고와 함께 생성되어 `Running`이 됐다. `enforce=restricted`에서는 같은 Pod가 `Forbidden`으로 거부됐고 사유로 `allowPrivilegeEscalation`, `capabilities.drop`, `runAsNonRoot`, `seccompProfile` 네 가지가 나열됐다. `enforce=baseline`에서는 `privileged: true` Pod가 `privileged (container "c" must not set securityContext.privileged=true)`로, `hostNetwork: true` Pod가 `host namespaces (hostNetwork=true)`로, `hostPath` 볼륨 Pod가 `hostPath volumes (volume "h")`로 거부됐고 설정 없는 일반 Pod는 생성됐다. `enforce=privileged`에서는 `privileged: true` Pod도 생성됐다. audit 모드의 감사 로그 기록은 확인하지 않았고 문서 근거만 있다.
