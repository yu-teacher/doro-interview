# M1 상세 계획 — 질문 은행 (읽기 전용 API + 화면)

> 범위: [DESIGN.md](DESIGN.md) §12의 M1. **로그인·체크·시험은 만들지 않는다**(M2·M3). 검수는 병행 트랙으로 분리했다: [REVIEW-TRACK.md](REVIEW-TRACK.md).
> 상태: **확정 (2026-10-20), 구현 중.** §3 의 D4·D12·D13·D14 는 사용자가 확정했다.

## 1. 목표와 완료 기준

M1은 **기능 완료**와 **공개 완료**를 나눠서 닫는다. 검수가 끝난 주제가 있어야 공개할 수 있는데, 검수는 개발과 독립된 트랙이라 개발이 거기에 막히면 안 되기 때문이다.

### 기능 완료 (개발 트랙, 이 문서의 S1~S8)
1. 로그인 없이 카테고리 → 주제 → 질문 상세를 열람하고 검색할 수 있다.
2. **검색이 한국어 부분 일치**다(예: "전파"가 "트랜잭션 전파 속성" 제목·키워드·본문에 걸린다). 여러 단어는 AND, 제목 > 키워드 > 본문 순으로 정렬한다.
3. **비공개 주제·닫힌(retired) 질문은 모든 API에서 404**다(목록·상세·검색 어디로도 새지 않는다).
4. 질문 상세에 **근거 배지**(공식 문서 / 보충 / 실험 확인), 핵심 키워드, 주제 출처 링크, 기준 버전이 보인다. 코퍼스 159개 본문이 전부 깨지지 않고 렌더링된다.
5. 모바일(320·375·414 폭, 가로 모드)에서 가로 넘침·글자 잘림이 없다(실제 브라우저로 측정).
6. 실제 jar + 실제 DB + 실제 브라우저로 "주제 → 질문 → 검색" 한 경로가 통한다(통합 e2e 1개).
7. 모든 테스트가 초록이고 `scripts/ci-test.sh all` 에 새 테스트가 포함된다.

### 공개 완료 (병행 트랙 + 사용자 서버 작업, §6·§7)
8. 트랜잭션 편 25개가 `REVIEWED`이고 `published: true` 로 공개된다([REVIEW-TRACK.md](REVIEW-TRACK.md)).
9. 읽기 전용 서비스가 서버에 배포되어 공개 주소 `/interview/` 로 열린다(★ 사용자 서버 작업 포함).

## 4. 작업 순서

각 단계는 **테스트가 초록인 상태로 로컬 커밋**한다. 변이 확인(일부러 망가뜨려 테스트가 실패하는지 보기)은 ◆ 표시.

### S1. 공통 기반
- `common` 패키지: `ApiResponse`, `ErrorCode`, `InterviewException`, `GlobalExceptionHandler`(404/400/500 규격, 스택 트레이스 미노출).
- 모듈 규칙 갱신: `common`은 다른 모듈에 의존하지 않고, 모든 모듈은 `common`에 의존할 수 있다. 규칙 자체 시험(fixture)에도 반영.
- 검증: 예외 → 응답 규격 단위 테스트, 아키텍처 테스트 통과 ◆(`common`이 `catalog`를 import 하는 위반 fixture 가 실패).

### S2. 카탈로그 조회 서비스
- **V2 마이그레이션**: `question.sources JSONB NOT NULL DEFAULT '[]'`(D14). 파서·검증기·로더에 선택 필드 `sources` 추가(URL 형식 검증, 해시 제외).
- `catalog` 모듈에 `CatalogReader`(인터페이스) + JDBC 구현. 반환 모델: 카테고리(주제 목록·주제별 질문 수·tier 분포), 주제(출처·기준 버전·설명), 질문 요약, 질문 상세(+이전/다음 질문 slug, `needsReview`, 질문별 `sources`, **`spokenAnswer`/`evidenceMd` 분리(D13)**).
- D3 노출 규칙을 **쿼리 한 곳**에 둔다(모든 조회가 같은 조건을 쓰게). D4 스위치는 이 조건에서만 읽는다.
- 검증(전용 스키마 + 고정 데이터): `sources` 파싱·저장·해시 제외(sources 만 바꿔도 `content_hash`·`needs_review` 불변), 답변 분리(코퍼스 159개 전부 `spokenAnswer`+`evidenceMd` 가 원문과 같음, 모범 답변 블록이 정확히 하나), 공개/비공개/닫힘 조합별 목록·상세 결과, 정렬(주제 sort → tier BASIC/DEEP/TRICKY → 질문 sort), 주제별 질문 수에서 닫힌 질문 제외. ◆ 노출 조건 제거 시 비공개 노출 테스트 실패.

### S3. 검색
- 입력 정규화: 공백 분리 단어 ≤ 5개, 단어당 ≤ 50자, 전체 ≤ 100자, 빈 입력은 400. **LIKE 와일드카드(`%`, `_`, `\`) 이스케이프**.
- 규칙: 모든 단어가 (제목 | 키워드 | 본문) 중 하나에 부분 일치(AND), 대소문자 무시. 점수 = 단어마다 제목 3 + 키워드 2 + 본문 1 합산, 동점은 정렬 규칙(S2). `matchedIn`(title/keywords/body)을 결과에 포함. 비공개·닫힘 제외(D3).
- 검증: 한국어 부분 일치("전파"→"트랜잭션 전파 속성"), 영문 대소문자("requires_new"), 여러 단어 AND, 점수 순서(제목 일치 > 본문 일치), `%`·`_` 입력이 와일드카드로 동작하지 않음, 너무 긴 입력·빈 입력, 비공개 비노출, SQL 인젝션 문자열이 데이터로만 취급됨. 실제 코퍼스(159)에서 "프록시" 검색이 기대 질문들을 반환.

### S4. API (`api` 패키지)
- `GET /api/v1/categories`(주제 포함), `GET /api/v1/topics/{slug}`(주제 + 질문 요약 목록), `GET /api/v1/questions/{slug}`, `GET /api/v1/search?q&limit`.
  - 게이트웨이가 `/interview` 를 떼므로 앱 안의 경로는 `/api/v1/...`(games와 같음). DESIGN §9의 `/v1/...` 표기와 접두 `/api` 를 일치시킨다.
- 헤더: 응답 `Cache-Control: no-cache` + 상세는 `ETag`(content_hash 기반, 조건부 요청 304). 보안 헤더는 게이트웨이/웹 nginx 몫.
- D4 스위치 + prod 가드: `prod` 프로파일에서 `expose-unpublished=true` 면 기동 거부.
- 검증(MockMvc/전체 컨텍스트, 전용 스키마): 각 엔드포인트 정상, 비공개 주제·닫힌 질문·없는 slug 가 **동일한 404 본문**(존재 여부 비노출), 검색 400/성공, ETag/304, prod 가드 거부 ◆(가드 제거 시 실패), 인증 없이 호출 가능.

### S5. 웹 기반
- Tailwind 4, react-router, API 클라이언트(`fetch`, 오류 규격 파싱, 404·네트워크 오류 구분), 레이아웃(헤더·검색창·다크 모드 토글 없이 시스템 설정 따름), 개발 서버 프록시(`/interview/api` → 8088, 게이트웨이처럼 접두 제거).
- 린트 규칙: `dangerouslySetInnerHTML` 금지, 기존 games 규칙(any·빈 catch·console.log·location.reload 금지) 이식.
- 검증: lint·tsc·vitest, 클라이언트 단위 테스트(오류 파싱, 경로 생성).

### S6. 마크다운 렌더러
- react-markdown + 배지 변환(remark 플러그인) + lowlight. D5·D6 규칙.
- 단위 테스트: 배지 4종 + 접두 형태, `(공식 문서의 패턴을 …)` 은 배지가 아님, 글머리 목록, 코드 블록 언어별 하이라이트, `Optional<T>` 가 글자 그대로 보임, `<script>` 입력이 실행·삽입되지 않고 글자로 보임.
- **코퍼스 골든 테스트**: 159개 본문 전부 렌더링(서버 렌더링 API 사용). 확인: ① 예외 없음 ② 코드 블록 수 = 펜스 수/2 ③ 배지 수 = 정규식으로 센 토큰 수 ④ `has_extra=true` 질문은 보충 배지가 정확히 있다 ⑤ 렌더 결과에 원시 `<script`/`<img`가 없음. ◆ 배지 정규식을 망가뜨리면 ③이 실패.
- 번들 예산: 초기 JS gzip **≤ 200KB**(현재 69.7KB, React 포함). 초과하면 하이라이트를 지연 로딩.

### S7. 화면
- **홈**: 카테고리 → 주제 카드(질문 수, tier 분포, 기준 버전). 공개 주제가 없으면 "검수 중인 주제입니다" 빈 상태(오류처럼 보이지 않게).
- **주제**: tier 탭(BASIC/DEEP/TRICKY/전체), "보충 포함" 필터, 주제 안 검색, 질문 요약 카드(제목·키워드·tier·보충 여부).
- **질문 상세**: 제목, tier·난이도, 키워드 칩, 본문(렌더러), "재검수 필요" 안내(`needsReview`), 출처 링크(주제 단위, 새 탭 `rel="noopener noreferrer"`), 기준 버전, 이전/다음.
- **검색 결과**: 일치 위치 표시, 결과 0건 안내, 입력 디바운스.
- 접근성 기본: 랜드마크·제목 계층, 키보드로 모든 조작 가능, 포커스 표시, 색 대비(WCAG AA), 터치 영역 ≥ 44px.
- 검증: 컴포넌트 테스트(로딩·빈 상태·오류·404 화면), 라우팅(없는 slug → 안내 화면).

### S8. 브라우저 검증 (실제 Chromium, 헤드리스)
- 모바일 레이아웃 e2e: games의 방식 이식(API 응답은 `page.route` 가짜 데이터). 폰 320·375·414 세로 + 812×375 가로. 가로 넘침·글자 잘림·터치 영역·입력 글꼴을 측정. **Playwright는 내장 Chromium 헤드리스**(`PW_CHANNEL=chrome` 금지, 저장소 규칙). 브라우저가 없으면 `web/` 에서 `npx playwright install chromium`.
- **통합 e2e 1개**: 격리 Postgres + 빌드한 jar(`expose-unpublished` 켬) + 웹 빌드 서빙 + 실제 브라우저로 홈 → 주제 → 질문(배지·코드 블록 확인) → 검색. curl 만으로 끝내지 않는다(허브 빈 화면 사고의 교훈).
- CI 반영: `ci.yml` web 잡에 chromium 설치 + `test:mobile`, backend 잡 또는 별도 잡에 통합 e2e. ◆ 일부러 가로 넘침을 만들어 모바일 테스트가 실패하는지 확인.

### S9. 배포 준비물 (서버 반영은 ★ 사용자)
- 만들 것: 웹 `Dockerfile`+`nginx.conf`(games 패턴, 정적 자산 장기 캐시·SW/매니페스트 재검증 규칙은 M2), `docker-compose.prod.yml`(API 8088·웹 3007, `127.0.0.1` 바인딩, 외부 네트워크 `doro_doro-network`), `deploy/gateway-interview.conf`(게이트웨이 조각: upstream·`/interview/api/`·`/interview/`·`= /interview` 301, CSP는 `script-src 'self'`), `scripts/apply-gateway-interview.sh`(백업 → `nginx -t` → reload, `--report-only` CSP), `scripts/setup-interview-server.sh`(`service_interview` DB·전용 역할·`.env`, 멱등, `--dry-run` 기본, 비밀 값 출력 금지), `docs/DEPLOY.md`.
- 규칙 준수(Doro `GATEWAY_ROUTING_RULES.md` §6): 접두는 `/interview/` 로 구체적, 헤더 4개, 가장 긴 프리픽스 우선, 정규식 location(포털 `/login`… 등)과 겹치지 않음, Guard 를 프록시하지 않음, 반영 전 `nginx -t` + 반영 후 공개 주소로 실제 호출.
- 이번에 **하지 않는 것**: BFF 클라이언트 등록·Guard 스키마·IAM 연동(M2), CD 워크플로 활성화(M2), 서비스 워커.
- 검증(서버 없이 가능한 범위): 웹 이미지 빌드·기동 후 `/interview/` 200, compose 문법 검증(`docker compose config`), 게이트웨이 조각을 임시 nginx 컨테이너에 끼워 `nginx -t` 와 라우팅 응답(HTTP) 확인, 스크립트 `--dry-run` 출력.

## 9. 문제(질문) 도메인을 고도화할 필요가 있나 — 검토와 결정 (2026-10-20, **A·B 확정**)

**결론: 큰 고도화는 지금 필요 없다. 작은 보강 둘(A·B)만 M1 에 넣는다 — 사용자가 확정했다.** 아래는 후보별 판단이다.

| 후보 | 얻는 것 | 비용 | 판단 |
|---|---|---|---|
| **A. 모범 답변 / 근거 분리** (말로 하는 답 ↔ 출처·보충·실험 설명) | 시험(M3)에서 "내 답 ↔ 모범 답변"만 먼저 비교하고 근거는 나중에 펼침. 검수 대상(근거)이 분명해짐 | **낮음**: 시드 구조가 이미 `**모범 답변` 블록 뒤에 근거 줄이 오므로 **저장 형식 변경 없이** 렌더·API 에서 나눈다 | **채택·확정 (M1 S2/S6, D13)**. 분리 규칙은 코퍼스 테스트로 고정 |

**왜 작게 가나**
1. 가치의 병목은 모델의 풍부함이 아니라 **콘텐츠의 정확성(검수)과 양(주제 확장)** 이다. 159개 중 REVIEWED 가 0개인 상태에서 필드를 늘리면 검수·작성 부담만 커진다.
2. 콘텐츠가 **frontmatter 가 있는 파일**이라 필드 추가가 **하위 호환**이다(선택 필드, 기존 파일 무변경). 지금 안 만든 것을 나중에 만드는 비용이 낮다.
3. 지금의 도메인 경계(`catalog` 가 질문을 소유, 사용자 상태는 `progress`/`quiz`)는 위 후보들을 모두 `catalog` 안에서 흡수할 수 있다. 경계가 바뀌지 않는다.

**A·B 를 채택할 때 바뀌는 것** (승인 시): S2 에 마이그레이션 `V2`(`question.sources JSONB NOT NULL DEFAULT '[]'`), 파서·검증기(선택 필드 `sources` 의 URL 형식, 질문 출처는 주제 출처의 부분집합이 **아니어도** 허용하되 경고 대상으로 표시), 로더 upsert, 해시 제외 테스트, API 응답 `spokenAnswer`/`evidenceMd` 분리 필드, 코퍼스 테스트("모범 답변 블록이 정확히 하나, 분리 후 두 부분을 합치면 원문과 같다"). (확정되어 §3 D13·D14 와 S2 에 반영했다.)
