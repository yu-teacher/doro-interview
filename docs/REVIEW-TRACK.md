# 검수 트랙 — 트랜잭션 편 25개를 REVIEWED 로

> M1 개발([M1-PLAN.md](M1-PLAN.md))과 **병행**하는 독립 트랙. 개발은 이 트랙을 기다리지 않는다. 이 트랙이 끝나야 **공개 완료**(M1-PLAN §1의 8·9번)가 가능하다.
> 상태: **제안 (2026-10-20)**. 시작 전 사용자 승인이 필요하다.

## 1. 목적과 게이트
- 시드 159개는 전부 `DRAFT`다. "공식 문서를 모델이 읽고 요약했다"는 2차 전달이라 틀린 내용이 섞여 있을 수 있다(DESIGN §3.3-4). 공개 서비스에서 틀린 정답은 면접 준비를 오도하므로 **검수가 노출 조건**이다.
- 이 트랙의 산출: 트랜잭션 편 25개가 `status: REVIEWED` + `reviewed_at`, 주제 `published: true`. 로더의 검증기가 "공개 주제는 모든 질문이 REVIEWED"를 강제한다(이미 구현됨).
- 트랜잭션을 첫 주제로 하는 이유: ① 실험 36개(`TxExperimentTest` 8 + `tx/` 28)가 **실행 가능한 독립 근거**다 ② 면접 빈출 ③ 공식 문서 출처가 9개로 명확하다.

## 2. 누가 무엇을 하나

| | Claude | 사용자 |
|---|---|---|
| 근거 대조 | 질문마다 **주장 단위**로 출처 문서와 대조해 표를 만든다(§4) | 표를 읽고 판정에 동의하는지 결정 |
| 실험 | 본문이 인용한 실험 테스트를 실제로 실행해 통과를 확인 | — |
| 수정 | 불일치·미확인 항목의 수정안을 제안하고 승인 후 파일에 반영 | 승인·거절, 말투·표현 조정 |
| 확정 | 승인된 질문만 `REVIEWED` 처리하고 커밋 | **최종 책임자.** 원문 표본 확인 |

사용자가 최종 책임자인 이유: 같은 모델이 만든 초안을 같은 모델이 검증하면 **오류가 상관**되기 쉽다. 그래서 아래 안전장치를 둔다.

## 3. 상관 오류를 줄이는 안전장치
1. **원문을 직접 가져와 대조**한다(요약 기억이 아니라 해당 문서 페이지의 현재 내용). 표에 **문서 URL과 절 이름**을 적어 사용자가 클릭해서 원문을 볼 수 있게 한다.
2. **고위험 주장**(기본값·숫자·예외·"항상/절대" 표현·버전 의존)은 표에서 따로 표시하고, 사용자가 **전부 원문으로 직접 확인**한다.
3. 나머지는 사용자가 **표본 20% 이상**을 원문으로 확인하고, 하나라도 표와 어긋나면 그 배치 전체를 다시 대조한다.
4. **실험은 독립 증거**다: 본문이 "실험 확인"이라고 한 주장은 테스트를 실제로 돌려 통과해야 한다(문서와 실험이 다르면 실험이 맞다는 시드의 규칙 유지).
5. 공식 문서가 다루지 않는 내용은 억지로 "공식"으로 만들지 않고 `(보충)`으로 남긴다. 단 보충도 틀리지 않았는지 본다.

## 4. 질문 하나의 검수 절차

**4.1 근거 대조표** (질문마다, 작업용 문서 `.private/review/transaction.md` — git 제외)

| 주장(요약) | 본문 표기 | 출처 URL·절 | 판정 | 고위험 | 조치 |
|---|---|---|---|---|---|
| 예) 트랜잭션은 스레드에 바인딩되어 새 스레드로 전파되지 않는다 | (공식 문서) | …/annotations.html · "Transaction settings" | 일치 | 예(범위 한정) | 없음 |

판정: **일치** / **불일치**(수정 필요) / **문서에 없음**(보충으로 유지 또는 삭제) / **버전 차이**(기준 버전 명시) / **확인 불가**(출처 접근 실패 등 — 확정 금지).

**4.2 체크리스트 (질문당, 전부 만족해야 REVIEWED)**
1. 사실 주장이 출처와 일치하고, 불일치는 수정됐다.
2. `(보충)` 표기는 보충으로 남아 있고 틀리지 않다. 근거가 있는데 보충으로 표기된 것은 공식으로 올린다.
3. 기준 버전(Spring Framework 7 / Boot 4)에 맞다. 버전 의존 설명은 버전을 적었다.
4. 실험 인용이 있으면 해당 테스트가 통과한다.
5. **"데모 근거" 등 비공개 데모 프로젝트 언급**을 독자가 확인할 수 있는 형태(일반 설명 또는 짧은 코드 발췌)로 바꿨다. 클래스·메서드 이름만 남기지 않는다.
6. 모범 답변이 30~60초 분량으로 말할 수 있고(대략 250~450자), 핵심 키워드가 답변 안에 실제로 등장한다.
7. 오탈자·코드 블록 문법이 맞다.

**4.3 반영**: 수정은 `content/spring/transaction/tx-NN.md` 에 직접. `status: REVIEWED`, `reviewed_at: YYYY-MM-DD` 추가. 본문이 바뀌면 로더가 해시를 갱신한다(DRAFT→REVIEWED 전환 자체는 `needs_review`를 올리지 않는다).

## 6. 도구 (작게)

## 7. 종료 조건과 다음 주제

## 9. 메타데이터 작성: 개념 사전·질문 연결·필수도 (M1-PLAN D15~D17)

검수와 **같은 배치에서** 한다(질문을 이미 읽고 있어 가장 싸다). **트랜잭션 편부터**, 값은 모두 사용자 승인으로만 파일에 들어간다. 승인 전 값은 비워 둔다(코드는 값이 없어도 동작한다).

**9.1 개념 사전(`content/_concepts.yml`)**
- 개념 = 주제를 가로지르거나 면접에서 하나의 이야기로 묶이는 것(예: 프록시, 트랜잭션 경계, 영속성 컨텍스트, 빈 생명주기). 목표 30~50개, 동의어 금지, slug 영소문자·하이픈(한 번 정하면 불변), 이름은 짧은 한국어 명사구.
- 순서: B1 에서 tx 8개를 읽으며 **초안 사전 10개 안팎**을 Claude 가 제안 → 사용자 승인 → 파일 반영. 이후 배치에서 필요한 개념만 추가(추가도 승인).
- 질문당 개념 **1~3개**(핵심 개념 우선). 사전에 없는 개념을 쓰면 로더 검증이 거부한다.

**9.2 질문 연결(`links`)**
- `FOLLOWUP`: 이 질문에 답하면 면접관이 이어 물을 만한 질문. `PREREQ`: 이 질문을 이해하려면 먼저 알아야 하는 질문. `RELATED`: 같이 보면 좋은 질문(방향 없음).
- 출처 질문에만 적는다. 질문당 ≤ 5개. 주제를 가로질러도 된다(예: aop-10 ↔ tx-15). FOLLOWUP·PREREQ 는 순환 금지(검증기가 거부).
- 기준: **면접관이 실제로 이어 묻는 흐름**만. 억지 연결 금지. 키워드 겹침은 후보로 쓰지 않는다(12/159로 실측, 의미로 읽고 제안).

**9.3 필수도(`importance`) 기준표**
| 값 | 뜻 | 예 |
|---|---|---|
| 3 필수 | 신입·주니어 백엔드 면접에서 개념 이해를 거의 반드시 확인한다 | 트랜잭션 ACID, `@Transactional` 동작 원리 |
| 2 자주 | 자주 나오지만 회사·맥락에 따라 갈린다 | 전파 속성, 격리 수준 |
| 1 심화 | 경력·함정 질문. 모르면 감점은 작고 알면 가산 | 프록시 모드별 차이, 특수한 예외 규칙 |
- **통계가 아니라 판단값**이다. 외부 질문 수집·크롤링은 하지 않는다(콘텐츠 정책 §4). 근거가 약한 질문은 비워 둔다(미분류).
- 한 주제에서 3의 비율이 지나치게 높으면(과반) 기준을 다시 맞춘다.

**9.4 절차(배치마다)**: 검수 대조표(§4.1)에 열 세 개(개념 제안·연결 제안·필수도 제안)를 더해 한 번에 보여 준다 → 사용자가 질문별로 승인/수정 → 승인분만 `concepts`/`links`/`importance` 로 파일에 반영 → 같은 배치 커밋. 형식은 README 의 "콘텐츠 추가·수정 방법"에 있다(S2b 에서 갱신).

**9.5 B1(이미 검수한 tx-01~08)에 대한 소급**: B1 의 이어 작업으로 8개에 대해 개념 사전 초안·연결·필수도 제안을 만든다. 본문 해시가 바뀌지 않으므로 REVIEWED 상태나 `needs_review` 에 영향이 없다.
