# 도로 면접 (doro-interview) 기획

> 상태: **기획 확정 (2026-10-20)**. 코드 없음. §13의 결정 사항은 모두 확정이다. 착수 계획은 [M0-PLAN.md](M0-PLAN.md). 시드 실측으로 바로잡은 가정은 §3.3.

## 1. 한 줄 소개
**자바·스프링·네트워크·DB 등 개발 면접 질문을 종합적으로 모아 두고, 내가 "완전히 학습했다"고 체크한 질문들만 랜덤으로 받아 실전처럼 점검하는** 면접 준비 서비스. 도로의 서브 서비스(`/interview/`).

핵심 루프: **사전에서 읽고 공부 → 학습 완료 체크 → 시험에서 체크한 것만 랜덤 출제 → 틀린 질문은 '다시 공부 후보'로 표시 → 사전에서 직접 체크를 해제하고 다시 공부.**

제품은 두 영역으로 나뉜다: **사전**(질문 은행·체크·노트)과 **시험**(랜덤 면접·퀴즈·현황). 시험은 사전의 체크 상태를 **읽기만** 하고 바꾸지 않는다(§6.0).

## 2. 대상, 목표, 비목표
- 대상: 만든 사람과 지인(도로 계정을 가진 사람). 불특정 다수 서비스가 아니다.
- 범위: 주제는 계속 늘어난다. 지금은 스프링 7편뿐이지만 **카테고리(자바, 스프링, 네트워크, DB, OS, 자료구조, 시스템 설계 …) 아래에 주제(편)가 쌓이는 구조**로 처음부터 만든다.
- 목표
  1. **사전 영역**(상단 탭 "사전"): 카테고리·주제·난이도·근거 종류로 훑고 검색한다.
  2. **학습 완료 체크(개인별)**: 질문마다 "완전히 학습함"을 내가 직접 표시한다. 카테고리·주제별 진도가 보인다.
  3. **랜덤 면접**: 체크한 질문(기본)만 풀로 삼아 랜덤으로 출제한다. 답해 본 뒤 모범 답변과 비교하고 스스로 평가한다. 틀린 질문은 체크를 **자동으로 바꾸지 않고** 사전에서 "다시 공부 후보"로 보이게 한다. 체크 해제는 사용자가 사전에서 직접 한다.
  4. **신뢰**: 답변의 각 주장이 "공식 문서 확인 / 덧붙인 설명 / 실험으로 확인"으로 구분된다.
- 비목표(1차): 간격 반복 스케줄링(§7 끝에 확장 여지만 남김), 사용자 작성 질문 공유, 커뮤니티·댓글, 음성 인식, 결제, 외부 질문 크롤링, 오프라인 큐.
- 성공 기준: 만든 사람이 실제 면접 전 2주 동안 매일 쓴다. 지표(활성 일수, 체크한 질문 수, 랜덤 면접 완료 수)는 서비스 안에서 볼 수 있으면 충분하다.

### 3.2 실측으로 확인한 것 (2026-10-20, grep 계수)
- 문서마다 `### Q.` 수 = `**모범 답변` 수 = `**핵심 키워드` 수가 **정확히 일치**한다. 기계 변환이 가능하고, 불일치는 곧 변환 실패로 취급할 수 있다.
- 질문 구조는 `## 기본 / ## 심화 / ## 꼬리 질문`, 끝에 `## 출처`. 02·06·07은 `## 개요` 또는 `## 버전 변화 한눈에 보기` 같은 **질문이 아닌 절**이 더 있다(파서가 건너뛰어야 한다).
- 코드 블록이 많다(총 126개 펜스 줄). 렌더러가 코드 하이라이트를 지원해야 한다.

### 3.3 v1 가정이 틀렸던 곳 (설계에 반영함)
1. **"꼬리 질문"은 체인이 아니다.** 39개는 `## 꼬리 질문` 절에 모여 있지만 **부모 질문과의 연결 정보가 없다**(독립된 함정·심화 질문). 따라서 v1의 `parent_id` 자동 생성과 "꼬리 질문 체인" 모의 면접은 불가능하다. → 계층을 `BASIC / DEEP / TRICKY`로 두고, 연결은 선택적 `question_link(from, to)`를 **사람이 지정**한다. 모의 면접은 "BASIC에 답하면 같은 주제의 DEEP/TRICKY 중 미평가·취약 항목을 이어서 낸다"로 정의한다.
2. **출처는 질문 단위가 아니라 문서 단위다.** 각 문서 끝 `## 출처`에 URL 목록이 있고 질문별 출처는 없다. → `source`는 `topic`에 달고, 질문에는 "근거 종류"만 둔다.
3. **근거 배지 표기가 문서마다 다르다.** 실제 표기 분포: `(공식 문서)` 69, `(공식)` 40, `(보충)` 96, `(실험 확인)` 15. 게다가 02·06은 "**표시가 없는 사실은 공식 문서에서 확인한 것**"이라는 규칙을 쓰고(06은 `(공식` 표기 0건), 나머지 문서는 표시가 있어도 `공식 문서:` 글머리처럼 괄호 없는 형태가 섞여 있다. → 배지를 문서 전체에서 자동 추출하면 틀린다. **문서별 규칙을 설정으로 두고**(`default_evidence: OFFICIAL|UNKNOWN`), 질문 단위 요약은 "(보충)이 하나라도 있나"만 자동 판정한다. 나머지는 검수 때 사람이 확정한다.
4. **"공식 문서를 모델이 요약해서 읽었다"** 는 경고가 시드 README에 있다(2차 전달). 즉 시드 전체가 `draft`다. 공개 서비스에서 틀린 정보는 면접 준비를 오도하므로 **검수가 노출 조건**이다(§5).

## 4. 콘텐츠 정책
- 질문·답변은 **공식 문서를 읽고 직접 정리한 것**만 싣는다. 책·블로그·타 사이트 문구는 옮기지 않는다(공개 서비스, 저작권).
- 콘텐츠는 코드가 아니라 **데이터**다. 저장소 `content/<topic>/*.md`(질문 하나당 파일 하나 또는 편당 파일 하나, §5.2)가 원본이고 DB는 사본이다. 손으로 INSERT 하지 않는다.
- 항목마다 **기준 버전**(예: Spring Framework 7 / Boot 4)과 마지막 검수일을 둔다. 버전이 오르면 낡은 항목을 찾을 수 있어야 한다.
- 개인 프로젝트 경험 이야기(STAR)는 이 서비스에 넣지 않는다(비공개 저장소 `interview-prep`).
- 공개 레포 원칙: 문서에는 서비스의 설계와 쓰임만 적고, 약점·운영 세부는 git 제외 `.private/`에 둔다.

## 5. 콘텐츠 파이프라인과 검수 (가장 큰 위험)

### 5.1 검수가 병목이다
159개 전부를 공식 문서와 대조하는 일은 작지 않다(질문당 5~10분이면 13~26시간). 그래서 **노출 단위를 질문이 아니라 주제(편)로** 한다. 한 편의 검수가 끝나면 그 편만 공개한다.
- 검수 완료 기준(질문당): ① 답변의 사실 주장이 출처 URL의 공식 문서와 일치 ② `(보충)`은 보충으로 남기되 틀리지 않음 ③ 버전 기준 표기 ④ 실험이 있는 주장은 테스트가 통과하는 것을 확인.
- 검수 순서 권장: **트랜잭션**(실험 36개로 근거가 가장 단단하고 면접 빈출) → JPA → IoC/DI → AOP → MVC → 부트 → 기타.
- 사이트 기능 개발은 검수와 **병렬**로 간다. 개발 중에는 검수가 끝난 1편(트랜잭션)만으로 모든 화면을 시험한다.

### 5.2 변환기 (M0)
- 입력: 시드 마크다운. 출력: `content/` 하위 질문 파일(frontmatter + 본문) 또는 정규화 JSON.
- 규칙: Q·모범 답변·키워드 개수 불일치 시 **실패**. 질문 아닌 절은 건너뜀. 문서별 설정(§3.3의 배지 기본값)을 읽음. 코드 펜스 보존.
- 질문 `slug`는 **제목에서 만들지 않는 안정 ID**(`<주제약어>-<번호>`, 예: `tx-07`). 변환기가 첫 실행 때 한 번 부여하고, 이후 slug는 파일에 고정되어 변환을 다시 돌려도 바뀌지 않는다. 제목을 고쳐도 학습 기록이 끊기지 않게 하기 위함이다.
- 골든 테스트: 시드 159개를 변환하면 7편·159개·꼬리 39개가 나오고, 같은 입력에서 두 번 실행해도 결과가 같다(멱등).

### 5.3 반영(배포)
- 앱 시작 시(또는 배포 단계에서) `content/`를 읽어 DB에 **upsert(slug 기준)**. 파일에서 사라진 질문은 삭제하지 않고 `retired_at`으로 닫는다(학습 기록 보존).
- 질문의 `content_hash`가 바뀌어도 **사용자의 학습 체크·노트는 유지**한다. 단, 재검수 필요 표시(`needs_review`)만 올린다.

## 6. 데이터 모델

### 6.0 도메인 경계와 모듈
한 서비스, 한 DB, 한 배포 단위. 코드는 모듈(패키지)로 나눈다: 도메인 셋(`catalog`, `progress`, `quiz`), 신원 모듈 하나(`account`), 합성 계층(`api`), 공통(`common`)과 설정(`config`).

| 모듈 | 소유 | 쓰는 주체 |
|---|---|---|
| `account` (사용자) | 이 서비스 안의 **사용자 사본** `interview_user(user_id, created_at, deleted_at)`(닉네임·이메일 없음), 현재 사용자 확인(`GET /api/v1/bff/session`), 탈퇴 동기화(`iam_sync_state`, `AccountDeleted` 이벤트). **Doro SDK 를 아는 유일한 모듈**(`config` 제외, ArchUnit R1) | 시스템(첫 쓰기·session 조회, 탈퇴 동기화) |
| `catalog` (사전) | `category`, `topic`, `question`, `question_link`, 검수 상태 | 편집자(콘텐츠 파일) |
| `progress` (학습 진도) | 학습 완료 체크(`user_progress`), 내 노트(`my_note`) | 학습자 본인 |
| `mine` (내 질문) | `my_question`, 내 질문 읽기 창구 `mine.read`(`MyQuestionReader`, 삭제 이벤트 `MyQuestionDeleted`) | 학습자 본인 |
| `quiz` (시험) | `quiz_session`, `quiz_item`, `quiz_question_stats`, 출제 알고리즘 | 학습자 + 시스템 |

사용자의 **원본은 Doro IAM**이다. `account`는 로그인 후 첫 `GET /api/v1/bff/session`에서 IAM 주체 id로 사본 행을 만들고(games의 `game_users`와 같은 방식), 영구 탈퇴 시 익명화·삭제 동기화를 맡는다(§10). 비밀번호·이메일·역할 같은 신원 정보는 갖지 않는다. 다른 모듈은 **`user_id`(UUID)** 만 참조하고 `account`의 엔티티를 쓰지 않는다. 학습·시험은 "사람"을 모델링하는 게 아니라 `user_id`에 붙은 기록이다.

의존 방향(**한 방향만 허용**, 순환 금지):
- `account` → 없음. 현재 사용자 해석(`CurrentUser`)을 인터페이스로 제공하고 **`api` 컨트롤러만** 쓴다. 서비스 계층(`ProgressService` 등)은 사용자 id 를 **인자로 받는다**(M2-PLAN D5): 남의 id 를 읽을 길이 시그니처에 드러나고, 사용자 id 를 입력으로 받는 엔드포인트가 없음을 구조 시험이 고정한다.
- `catalog` → 없음. 사용자 상태가 전혀 없는 읽기 전용 콘텐츠.
- `progress` → `catalog` (질문·주제 가시성 판정과 질문 slug 목록: `isVisibleQuestion`·`visibleQuestionSlugs`), `account` (`AccountDeleted` 이벤트 구독).
- 다른 모듈이 시험 통계를 읽는 통로는 **`quiz.read` 패키지**(`QuizStatsReader`: 후보 판정용 `lastWrongAmong`·`lastWrong`)뿐이다(ArchUnit 로 고정).
- `quiz` → `catalog` (질문 읽기), `account` (`AccountDeleted` 구독), `progress` (**`progress.read` 패키지만**: `ProgressReader` 로 "내가 체크한 질문" 풀 구성, JDK 타입만 반환). **`quiz`는 `progress`에 쓰지 않는다**(`progress.read` 밖의 클래스를 쓰면 ArchUnit 이 빌드를 깨뜨린다).
- 합성 계층(`api`)은 세 모듈을 읽어 화면용 응답을 조립한다. 예: 질문 목록에 `learned`(progress)와 `recentWrong`(quiz 통계)을 붙인다. 모듈 간 호출은 인터페이스(`ProgressReader`, `QuizStatsReader`)로 하고 서로의 엔티티·리포지토리를 직접 쓰지 않는다.
- 모듈 사이에는 **DB 외래키를 걸지 않는다**(질문 ID/slug만 참조, 존재 검증은 서비스 계층). 나중에 `catalog`를 따로 떼어낼 수 있게 하기 위함이지, 지금 서비스를 쪼개자는 뜻은 아니다. 풀 구성이 "카탈로그 ∩ 내 체크" 조인이라 지금 쪼개면 서비스 간 호출만 늘어난다.
- 경계는 아키텍처 테스트로 고정한다(패키지 의존 규칙 위반 시 빌드 실패, 예: ArchUnit).

DB `service_interview`, 서비스 전용 Postgres 역할(도로 DB 계정 분리 규칙). Flyway. 테스트는 **실제 Postgres**(H2는 마이그레이션 문제를 가린다는 전례).

**콘텐츠(공용)**
- `category(slug PK, name, sort)` — 자바, 스프링, 네트워크, DB … 새 카테고리는 데이터 추가만으로 늘어난다.
- `topic(slug PK, category_slug FK, name, sort, description, sources JSONB[url,title], base_version, published BOOL)` — 시드 7편은 모두 카테고리 `spring`. `published`는 주제 단위 노출 스위치.
- `question(id UUID, slug UNIQUE, topic_slug FK, tier[BASIC|DEEP|TRICKY], difficulty 1~3, title, answer_md, keywords TEXT[], has_extra BOOL, evidence_note, sources JSONB(검수 때 대조한 출처 URL, 해시 제외·M1 V2), content_hash, status[DRAFT|REVIEWED], reviewed_at, needs_review BOOL, retired_at, updated_at)`
- `question_link(from_id, to_id, kind[FOLLOWUP|PREREQ|RELATED])` — 사람이 지정(D15). 없어도 동작해야 한다.
- `concept(slug, name, description, sort)`, `question_concept(question_id, concept_slug)` — 통제 어휘 개념 태그(D16). `question.importance` 1~3 또는 미분류(D17). 세 가지 모두 해시 제외 메타데이터.
- 인덱스: `(topic_slug, tier, sort)`. 검색은 `ILIKE` 부분 일치(제목·키워드·본문, 다중 단어 AND)로 하고 **pg_trgm 은 쓰지 않는다**: 159행, 합성 10,000행에서도 6ms 였다(M1-PLAN D1). 행이 수천을 넘거나 지연이 문제될 때 도입한다.

**개인별 학습 상태**
- `user_progress(user_id, question_slug, learned_at, PK(user_id, question_slug))` — **행이 있으면 "완전히 학습함", 없으면 미학습.** 체크하면 행 생성, 해제하면 행 삭제(PUT 으로 상태 지정, 멱등). 진도가 소유하는 사실은 이것뿐이다.
- `quiz_question_stats(user_id, question_slug, ask_count, miss_count, last_asked_at, last_result[CORRECT|WRONG], PK(user_id, question_slug))` — **시험이 소유하는 통계.** 가중 랜덤과 "다시 공부 후보" 표시의 원본이다. 건너뜀은 통계에 반영하지 않는다. **다시 공부 후보 = 내 체크가 있고 `last_result` 가 WRONG 인 질문**(체크가 풀리면 후보도 사라지고, 틀려도 체크는 자동으로 풀리지 않는다).
- `quiz_session(id UUID — 클라이언트가 만든다, user_id, scope JSONB[categories,topics,tiers], include_unlearned, planned_count 1~30, started_at, finished_at)` — 시작할 때 문제 순서를 전부 정해 `quiz_item` 을 결과 없이 만들어 두므로 새로고침해도 이어서 풀 수 있다.
- `quiz_item(session_id, seq, question_slug, result NULL|CORRECT|WRONG|SKIPPED, seconds, answer_text NULL ≤2,000자, answered_at, PK(session_id, seq), UNIQUE(session_id, question_slug))` — 세션 기록. **결과는 한 번 정하면 고정**이다(같은 결과를 다시 보내면 변화 없음, 다른 결과는 409).
- `user_pref(user_id PK, include_unlearned_default BOOL 기본 false)`
- `my_note(user_id, question_slug, body, updated_at)` — **일반 텍스트**로만 저장·표시(XSS 면적 제거). 길이 상한.
- `my_question(id UUID — 클라이언트가 만든다, user_id, title ≤200, answer_text ≤4000, keywords TEXT[] ≤10개·각 ≤40, tier, source_label ≤40 NULL, created_at, updated_at)` — **내 질문**(M4): 사용자 한 명만 보는 질문. slug 는 `my-<id>`, 체크(`user_progress`)·시험(`quiz_*`)은 이 slug 로 가리킨다. 사용자당 300개, 전부 일반 텍스트. 공용 응답·검색·진도 분모에는 절대 섞지 않는다.
- 사용자 사본 `interview_user` 는 `account` 모듈 소유(§6.0). 위 모든 `user_id` 는 IAM 주체 id이며 외래키는 걸지 않는다.

규칙
- 체크·해제는 **멱등**(PUT 으로 상태를 지정, 토글 아님). 더블 클릭이 상태를 뒤집지 않게 한다.
- 질문이 `retired` 되면 풀에서 빠지되 기록은 남는다. 질문 내용이 바뀌어(`content_hash`) 재검수가 필요하면 `needs_review`만 올리고 **학습 완료 체크는 유지**한다(그 변경을 알려 주는 표시만 붙인다).

## 7. 랜덤 출제 명세
순수 함수 `pick(pool, history, n, rng) -> questions` 로 구현하고 난수는 주입한다(테스트가 재현 가능).

- **풀**: 기본은 `내가 학습 완료로 체크한 질문`(`user_progress` 행이 있는 질문). 범위는 카테고리·주제·tier 다중 선택으로 좁힌다. 옵션 "미학습 포함(전체에서)"을 켜면 `published` 전체로 넓힌다(아직 체크하지 않은 것을 점검해 보고 싶을 때).
- **풀 크기 처리**: 풀 < 요청 N 이면 있는 만큼만 내고 "체크한 질문이 N개보다 적습니다"를 알린다. 풀이 0이면 시작하지 않고 질문 은행으로 안내한다.
- **가중 랜덤**: 균등이 아니라 가중치로 뽑되 단순하게 한다.
  - 기본 1.0, 한 번도 안 나온 질문 ×1.5, 마지막 출제가 오래될수록 ×(1 + 최대 1.0), `quiz_question_stats.miss_count` 가 많을수록 ×(1 + 0.25·min(miss, 4)).
  - **같은 세션에서는 중복 금지**, 직전 세션에서 나온 질문은 가중치 ×0.5.
  - "완전 무작위" 모드 스위치를 둔다(가중 없음).
- **자기 평가**: 답을 말해 본 뒤 모범 답변을 보고 `맞음 / 틀림` 두 단계. (키워드 체크리스트가 있어 "키워드 몇 개 말했나"를 보조로 보여 준다.)
  - 맞음 → `ask_count+1`, `last_result=CORRECT`.
  - 틀림 → `ask_count+1`, `miss_count+1`, `last_result=WRONG`. **체크는 건드리지 않는다.** 체크한 질문이 최근 틀렸다면 사전·홈에서 **"다시 공부 후보"** 로 표시되고, 거기에 해제 버튼이 있다(사용자가 직접 해제). 이후 `CORRECT` 가 한 번이라도 나오면 후보 표시는 사라진다.
  - 건너뛰기는 기록만 남기고 가중치에 영향 없음.
- **엣지**: 같은 질문 중복 제출은 `(session_id, seq)` 로 멱등. 풀에서 질문이 도중에 retired 되면 그 세션에서는 그대로 진행. 탈퇴 사용자는 §10 삭제.
- 테스트: 풀 구성(체크/미체크/주제 필터/옵션), 풀 부족·0, 세션 내 중복 없음, 가중치 계산(경계값), 오답 후보 표시 조건(체크한 질문이 최근 오답일 때만, 이후 정답이면 해제됨), 시험이 진도에 쓰지 않음(아키텍처 테스트), 멱등, 다른 사용자 데이터 격리.
- **확장 여지**: 나중에 간격 반복이 필요하면 `quiz_question_stats` 에 `due_at/interval` 을 더하고 `pick` 의 가중치를 대체하면 된다. 이번 범위에서는 만들지 않는다.

## 8. 모드와 화면 (모바일 우선 PWA)
- **홈**: 카테고리별 진도(체크 수/전체), 다시 공부 후보(체크했지만 최근 틀린 질문, 5개까지, 여기서 바로 체크 해제), 내 현황 링크. 시험 시작은 상단 "시험" 탭. *학습 연속 일수는 비목표로 뺐다*(날짜 기반 활동 기록이 새로 필요하다. M3-PLAN §10 Q5).
- **질문 은행**: 카테고리 → 주제 탭, 검색, 필터(난이도·tier·`보충 포함`·**내 체크 상태**). 질문 상세에 모범 답변, 핵심 키워드, **인라인 토큰 근거 배지**(`(공식 문서)`·`(보충)`·`(실험 확인)` 표기 위치에 그대로 배지, M1-PLAN D5), 기준 버전, 주제 출처 링크, **"완전히 학습함" 체크 토글**, 내 노트.
- **빠른 체크**: 주제 목록에서 질문 옆 체크박스로 바로 체크·해제하고, 주제 전체 "모두 체크/해제"는 확인창을 거친다(실수 방지).
- **시험 영역**(상단 탭 "시험") **랜덤 면접**: 범위 선택(카테고리·주제·tier·개수·미학습 포함 여부) → 한 문제씩 질문만 보이고 타이머 → 내 답 입력(선택) → 모범 답변과 나란히 비교 → 맞음/틀림 → 결과 화면(맞힌 비율, 틀린 질문 목록과 각 질문의 "사전에서 보기" 링크).
- **퀴즈(훑기)**(`/skim`, M3 구현): 주제(와 난이도)를 고르면 질문 제목만 보이고 "키워드 보기"로 자가 점검(알았음/모르겠음). **서버에 아무것도 보내지 않고 로그인도 필요 없다**(질문 목록 응답만 쓰고 섞기는 화면 안에서).
- **내 현황**: 카테고리·주제별 진도 바, 30일 출제량·정답률, 자주 틀린 질문 TOP.
- **내 질문**(M4 계획): 내가 추가한 질문 목록·추가·수정·삭제, 일괄 추가, 체크. (관리/편집자 화면은 만들지 않는다.)
- 비로그인 사용자는 질문 은행만 읽을 수 있고, 체크·랜덤 면접·노트는 로그인 유도.
- 접근성·가독성: 코드 블록 가로 스크롤, 큰 터치 영역, 다크 모드. 서비스 워커(PWA)는 M2 에서 구현했다: 네트워크 우선 내비게이션·API 비캐시·안전한 순간 업데이트(M2-PLAN §6, 결과는 §13).

## 9. API (`/interview/api/`, 게이트웨이가 `/interview` 를 떼고 전달)
- 공개(published 주제·닫히지 않은 질문만, 그 외는 404): `GET /api/v1/categories`(주제 포함), `GET /api/v1/topics/{slug}`(질문 요약 목록), `GET /api/v1/questions/{slug}`, `GET /api/v1/search?q&limit`(페이지네이션 없음, limit 기본 30·최대 100, M1-PLAN D2)
- 로그인 필요(없으면 401), M2 구현: `PUT /api/v1/progress/{slug} {learned}`(멱등), `PUT /api/v1/progress {topic, learned, expectedCount}`(주제 일괄; 확인창에 보여 준 개수와 실제가 다르면 **409**), `GET /api/v1/progress/summary`, `GET/PUT /api/v1/notes/{slug}`(일반 텍스트, 2,000자, 공백뿐이면 삭제). 본문은 정해진 필드만 정확한 JSON 타입으로 받는다(모르는 필드·`"false"` 문자열은 400). 사용자 id 는 토큰에서만 얻고 경로·본문·쿼리에 받지 않는다. 게이트웨이는 쓰기를 `PUT` 만 통과시킨다. 로그인 상태 조회는 `GET /api/v1/bff/session`(로그인 필요 없음, 항상 200).
- 로그인 필요, M3 구현: **쓰기는 전부 PUT, 세션 id 는 클라이언트가 만든 UUID**(게이트웨이가 쓰기를 PUT 만 통과시키고, 같은 id 로 다시 보내면 같은 세션이라 멱등이다): `PUT /api/v1/quiz/{sessionId} {count, includeUnlearned, categories?, topics?, tiers?, mode?}`(풀이 비면 400 `QUIZ-400-01`), `GET /api/v1/quiz/{sessionId}`, `PUT /api/v1/quiz/{sessionId}/items/{seq} {result, seconds, answerText?}`, `PUT /api/v1/quiz/{sessionId}/finish`, `GET /api/v1/me/stats`(최근 30일), `GET/PUT /api/v1/me/prefs`, `GET /api/v1/review-candidates`. 남의 세션은 404(존재를 알리지 않는다). 질문·주제 응답에는 로그인한 사용자에게만 `reviewCandidate` 가 `learned` 와 같은 방식으로 합쳐진다.
- 내 질문(M4 구현): `GET /api/v1/mine`, `GET /api/v1/mine/{id}`, `PUT /api/v1/mine/{id}`, `PUT /api/v1/mine/{id}/deleted`, `PUT /api/v1/mine`(일괄). 응답은 `no-store`, 공용 응답에 섞이지 않는다. (편집자 API 는 만들지 않는다.)
- 오류 규격·페이지네이션·레이트 리밋은 games와 같은 규약을 쓴다. 주제의 질문 목록·질문 상세·검색 결과·개념 상세 응답에는 **로그인한 사용자에게만** `learned` 가 합쳐진다(비로그인 응답은 `learned` 키 자체가 없어 M1 과 바이트가 같다). 응답 본문이 곧 사용자별 ETag 이고, 로그인 응답은 `Cache-Control: private, no-cache` 다.

## 10. 인증·권한·개인정보
- **로그인은 처음부터 게이트웨이 모드**(별도 BFF `doro-bff`가 로그인·세션을 맡고 게이트웨이가 Bearer를 붙임). games가 가진 `embedded` 모드(자체 세션·OAuth 클라이언트)는 만들지 않는다. 서비스가 제공할 것은 **Bearer 검증**과 `GET /api/v1/bff/session`(서비스 프로필 모양) 뿐이고, 사용자 행은 로그인 후 첫 session 조회에서 만든다. 붙이는 순서(`Doro/docs/BFF.md`): ① Doro 관리자 API로 OAuth 클라이언트 `doro-interview` 등록(`first_party=true`, 콜백 `/interview/api/v1/bff/callback`) ② **Doro 레포**의 `doro.bff.services.interview.*`(클라이언트·쿠키 이름·경로·CSRF 헤더)와 `doro.iam.oauth-client-ids` 에 추가 ③ **Doro 레포**의 게이트웨이 `nginx.conf` 에 BFF 라우트·`auth_request` 내부 location·API location 설정과 라우팅 시험 기대값 추가. ②③은 Doro 레포 변경이라 Doro 레포 PR이 별도로 필요하다(푸시는 사용자).
- 권한은 코드 분기가 아니라 Guard. 스키마 `interview_question { relation editor: user }`, `@DoroGuard` 로 편집 API 보호. 서비스 토큰은 호출자별(`schema-write`). **M4 에서 편집자 권한과 함께 붙인다**(M2 의 권한은 "본인 것만" 이라 `user_id` 를 토큰에서만 얻는 구조로 보장하고 `doro.guard.enabled=false`, M2-PLAN D3).
- 열람은 공개, 학습·노트·모의는 본인만(소유 검증을 서비스 계층에서, 테스트로 타인 접근 거절 확인).
- **탈퇴 동기화**(M2 구현): SDK 의 주기 조회(`DeletedUsersSync`)가 `DeletedUserHandler` 를 부르고, `account` 가 `interview_user` 에 **무덤 표식을 upsert**(방문한 적 없는 사용자도: 탈퇴 직후 아직 유효한 토큰이 행을 되살리는 경주를 막는다)한 뒤 `AccountDeleted` 이벤트를 발행한다. `progress`(M2)·`quiz`(M3)의 리스너가 **같은 트랜잭션**에서 자기 데이터를 지우고, 하나라도 실패하면 표식까지 롤백되어 다음 주기에 같은 사용자부터 재시도한다. 진행 위치는 `iam_sync_state`. 정책(영구 탈퇴 시): `my_note`, `quiz_item.answer_text`는 **삭제**(사용자가 쓴 글), `user_progress`/`quiz_question_stats`/`quiz_session`/`quiz_item`은 **행 삭제**(통계 가치가 낮다). 30일 유예 정책과 맞춘다.
- 노트·모의 답은 일반 텍스트. 질문 본문 마크다운은 **렌더 시 구조적으로 안전하게** 그린다: 원시 HTML 을 해석하지 않는 렌더러(react-markdown, `rehype-raw` 미사용), `dangerouslySetInnerHTML` 사용 금지(린트). 본문은 저장소 파일(작성자 신뢰)이고, 사용자 입력(노트·답)은 일반 텍스트다. 화면에서는 `script-src 'self'` CSP.

## 11. 구조와 배포
- 구조는 `doro-games` 복제: `src/`(Spring Boot, Flyway, Guard·IAM 연동), `web/`(React+Vite PWA), `docs/`, `scripts/`, `deploy/`, `content/`.
- **포트**: API 8088, 웹 3007. 현재 compose에 쓰이는 포트(3002/3005/3006, 8082/8086/8087, 9000/9001)와 충돌 없음을 확인했다. 배포 전 서버에서 한 번 더 확인한다.
- 배포 체크리스트(사용자가 서버에서 직접 실행하는 단계 표시 ★):
  1. ★ `setup-interview-server.sh`: DB `service_interview`와 전용 역할, `.env`(세션 키 불필요: BFF 모드; 탈퇴 동기화 토큰 `DORO_IAM_INTERNAL_TOKEN` 은 Doro 쪽 `enable-deleted-sync.sh` 가 발급하고 이 스크립트는 있는지만 점검). Guard 서비스 토큰·스키마는 M4. BFF 클라이언트 등록·Doro 설정은 docs/DEPLOY.md 의 "로그인 연결" 순서. 멱등, `--dry-run` 기본.
  2. CI: 백엔드 테스트(실제 Postgres, 격리 포트), 웹 테스트, 변환기 골든 테스트, 병렬 잡. 배포는 main의 CI 성공 후.
  3. ★ 게이트웨이 `/interview/` 반영(백업 → `nginx -t` → reload). CSP는 먼저 Report-Only로 위반 확인 후 강제. 서버 수준 헤더는 location에서 상속되지 않으므로 공통 헤더를 다시 적는다.
  4. PWA: 서비스 워커 precache의 모든 URL이 게이트웨이를 거쳐 **리다이렉트 없이 200**이어야 한다(허브 빈 화면 사고). `navigateFallback`은 허용 목록으로.
  5. 허브(`/`)에 서비스 카드 추가.
  6. 실제 브라우저로 로그인→학습 완료 체크→랜덤 면접→평가 확인(curl만으로 끝내지 않는다).
- 테스트 규칙: Playwright는 내장 Chromium 헤드리스(`PW_CHANNEL=chrome` 쓰지 않음).

## 13. 위험과 결정

### 위험
| 위험 | 영향 | 완화 |
|---|---|---|
| 검수 부족한 내용 공개 | 잘못된 답을 외움 | 주제 단위 `published`, 검수 전엔 비공개 |
| 공식 문서 버전 변화 | 낡은 답변 | 기준 버전·재검수 표시 |
| slug가 바뀜 | 학습 기록 유실 | 파일에 고정된 번호형 slug, 제목 변경과 분리 |
| 배지 자동 추출 오류 | 근거 오표시 | 문서별 규칙 + 검수에서 확정 |
| "학습 완료"를 후하게 체크 | 랜덤 면접이 쉬워져 점검 효과 하락 | 오답 후보 표시, 미학습 포함 옵션, 현황에 정답률 표시 |

| 노트 XSS | 계정 탈취 | 일반 텍스트만 + CSP |
| 서버 반영 단계가 사용자 손 | 배포 지연 | 스크립트 멱등·dry-run, 체크리스트 |
| PWA precache 실수 | 빈 화면 | 모든 URL 200 확인, 실제 브라우저 검증 |

### 확정된 결정 (2026-10-20)
1. **`DRAFT` 노출**: **숨김**(주제 단위 공개). 근거: §3.3-4.
2. **검수 방식**: **트랜잭션 편부터**. 검수는 만든 사람이 출처 URL과 대조하고, 초안 정리는 Claude가 맡는다.
3. **출제 후 평가**: **맞음/틀림 2단계**. 틀려도 **체크는 자동으로 바꾸지 않고** 사전에서 "다시 공부 후보"로 표시, 해제는 사용자가 직접(분리 안 B). 간격 반복은 이번 범위에서 제외.
4. **랜덤 면접의 내 답**: **저장**(`quiz_item.answer_text`, 탈퇴 시 삭제)하고 노트와는 분리.
5. **풀 기본값**: **체크한 질문만**, "미학습 포함"은 옵션. 한 질문의 "학습 완료"는 **본인 선언**(시험 통과를 요구하지 않음).
6. **실험 테스트 연결**: 사이트에는 **코드 발췌와 "실험 확인" 배지만** 싣고 원본 테스트 레포 링크는 보류(공개 여부는 별도 결정).
7. **AI 피드백(M6)**: **보류**. 지인에게 열면 사용량 제한이 필요하다.
8. **이름과 톤**: 가칭 "도로 면접". 도로롱 캐릭터 사용 여부는 UI 단계(M1)에서 정한다.
9. **사전/시험 분리**: **화면·모듈 분리, 서비스는 하나**(`catalog`/`progress`/`quiz`, §6.0). 시험은 진도를 읽기만 한다.
10. **로그인 모드**: **BFF 게이트웨이 모드 고정**(games식 embedded 미구현).
